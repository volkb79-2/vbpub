## HIGH

### H1. `verify-images` will fail for `docker-stats-exporter` (false negative, blocks the build step)
`scripts/release/artifacts.py` SMOKE dict: `"docker-stats-exporter": ["python", "-m", "py_compile", "/app/exporter.py"]`, run as `--user 65534:65534`.
`infra/docker-stats-exporter/Dockerfile` has `WORKDIR /app`, `COPY ... /app/exporter.py` as root, no `USER`, no chown. `py_compile` writes `/app/__pycache__/exporter.*.pyc`; as uid 65534 on a root-owned dir that raises `PermissionError` and exits 1 (reproduced locally with a read-only dir: `[Errno 13] Permission denied: 'ro/__pycache__'`, exit 1). `PYTHONDONTWRITEBYTECODE` does not stop `py_compile`.
Scenario: `cmru release` build step, after bake, `verify-images` reports `docker-stats-exporter: import smoke as uid 65534 failed` and the release aborts although the image is fine.
Fix: smoke with an import that does not write (`python -c "import ast,sys;ast.parse(open('/app/exporter.py').read())"` or `python -B -c "import sys; sys.path.insert(0,'/app'); import discovery"`), or `compile(open(...).read(),...)`. The unit test (`tests/unit/test_release_artifacts.py:159-170`) uses a fake docker runner, so it cannot catch this; add a test that the smoke argv for each image performs no filesystem write, or run the real smoke once on r1002 before P11 (report already recommends one real bake).

## MEDIUM

### M1. Local `--push` with empty REGISTRY targets Docker Hub namespace `dstdns/`
`docker-bake.hcl` release targets: `REGISTRY != "" ? "${REGISTRY}/${RELEASE_NAMESPACE}/dstdns-<svc>:${VERSION}" : "${NAMESPACE}/<svc>:local"`. `docker buildx bake release-registry --push` (or `release-all --push`) with no env resolves to `docker.io/dstdns/<svc>:local` (confirmed by `--print`). Via cmru this cannot happen (the handler's `_docker_login` hard-requires `REGISTRY`, handlers.py:1030, and env.py always sets it), so it is a manual-run hazard only; a failed auth is the likely outcome, but if the operator owns/has access to that Hub namespace an image leaks. Also REGISTRY set with VERSION unset pushes `:local`.
Suggested hardening: a bake variable guard is not possible in HCL, so put the check in `artifacts.py verify-images` (refuse any tag without the registry prefix) or document "never `--push` without env.py" in the bake header. Low effort.

### M2. `base-app` / `dstdns-app-base:latest` (the memo-open point): resolved as safe, but unpinned by any test
`docker buildx bake --print --push release-registry` shows `base-app` keeps `"output": [{"type":"cacheonly"}]` while all 8 release targets get `push=true`. So `dstdns-app-base:latest` is not pushed to Docker Hub or GHCR in the current buildx. The report's "unverified" caveat can be closed on this evidence (still confirm once in P11 with `docker buildx imagetools inspect docker.io/library/dstdns-app-base` being absent, optional). No test pins it; add a config test that `base-app` is never in `release-registry` and its tag carries no registry prefix, so a later "helpful" edit cannot change it. Relatedly the verified (loaded) image and the pushed image are two separate bake runs (`--load`, then `--push`); they are identical only through the BuildKit cache. `verify-images` therefore verifies the pre-push build; `bundle` reads the pushed digest but never re-checks labels on it. Cheap improvement: in `bundle`, `docker buildx imagetools inspect --format '{{json .Image}}'` labels check, or accept the cache assumption explicitly.

### M3. `check_from_empty_dir` masks failure of `ciu env generate` and does the thing the report avoided elsewhere
`artifacts.py` `check_from_empty_dir`: exit code of `ciu env generate` ignored (S16.3 workaround), success judged only by presence of `ciu.env` and `ciu.instance.generated.toml`. A genuine failure after those two files are written (e.g. a template error later in the run) would be hidden. It also runs with the caller's full `os.environ` (CMRU_*, INSTANCE_ID, DOCKER_* leak into the check). The report says `ciu env generate` was not run in the worktree root because it "can create a docker network", yet the check-only path runs exactly that. Not observed here (stage-bundle passed), but P8 should replace this with the ciu fix (CIU-168..171) and until then match on the specific S16.3 message instead of ignoring the code, and run with a scrubbed env.

### M4. Staging copies working-tree bytes of tracked files, not the commit
`stage()` uses `shutil.copy2(repo/rel)`; `expand_allowlist` only checks the path is in `git ls-files`. The docstring says "the bundle is the release commit, never the working tree". In `cmru release` the candidate worktree is clean so it holds; for a manual `stage-bundle --check-only` on a dirty tree the check proves the dirty tree. Also a tracked-but-deleted file gives an uncaught `FileNotFoundError` (not `ArtifactError`, so traceback instead of `[ERROR]`), and symlinks are followed with no guard (none tracked today in the allowlist: checked `git ls-files -s` mode 120000). Suggest `git show`/`git archive` of the commit, or at least `git diff --quiet -- <paths>` plus an `is_symlink()` refusal.
