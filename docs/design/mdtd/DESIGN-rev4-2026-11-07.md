# mdtd: mdt-cockpit host services as a daemon with ctl and socket clients (DESIGN, rev 4: operator-approved, all questions closed)

Status: DESIGN + IMPLEMENTATION PLAN, 2026-11-07, APPROVED (rev 4 closes the four rev-3 questions, section 10). Nothing in the repo was edited and no host was touched.

Rev 3 applies the operator rulings on rev 2:
- (1) Keep it simple.
  - Three levels, with no exec sandbox and no grant or consent machinery.
  - `mdt-control` runs host commands as the caller's regular host user, as if logged in through SSH.
  - `mdt-root` additionally allows `--user=<any host user>`, root included.
  - The typed governance verbs stay.
- (2) Defaults.
  - Listed login users and the runner user get observe and control.
  - root membership is empty.
  - Peers in `dev-gates.slice` and `dev-buildkitd.slice` are refused control and root.
- (3) No Docker proxy, no rootless track, no restricted-template track (only short notes, section 11).
- (4) Rollout.
  - Nothing on the controller host.
  - mdtd is deployed on <host>, then <host>, by fresh reinstalls with the new debian-install-v2 recipe.
  - Rollback is a reinstall.

The rulings from earlier revisions stand:
- Verb homes: `<name>d` root offline + `-t`; `<name>ctl` socket client; `<name>` end user.
- The approved iogovmon ownership matrix.

## 0. Headline (rev 3)

- **Packaging.** One wheel `mdtd` (new cmru project, `mdt-cockpit/mdtd/`) with three binaries:
  - `mdtd`: root, offline, plus `-t` (also ExecStartPre);
  - `mdtctl`: socket client for operating the service;
  - `mdt`: end-user client, replacing the bash `customization/mdt`.

  The verbs are listed in 3.1.
- **Processes:**
  - `mdtd.service`: root core (workers, scheduler, snapshot, journals, control and root levels, exec launcher);
  - `mdtd-observe.service`: unprivileged, serves the snapshot;
  - `mdtd-psiguard.service`: separate, no docker.
- **Three levels, three tool groups, never `docker`** (install refuses it for every level):

  | Level | Group | Socket | Allows |
  |---|---|---|---|
  | observe | `mdt-observe` | `/run/mdtd/observe/mdtd.sock` | read-only |
  | control | `mdt-control` | `/run/mdtd/control/mdtd.sock` | the typed governance verbs, plus `mdt host-exec`/`host-shell` **as the caller's regular host user**: full access to that user's files, an intended container break-out acting as an SSH-like bridge |
  | root | `mdt-root` | `/run/mdtd<home>` | additionally `--user=<any host user>`, root included; membership empty by default |

- **Regular user = the socket peer's uid mapped to the host account with that uid.**
  - The cockpit templates and the runner already give the container user the host user's uid.
  - An optional `[exec.uid_map]` in `/etc/mdtd/mdtd.toml` overrides the mapping.
  - Refused: no matching account, uid below 1000, uid 0, or a nologin shell.
  - **This is advisory when the container user can change uid** (sudo in the container): such a caller can act as any regular host user.
- **Exec mechanism.**
  - A transient systemd unit via `systemd-run --uid=<user> -p PAMName=mdtd-exec`, so the PAM and logind session look like an SSH login.
  - `--pty` for the shell, `--pipe` for commands. The client's stdio is passed over the socket.
  - The exit code passes through. cwd is mapped through the peer container's bind mounts, else the user's home. The environment is minimal.
  - The unit is stopped when the client disconnects.
  - Audit records argv, user and peer cgroup.
  - No sandbox, no time cap, no grants. A kill-switch file per level stays, because it is trivially cheap.
- **Unchanged from rev 2:** the cgroup workers, the approved iogovmon ownership matrix (IO re-assert never ported, deleted at IG-15b), the doctor port with check.sh deleted, and the bug fixes (psi-guard throttle undone, inert `io.weight`, run-gate treating absence as emptiness).
- **Deployment.**
  - Each stage goes to <host>, then <host>, by a **fresh reinstall**. The pipeline: debian-install-v2 (data-area-v2 partitioning from config), then the host-setup consumer, which runs `cgpd install`, `toposd install`, `mdtd install`, the `iogovmon` install per its flags, the tool groups and the listed users.
  - Verification order: the existing VM lanes first, then the doctor chain on the real host.
  - Rollback is a reinstall.
  - Because every host is installed fresh, there is no upgrade or migration code and no P-11 exercise. The controller host and its devcontainer are untouched.
- **Cross-plan amendment X-01 remains:** `cgpd install` and `toposd install` refuse docker for every level, and the sockets plan's phase-2 docker defaults change to tool groups.

## 1. Goals, non-goals, threat model

### 1.1 Goals
1. Devcontainers and agents see the host governance state, structured, without host-root.
2. Routine governance operations need no privileged helper.
3. Host commands become an explicit, audited bridge:
   - as the caller's own host user (control);
   - as any user, root included (root).
4. One supervised home for the resident logic, and one structured doctor.
5. Single-writer ownership with iogovmon (approved matrix). No duplication of cgpd, topos or iogovmon.
6. The host decides access by group membership and mounted level directories.

### 1.2 Non-goals
- A tuning API (iogovmon).
- Wrapping cgpd or topos.
- dockerd configuration.
- Confining exec.
- A Docker proxy, rootless Docker, a restricted template (section 11).
- Any rollout on the controller host.
- deb packaging.

### 1.3 What each level means (stated plainly)
| Level | Effect of holding it |
|---|---|
| observe | Read governance numbers, unit states, container names, slices and caps. No state change, no env, cmdlines or files. |
| control | Run the typed governance verbs (3.6) AND **act as your regular host user** on the host: read and write that user's files, run anything that user may run, including docker if that user is in the docker group. For a caller whose container user can change uid (sudo, container root), that means **any regular host user** with uid ≥ `min_uid`, because the peer uid is chosen inside the container. |
| root | Act as **any host user including root**: full host root. |

- **Devcontainers that hold the Docker socket** (`templates/devcontainer.json:75`, `:222`) are host-root-equivalent regardless. For them mdtd adds a documented, audited path instead of the privileged nsenter helper (`customization/mdt:268-270`, `:328-335`). The repo's incident notes name that helper as the likely trigger of cgroup2 flags being stripped (`scripts/debian-install-v2/testing/vm/USAGE-TESTING.md:647-663`).
- **Container root bypasses socket DAC**, and **container root can `setgroups()` any GID**, because there is no userns-remap. So group gating, like uid mapping, is advisory against a container user who can become root.
  - The daemon still re-checks the GID for container peers, so the honest and the careless are stopped.
  - Container uid 0 is never treated as root on control.
- **Default lane-tier deny.** Peers in `dev-gates.slice` and `dev-buildkitd.slice` are refused control and root even when they hold a GID (`[levels] deny_slices`, configurable).

### 1.4 Audit
- File: `/var/lib/mdtd/audit/audit-YYYY-MM.jsonl` (0600, directory 0700 root), append-only with `fsync`, hash-chained.
- Rotation: 16 MiB × 8. A one-line copy goes to journald (`SYSLOG_IDENTIFIER=mdtd-audit`).
- Records: `{ts, boot_id, seq, prev_sha256, principal{kind, pid, uid, gids, cgroup, container_id, container_name}, level, verb, args, decision, result, duration_ms}`.
  - For exec: `argv` (full), target `user`, `tty`, host `cwd`, the unit name, the exit status.
- Refusals are aggregated per (principal, code) per minute.
- `mdtd audit show|verify` on the host.
- Not tamper-proof against root-level users (they are root). Arguments are logged in full; secrets belong on stdin.

### 1.5 Bounds (connection hygiene, not confinement)
- Request line 64 KiB with a 10 s deadline. Argv ≤ 256 elements and ≤ 32 KiB.
- Observe: 64 readers, 20 req/s per principal (burst 40), 4 event streams per principal.
- Control and root: 16 readers. Typed-verb rates are in 3.6.
- At most 32 concurrent exec sessions per host. An exec has no time cap.

### 3.3 Groups, users, discovery
- **Groups.** `mdtd install` installs a sysusers file:

  g mdt-observe
  g mdt-control

  It refuses `docker` (name or GID) for any level, and equal GIDs.
- **Members.**

- **Devcontainers.**

  1. the group exists (`getent`);
  2. it is not the docker GID;
  3. the host user is a member;
  4. the current session holds it ("re-login" otherwise);
  5. the exported GID equals getent ("refusing to add a GID you do not hold" otherwise);

  Each message names the remedy: the `MDTD_*_USERS` key, re-running install.sh, a new login, then a rebuild.
- **Runner.** `scripts/netcup/runner/start-cockpit-runner.sh` (today `--group-add "$(getent group docker | cut -d: -f3)"`, line 14):
  - adds `--group-add` for each level GID that `RUNNER_USER` holds, and mounts all three level directories;
  - refuses without observe;

### 3.4 Authorization
1. **Mount:** the level directory must be mounted (L1).
2. **Socket DAC:** the socket's group and mode (L2).
3. **Daemon-side GID re-check:** a container peer must hold the level GID; a host peer is checked by gid. Identity is read race-free: `SO_PEERCRED`, then `SO_PEERPIDFD`, then `/proc/<pid>/{cgroup,status}`, then a `pidfd_send_signal(0)` liveness check.
4. **Lane-tier deny:** default `deny_slices = ["dev-gates.slice", "dev-buildkitd.slice"]` for control and root.
5. **Kill switches:** `control.disabled` and `root.disabled` refuse the whole level.
6. **Audit.**

There is no allow-list, grant or approval layer. Kernels without `SO_PEERPIDFD` get observe only.

### 3.7 Exec: `mdt host-exec` / `mdt host-shell`
**Request.**
- Line: `{"verb": "exec", "args": {"user": null | "<name>" | <uid>, "argv": [...] | null, "tty": bool, "cwd": "<caller path>", "env": {"TERM": …, "LANG": …, "LC_*": …}}}`.
- `argv: null` means a login shell.
- The client passes its stdin, stdout and stderr (or its tty) by `SCM_RIGHTS` on the connection.

**Target user.**
- **The mapped regular user** (the default; control and root):
  1. Take the peer uid from `SO_PEERCRED`. Without userns-remap it is the host uid. The cockpit's uid alignment (`MDT_USER`/`MDT_UID` in the templates; runner `usermod -u $runner_uid`, `start-cockpit-runner.sh:39-40`) makes it equal to the launching host user's uid.
  2. If `[exec.uid_map]` in `mdtd.toml` has an entry for that uid (for example `1000 = "volker"`), use it.
  3. Otherwise use `getpwuid(uid)`.
  4. **Refuse** when no host account has that uid, when the uid is below `min_uid` (default 1000; covers uid 0 and system accounts), or when the account's shell is `nologin`/`false` (as SSH would).
  - Host peers map to themselves under the same rules.
  - **Advisory when the container user can change uid:** a container root can `setuid()` to any uid, so the mapping then admits any regular host account. That is stated in 1.3 and in `mdt host-exec --help`.
- **`--user=<name|uid>`**: accepted only on the root level. Any existing host account, root included. A nologin shell is allowed here (explicit root intent).

**Launch** (recommended mechanism: a transient unit, not fork+setuid):
- Command:
  ```
  systemd-run --unit=mdtd-exec-<id> --slice=mdtd-exec.slice --collect --wait --quiet --send-sighup
              --uid=<user> -p PAMName=mdtd-exec -p WorkingDirectory=<host cwd>
              --setenv=TERM=… --setenv=LANG=…
              --pty | --pipe   -- <argv | the user's login shell with -l>
  ```
  The received fds become systemd-run's stdio.
- Why a transient unit:
  - PID 1 starts it in the host namespaces. The core itself runs in a `ProtectSystem=strict` private mount namespace, so a forked child would inherit a read-only filesystem.
  - systemd performs `initgroups`, sets `HOME`/`USER`/`SHELL`, and with `PAMName=` opens an account+session PAM stack (pam_systemd creates a logind session, `XDG_RUNTIME_DIR`, limits). That is the SSH-login semantics without authentication.
  - It is the `run0` pattern (systemd 256 or later).
  - A hand-written setuid helper would have to reimplement all of this.
- **cwd mapping.** The client sends its cwd.
  - For a container peer, mdtd maps it through the peer container's bind mounts (docker inspect `Mounts[].Destination → Source`, longest prefix), for example `<checkout>` to the host checkout path.
  - If that is unmappable or not accessible to the target user, it falls back to the target user's home, and a note goes to stderr.
- **Environment:** minimal. `TERM`, `LANG` and `LC_*` from the client, plus what PAM and systemd set. No other client env.
- **Exit code:** the remote command's status. 125 means a launch failure, as with docker.
- **Disconnect:** `systemctl stop mdtd-exec-<id>` kills the unit's cgroup.
- **Signals:** Ctrl-C reaches the command through the pty, or is forwarded as SIGINT in pipe mode.
- **No time cap and no resource confinement** beyond the accounting slice (ruling).

### 3.9 Wire protocol and exit codes (cgp conventions: `scripts/cgroup-profiler/src/cgprofile/ctlwire.py`, `docs/PROTOCOL.md` §2, §6, §10.1, `docs/CGPCTL-SPEC.md` §1)
- One JSON line `{"verb","args","contract"}`: exactly those keys, duplicate keys refused, NaN refused, unknown args named.
- One response line `{"ok", "contract", "schema", "data"}` or `{"ok": false, "error": {"code", "message"}}`.
- Streaming for `events-follow` and `exec` (the last line is `{"event": "exit", "status": N}`).
- Own stdlib module `mdtd.wire`.

| Error code | Exit |
|---|---|
| `bad-argument`, `unknown-verb`, `wrong-level`, `not-streaming` | 2 |
| `peer-refused`, `level-disabled`, `user-refused` | 2 |
| `precondition`, `not-available` | 3 |
| `rate-limited`, `busy`, `conflict`, `daemon-error` | 1 |
| unreachable, with cause `socket-not-mounted|socket-missing|daemon-refusing|socket-permission|contract-unsupported` | 3 |
| exec | the remote status; 125 = launch failure |
| Ctrl-C | 130 |

## 4. Processes, privileges, state
| Process | User | Does |
|---|---|---|
| core | root | scheduler and steps, `docker events` child, inotify, snapshot, journals, doctor runner, control and root levels, exec launcher |

Rules:
- Only `mdtd.apply.*` may write cgroupfs or the override file, or call `set-property`, `mount -o remount`, `docker rm` or `systemd-run`. A static per-call-site allow-list enforces it, plus a mutation test.
- The observe server imports no writer module.

Hardening (aligned with `scripts/cgroup-profiler/src/cgprofile/data/cgpd.service.in`):
- Core:
  - `MemoryMax=384M`, `CPUQuota=50%`, `TasksMax=128`, `OOMScoreAdjust=-500`;

  - restart backoff.
  - VM spike M1-03a: cgroup2 remount from the private mount namespace, and `systemctl`/`systemd-run`/`docker` socket reach under it.

## 6. Deployment: fresh install of <host>, then <host> (no controller host)
**Rule.** Every mdtd stage is delivered to a host by **reinstalling** it with debian-install-v2 and the stage's pinned releases:
- <host> first, verified, then <host>, each with an operator go;
- never <protected-host>;
- the controller host and its devcontainer are not touched.

Consequences:
- There is no upgrade, migration, P-11 or rollback code to write or test. `install` must still be idempotent (a second run is a no-op).
- What a stage deletes is simply no longer installed.

**What the installer runs** (DIV2 stages; the data-area-v2 partitioning from branch `div2-data-area-v2-20261105` must be on main first):
1. **Stage 1** (existing): partition table and data area from config sizes (data-area-v2 `partitioning` object), swap, Docker install + `daemon.json`, users and SSH keys (`_configure_users` `installer.py:913`, `_configure_persistent_ssh_keys` `:4588`), apt, journald.
2. **Stage `host_services`** (new, INST-01; plan 5.8 generalised):
   1. fetch the pinned bundle (wheels + sha256: mdtd, cgprofile, topos, augeaswrap, cli-extended, iogovmon, iobench, plus the mdt-cockpit host-setup release tarball; augeaswrap and cli-extended are a wheel pair, zipimport-able, stdlib-only; the `mdt-host-setup` fragment and the service fragments are published through `augeaswrap endpoints publish`);
   2. write `/etc/mdt/host-setup.env` from the installer JSON object `mdt_host_setup` (the values the wizard would ask for, incl. `MDT_HOST_USERS`, `MDTD_*_USERS`, slice sizes, `HOST_ROLE`, `IOGOVMON_INSTALL`/`IOGOVMON_MODE=adopt`);
   3. run host-setup `install.sh` non-interactively (it becomes a caller of augeaswrap, work package HS-2). In order, it:
      - renders slices, drop-ins and BuildKit;
      - runs `cgpd install`, `toposd install` and `mdtd install` (zipimport bootstrap, plan P-7) with the per-level users;
      - runs `iogovmonctl install --baseline-only` only when `IOGOVMON_INSTALL=install` (IGM IG-13a/IG-15a, adopt mode);
      - installs `/etc/profile.d/mdt-host-groups.sh`;
      - publishes the admission cap;
   4. run `mdtd doctor --json`. A failed check fails the stage and sends the installer notification.
3. **First login** by the operator; then start the devcontainers and the runner from the current templates (first creation on a fresh host).

**What verifies it, in order:**
1. **VM first.**
   - The existing debian-install-v2 QEMU/TCG harness (`scripts/debian-install-v2/testing/vm/`) runs a full install with `host_services` enabled on a fresh guest.
   - The existing mdt-cockpit `vm-system` lane (`HS/tests/run-vm-acceptance.sh`) runs the host-setup and mdtd assertions.
   - No new lane: the case is added to the existing DIV2 VM test cases and to `vm-governance-acceptance.sh`.
2. **Real host, after the reinstall** (Sonnet host agent or controller):
   1. The doctor chain: `cgpd doctor --json`, `toposd doctor --json`, `iogovmonctl doctor --json` (if installed) and `mdtd doctor --json` (aggregates the others) are green.
   2. Inside a devcontainer and the runner: `mdt doctor` and `mdtctl status` are green.
   3. `mdt host-exec -- id` shows the login user (M2).
   4. A lane runs and its psi-guard classification reads `known` (S1-10).
3. Only then <host>.

**Rollback** is a reinstall with the previous recipe and pins.

**The data area is NOT preserved** (decision 10.2). Each reinstall deliberately applies the new data-area-v2 sizing (repartition), so the data area is recreated. Before each reinstall, R2 evidence and closeouts are exported to the controller, following the <host> precedent of 2026-11-05 (`reports/<host>-reinstall-REPORT.md`, `reports/reinstall-READINESS-20261105.md`). That export is part of INST-02.

## 9. What could go wrong (adversarial)
1. **Control is a deliberate break-out.** A compromised container whose user can change uid acts as any regular host user, which includes any user in the docker group, which is root. The doctor `level-policy` check lists `mdt-control` members who are also in `docker` as a `warn` ("control = root for this user"). It is accepted by ruling.
2. **uid alignment drifts** (a template without `MDT_UID`, a container user created at another uid). The mapping then maps to another account or refuses. `mdt whoami` shows the mapping before use, and `[exec.uid_map]` pins it.
3. **The core is a single point of failure for governance.** psi-guard is separate, applied values persist, watchdog and sweep, `Wants=` on sockets.
4. **`-t` in ExecStartPre refuses start after a bad env edit.** Caps persist, new containers stay uncapped, psi-guard checks only its own keys, and `systemctl status` shows why.
5. **The port regresses caps** (MDT-016). Differential tests, VM parity, the never-withdraw rules as named tests.
6. **`systemd-run` semantics** (fd forwarding, `--pty` on a passed tty, exit-code passthrough with `--wait`, PAM session creation) are inferred. M2-03 has VM rows. Fallback: `--pipe` only, and read `ExecMainStatus` via `systemctl show` before collect.
7. **Every stage needs a reinstall** of <host> and <host>, and the data area is recreated each time. R2 campaigns pause, and caches are lost. Evidence survives only through the INST-02 export.
8. **The shared image changes `mdt`.** The controller's devcontainer stays pinned to a pre-M2 image until a reinstall decision for that host (decision 10.3).
9. **Secrets in exec argv end up in the audit log.** Documented.
10. **Kernels without `SO_PEERPIDFD`** get observe only (fail closed).

## 10. Decisions (all questions CLOSED, operator 2026-11-07)
1. **Every stage is delivered by full reinstall.** No in-place upgrade code is written.
2. **The data area is not preserved.** Each reinstall applies the new data-area-v2 sizing, so the data area is recreated. R2 evidence and closeouts are exported to the controller before each reinstall (INST-02, <host> 2026-11-05 precedent).
3. **The controller's devcontainer is pinned to a pre-M2 image** (keeping `host-escape`) until a reinstall decision for the controller host. M2-04 records the pin in the controller's `devcontainer.json.local`.
4. **Exec mechanism and uid mapping as designed:** `systemd-run` transient unit with `PAMName=mdtd-exec`; identity by peer uid ≥ 1000 with an optional `[exec.uid_map]`; refuse otherwise.
