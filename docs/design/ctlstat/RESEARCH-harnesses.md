# ctlstat research: which harness to extend instead of building workarounds or a UI

Date 2026-11-09. Read-only research. Web content treated as untrusted data. Shallow clones of pi, opencode and (sparse) codex were READ in the scratchpad and deleted; nothing was built, installed or run. Local installed packages (pi 1.5.0 docs, opencode 2.2.6, reasonix 2.58.0, codex 0.167.0, claude 2.1.319 under `/opt/mdt/npm/lib/node_modules`) were read as files only. Builds on `ctlstat-REQUIREMENTS.md` 10-12.3, `ctlstat-RESEARCH-compaction-endpoints.md` and `ctlstat-EXPERIMENT-compaction-hooks.md`; where this report corrects the earlier compaction research it says so.

## Summary (10 lines)

1. Open source, all of them except Claude Code: opencode MIT, pi MIT, reasonix MIT, Codex CLI Apache-2.0, Goose Apache-2.0, OpenHands SDK MIT. Claude Code is proprietary ("SEE LICENSE IN README.md" in its npm package). LICENSE files for opencode, pi and Codex were read in the clones; reasonix, Goose and OpenHands are cited from `package.json` / GitHub API (SPDX), not the LICENSE file.
2. Repo identities (verified via GitHub API): opencode = `anomalyco/opencode` (formerly `sst/opencode`; the org Anomaly, dev branch `dev`); pi = `earendil-works/pi` (formerly `badlogic/pi-mono`; bought by Earendil, Mario Zechner still the main committer); reasonix = `esengine/DeepSeek-Reasonix` (Go CLI plus Studio desktop app, DeepSeek-first but any OpenAI-compatible provider).
3. The earlier compaction research is CORRECTED for opencode: v2 (2.2.x, the rewrite we have installed) has a plugin hook `compaction` whose `result` field replaces the model request with our own summary (`packages/plugin/src/promise/session.ts` `SessionCompaction`). So opencode is pluggable, not "no instruction channel"; only its HTTP `POST /api/session/:id/compact` has no instruction field.
4. Best fit for G-b/G-d (inject after tool calls, agent-written compaction prompt, pluggable summarizer): **pi**. `tool_result` hook can modify results, `context` hook edits each LLM request, `session_before_compact` supplies our own summary, RPC `compact` takes `customInstructions`, JSONL has exact per-message usage. No patch needed.
5. Best fit for "do not write a UI" and unattended server operation: **opencode v2**. A long-lived server (`opencode serve`/service) owns sessions, jobs and schedules; TUI, web app and desktop app attach as clients; HTTP API has prompt, synthetic (wake), compact, context, interrupt, schedule. Cost: v2 is days old (2.2.5 on 2026-10-30, 2.2.6 on 2026-11-06), Effect-4 plugin API, 4,211 open issues.
6. **Codex CLI** is already our worker harness and has a real app-server (stdio/unix/ws, `codex --remote ADDR` TUI attach) and PostToolUse `additionalContext` hooks, but compaction is the weak spot: `thread/compact/start` takes only `threadId`, PreCompact stdout is ignored (source test `pre_compact_ignores_plain_stdout`), OpenAI-provider compaction is opaque. Smallest patch: add `instructions` to `ThreadCompactStartParams` (Rust, drift-heavy).
7. **Claude Code** meets G-a, G-b, G-d by measurement (E1-E4) and stays a valid controller host; it cannot be extended beyond hooks, and a Claude subscription is reportedly not usable from third-party harnesses (third-party claim, UNVERIFIED), so Anthropic models in pi/opencode likely mean API billing.
8. reasonix: promising extension protocol (17 hook points incl. `tool.after`, `compaction.prepare/complete`, `host/prompt/submit`, ACP over stdio) but hook semantics and per-turn usage storage are undocumented, single-maintainer (two humans hold ~85% of commits). Use as worker only. Goose: hooks have no `additionalContext`, compaction template static: not better than the above. OpenHands SDK (Python, custom `CondenserBase`, agent-server REST/WS): a build-on library, only worth it if we want a Python controller of our own.
9. Ranking for our goals: 1 pi (hackability, goals G-a..G-d without patches), 2 opencode v2 (UI/server, G-c/e/g native, G-d via plugin), 3 Codex CLI (keep as worker), 4 Claude Code (keep as controller until a PoC passes), 5 reasonix, 6 OpenHands SDK, 7 Goose. Do not fork anything; both top picks are extensible by plugin/extension in TypeScript.
10. Smallest proofs of concept (half a day each, throwaway sessions, no estate files): pi extension (change-only `tool_result` injection plus `session_before_compact` reading a handover file, driven by `pi --mode rpc`), and opencode plugin (`compaction` hook returning an external summary, driven by the HTTP API). Section "PoC proposal" has the exact steps and pass criteria.

## Goals used (from the task)

G-a machine-readable log with per-turn usage; G-b hook that injects change-only text after tool calls, with state; G-c wake an idle session on an external event; G-d harness-neutral external compaction (agent writes handover, service resumes and compacts, ideally pluggable summarizer); G-e unattended/headless with resume, ideally server/API so a separate UI attaches; G-f multi-model routing (gpt-6-luna, deepseek-v4.1-flash via gateways, Anthropic); G-g detached subagents/jobs that survive the controller; G-h licence and project health.

Legend: NATIVE = works as documented/measured; CONFIG = config or hook script only; PLUGIN = needs our own plugin/extension code in the harness's extension API (no source change); PATCH = needs a source change (location given); NO = not feasible.

## Per-harness notes

### pi (earendil-works/pi)
- Identity: Mario Zechner's `badlogic/pi-mono` (created 2025-08-09), moved to `earendil-works/pi`; sources agree Earendil acquired it in April 2026 (secondary reporting; the repo move itself is verified by the installed package: `repository.url git+https://github.com/earendil-works/pi.git`). Packages: `ai` (provider API), `agent` (7k lines loop), `coding-agent` (the CLI, 174k lines with tests), `tui`, `mcp`, `codemode`, `durable`, `chord`.
- Extension API is the richest read: events `tool_call` (can block), `tool_result` (**can modify result**, partial patches chain like middleware), `context`/`context_with_system` (before each LLM call), `before_provider_request`, `agent_before_settle` (can append entries and request one continuation), `turn_end`, `session_before_compact/session_compact/session_compact_failed`, `cache_warming_decision`; API `pi.sendMessage` (steer/followUp/nextTurn, `triggerTurn`), `pi.sendUserMessage`, `pi.appendEntry`, `pi.registerTool`, `ctx.getContextUsage()`, `ctx.compact()`, `ctx.waitForIdle()`, `ctx.newSession()`; extensions are TypeScript loaded from `~/.pi/agent/extensions` or packages (`docs/extensions.md`).
- Compaction details that matter to R12.3/R12.9: threshold `contextTokens > contextWindow - reserveTokens` (default 16,384) with per-model `compaction.modelOverrides`; the summary is a fixed Markdown template with mechanical read/modified-file lists; tool results truncated to 2,000 chars for the summarizer; summarization "disables prompt-cache writes" (so it does NOT reuse the warm cache, unlike Claude `/compact` and opencode); an extension can substitute the whole summary, which makes pi the cleanest host for the HYBRID plan (mechanical skeleton L0 plus our short prose L1 from a cheap model) with no patch.
- Gaps: no server socket (RPC is a child-process protocol, one client); no attach UI; the web UI is experimental. Anthropic subscription use is reportedly blocked for third-party harnesses (third-party article, UNVERIFIED), so Claude in pi means API billing.
- G-d flow in pi: agent writes `handover.md` and ends; service runs `pi --mode rpc --session <file>`, sends `{"type":"compact","customInstructions":"<handover>"}` (or an extension's `session_before_compact` reads `handover.md` and returns our summary), waits for the response (`estimatedTokensAfter`), then sends `prompt` "continue". RPC `compact` response reports usage so the cost record needed by section 10.1(d) comes for free.

### opencode (anomalyco/opencode, v2)
- v2 is a ground-up rewrite (packages `core`, `server`, `protocol`, `plugin`, `sdk`, `tui`, `app`, `desktop`, `session-ui`, `process-daemon`). Not the older v1 the compaction research quoted. Installed here as `opencode`/`opencode2` 2.2.6.
- Server API (`packages/protocol/src/groups/session.ts`): `session.create/list/get/fork/prompt/synthetic/shell/compact/wait/interrupt/background/context/stats/export/import/inbox.*`, `event.subscribe` (`GET /api/event`), `schedule.*`, `job.list`, `usage.limits`, forms, worktrees, PTY. Auth: password / pairing tokens (`packages/server/src/auth.ts`). One generated client (`packages/client`).
- Plugin API (`@opencode/plugin`, Promise or Effect flavour): transforms (agent, command, mcp, model, provider, tool, skill), runtime hooks (`session.hook` for `prompt`, `context`, `compaction`, `generate`, `title`, `model.request`, `http.request`, `retry`, `experimental.idle`; `tool.hook` for `execute.before/after`), RPC, GUI and TUI plugins. Plugins resolve `effect` from the host, so a plugin must be written against Effect 4 types: a learning-curve and drift cost.
- Compaction: auto at `buffer` (15%, min 16k) with `keep.tokens`; experimental `background_compaction` precomputes a summary while the cache is warm and applies it later; the summary request is built to reuse the normal prompt prefix ("reuse its prompt cache", `session/compaction.ts` comments). No instruction field on the HTTP endpoint; the hook is the extension point.
- Storage is SQLite (tables `session_v2`, `session_message`, `session_part`, `session_inbox`, `event`, `job`, `schedule`), not JSONL: the ctlstat adapter must read it read-only (WAL) or use the API.
- Weak points for us: 4,211 open issues; v2.x is two weeks old; `experimental.*` names "may still change"; the context-hook persistence question is open.

### Codex CLI (openai/codex)
- Apache-2.0, Rust, OpenAI staff. Hook events (docs): `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PreCompact`, `PostCompact`, `UserPromptSubmit`, `SubagentStop`, `Stop`, `PreModelRequest`, `PostModelRequest`, `Interrupt`, `SessionStart`, `SubagentStart`, `SessionEnd`; `additionalContext` for SessionStart/SubagentStart/UserPromptSubmit/PreToolUse/PostToolUse; `PostModelRequest` carries `token_usage`; `PreModelRequest`/`PostModelRequest` are diagnostic only. This makes G-b feasible on the estate's worker harness by config alone, with the same change-only throttle script as E3.
- app-server (`codex-rs/app-server`): JSON-RPC with `thread/start|resume|fork|compact/start|queue/*|goal/*|tokenUsage/updated|status/changed`, `turn/start|steer|interrupt`, `command/exec`, `fs/*`, `hooks/list`, `plugin/*`; transports `stdio://`, `unix://PATH`, `ws://IP:PORT`, `off`. `codex --remote ADDR` runs the TUI against it. That is a real server+client split.
- Compaction (corrects nothing earlier, but sharpens it): `ThreadCompactStartParams { thread_id }` only; PreCompact hook stdout ignored; `compact_prompt` config works on the local-summary path only.
- Fork cost: very high (Rust, daily drift, 27k issues, alpha tags every few days). Not recommended; use config, hooks and the app-server as is.

### Claude Code (comparison)
- Closed source, vendor-run. All of G-a, G-b, G-d proven by our experiments (E1-E5, headless `-p`). G-c via `asyncRewake`/Monitor/new `-p --resume`; G-e partial (no multi-client server; `claude agents --json` covers `--bg` sessions only, E-020); G-g via `nohup`; G-f Anthropic only. Extension surface is hooks, skills, MCP, plugins, Agent SDK; no source access, vendor can change behaviour (auto-compaction fired at ~70k for a 100k setting, E2). Keep as controller host until a PoC beats it.

### reasonix (esengine/DeepSeek-Reasonix)
- What it is: "an open-source coding agent for your terminal, desktop, browser and editor", MIT, Go CLI (`reasonix`, `reasonix run`, `reasonix web`, `reasonix acp`) plus Studio desktop (Node 24/pnpm), "Maintained by Huahui Yu"; default branch `studio` (2.x), 1.x on `main-v2` in maintenance. Local copy: npm package `reasonix` 2.58.0 shipping a `cli-linux-x64` binary (README note from the repo page; build details not inspected).
- Extensions: Extension Protocol v1 sidecars, JSON-RPC 2.0 over NDJSON on stdio (8 MiB frames), 17 frozen hook points: `agent.before_start, compaction.complete, compaction.prepare, context.prepare, frontend.event, input.receive, permission.decision, provider.request, provider.response, session.end, session.load, session.rotate, session.save, session.start, system_prompt.build, tool.after, tool.before`; `extension/intercept` (blocking) vs `extension/event` (observe); `compaction` is a single-owner replacement slot; capabilities `session.submit` (`host/prompt/submit`) and `session.read` (`host/session/read`, usage). The per-hook contracts live in `internal/ext/extension/protocol/schema.generated.json`, which I did not read: UNVERIFIED.
- Headless: `reasonix run`, `--resume`, `--continue`, `--copy`, `--output-format stream-json`, `--events-jsonl`, `session list|show|status|recovery --json`, `task monitor events --jsonl --follow`. Sessions are JSONL under `~/.reasonix/sessions/`. No documented external compaction call (the `POST /compact` strings seen in v1.17.12 were version-pinned, see `nyxloom/docs/research-external-compaction.md`).
- Verdict: good machine-readable inspection verbs; extension API promising but undocumented where we need it; maintainer concentration. Worker harness, not a platform.

### Other harnesses (picked on headless/server and extension strength)
- **OpenHands Software Agent SDK** (`OpenHands/software-agent-sdk`, MIT, Python): pick because it is the only candidate in the estate's language with a documented event-sourced conversation (`events/*.json` append-only), a pluggable condenser (`CondenserBase.condense()` returning a `Condensation` event with our own summary), Claude-Code-compatible hooks (`HookConfig`, `additionalContext`), and an agent server with REST+WebSocket and a web GUI. Why not first: it is a framework you assemble an agent from, not a coding CLI with our routes already working; default condenser trigger is event count; per-event usage unconfirmed. Source: docs.openhands.dev/sdk/{arch/condenser,arch/conversation,guides/hooks,guides/convo-persistence}.md.
- **Goose** (`aaif-goose/goose`, Apache-2.0, Rust, Linux Foundation AAIF): `goose serve` exposes `/status` and `/acp` with an `X-Secret-Key`; hooks follow the "Open Plugins hooks specification" but docs list only PreToolUse and Stop as controlling events and no way to inject context; compaction threshold configurable (`GOOSE_AUTO_COMPACT_THRESHOLD`) and the summary prompt is the file `compaction.md` (static); sessions in SQLite. Weaker than pi/opencode on G-b and G-d. Included for completeness because it is the other well-funded Rust agent with a server.
- Not examined further (stated reasons): aider (no server, no hook points, git-centric pair programmer), Cline/Roo (VS Code-centred; headless CLI and extension API not verified here), Crush (licence believed FSL, not OSI-open; UNVERIFIED), OpenClaw/Copilot CLI (installed locally but out of scope, not coding-harness candidates for the stated goals).

Answer to "extend something instead of building a TUI/UI": the only candidates that already have a server/API plus ready clients are opencode v2 (TUI, web app, desktop app on one long-lived server) and Codex (app-server plus `codex --remote` TUI; the desktop app speaks the same protocol), then OpenHands (agent-server plus web GUI) and Goose (desktop attached to `goose serve`). pi has no attach path today. ctlstat itself stays a status/guided-compaction service with JSON output (section 8.9 of the requirements); the operator front end should be opencode's web/TUI client or `codex --remote`, fed by ctlstat output as a message or a plugin tool, not a new UI.

Honest limit on "no crappy workarounds": none of the candidates removes the need for a per-harness adapter in ctlstat (log parser, injector, wake, compaction driver). What pi and opencode remove is the **workaround count inside each adapter**: pi needs zero (everything in extension API), opencode needs one (handover through a file into the `compaction` hook), Codex needs two (config `compact_prompt` for the local path, and the opaque remote path avoided for workers), reasonix needs unknown.

## What a fork or extension would involve (top 1-2)

### 1. pi: an extension, not a fork
- Shape: one TypeScript extension `ctlstat-pi` in `~/.pi/agent/extensions/` (or a package), about 150 lines: `tool_result` handler (call `ctlstat status --since-last --json` for this session id; return `{content:[...original, injected diff]}` only when the diff is non-empty, state in a closure keyed by `ctx.sessionManager` id), `turn_end` handler (use `ctx.getContextUsage()` to report pressure to ctlstat), `session_before_compact` handler (read `<session>.handover.md`, call the external summarizer or return `{compaction:{summary: L0+L1, firstKeptEntryId: preparation.firstKeptEntryId, tokensBefore: preparation.tokensBefore, usage}}`), and a watched trigger file (pattern of `file-trigger.ts`) for G-c.
- Supervisor (our code, language free): `pi --mode rpc --session <jsonl>`; commands `get_session_stats`, `compact`, `prompt`, `follow_up`; read events from the JSONL event stream (`docs/json.md`).
- Maintenance: the extension API changes between minors (the changelog shows breaking changes in 1.5.0 for TypeBox imports); pin the pi version, run the PoC as a regression test before each upgrade. Stable surface to depend on: `session_before_compact`, `tool_result`, RPC `compact`/`get_session_stats` (all documented in shipped docs).
- If a fork were ever needed: nothing in G-a..G-e requires one; the only missing piece is a multi-client server, which upstream is building (`apps/p3`, `packages/durable`), so forking would diverge from their direction. Do not fork.

### 2. opencode v2: a plugin plus a thin driver
- Plugin `ctlstat-opencode` (Promise API, `@opencode/plugin`): `ctx.tool.hook("execute.after", ...)` appends the change-only diff to `result` (or `ctx.session.synthetic` when persistence is required); `ctx.session.hook("compaction", (e)=>{ e.result = { summary: <L0+L1 from handover file and external summarizer>, tokens } })`; `ctx.session.hook("experimental.idle", ...)` optional for external-event loops.
- Driver: `POST /api/session/:id/compact` then `POST /api/session/:id/prompt "continue"`, `GET /api/event` for completion, `GET /api/session/:id/context` for the post-compaction view; sessions stay in the server so a controller restart does not lose them (G-g).
- If a patch is wanted (cleaner than the file hand-off): add an optional `instructions` field to the compact payload (`packages/protocol/src/groups/session.ts:441`), handler (`packages/server/src/handlers/session.ts:418`) and the compaction request type (`packages/core/src/session/compaction.ts`), then surface it in `SessionCompaction` for hooks. Small (about 30 lines), but every upstream release touching these files means a rebase; prefer the file hand-off plus plugin and offer the field upstream.
- Risks: v2 is new, Effect 4 plugin types, `experimental.*` hooks may rename, context-hook persistence unknown, SQLite schema is internal (use the API where possible), 4k open issues means slow fixes.

### 3. Codex (worker only)
- Config: hooks for G-b; `compact_prompt` per resumed app-server launch for G-d on the local-summary path; avoid remote compaction for workers (set provider capability/`remote_compaction` per route, effect UNVERIFIED). A one-field patch (`ThreadCompactStartParams.instructions` at `codex-rs/app-server-protocol/src/protocol/v2/thread.rs:1207` plus the compaction task in `codex-rs/core`) would also be rebased against a project with daily commits: not worth it.

## PoC proposal (smallest proofs, throwaway sessions, no estate files)

Both PoCs run in a scratch directory with a throwaway workspace, a cheap route (deepseek-v4.1-flash-eco via the existing `opendesign` gateway, or a Haiku API key for pi), under the host load rule (one process, `nice`). No clone, build or install needed for pi (installed 1.5.0 at `/opt/mdt/npm/bin/pi`) or opencode (2.2.6).

**PoC-A pi (target 3-4 h).**
1. Start `pi --mode rpc --session $X/s1.jsonl --model <cheap>` from a script; send 6 prompts that read small files and run bash commands.
2. Extension (a) `tool_result` injecting `[CTLSTAT]` change-only lines from a state file we edit mid-run; (b) `session_before_compact` reading `$X/handover.md`.
3. Checks: (i) the injected text is in the session JSONL and the model quotes the latest marker; silent when unchanged (compare E3); (ii) `get_session_stats.contextUsage` and the last assistant `usage` agree with the sum rule; (iii) send `{"type":"compact","customInstructions":"..."}` and confirm the `compaction` entry carries our summary text and `fromHook:true`, and the next `prompt` answers from it; (iv) record `tokensBefore`, `estimatedTokensAfter`, summarizer `usage`, wall time.
4. Pass: all four hold with no pi source changes. Fail modes to watch: `tool_result` patches not persisted, `session_before_compact` skipped in RPC mode.

**PoC-B opencode (target 3-4 h).**
1. Run an isolated server (own `XDG_DATA_HOME`, so the production DB is untouched) with a plugin; create a session via `POST /api/session`, prompt via `/prompt`.
2. Plugin (a) `execute.after` appending a marker, (b) `compaction` hook returning `{summary: <handover file text>}`.
3. Checks: does the marker persist in `GET /api/session/:id/context` and survive a second turn (resolves the open persistence question); `POST /compact` produces a compaction whose summary equals our text and no summariser model call is billed; `POST /prompt "continue"` works; kill and restart the server and confirm the session and its inbox resume (G-g).
4. Pass: marker persistence known either way, compaction pluggable end to end, restart recovery works.

Both feed directly into the already planned 5-arm replay evaluation (R12.9): pi gives arm E3 (supplied summary), opencode gives the same plus warm-cache background summary.

## Recommendation (one paragraph)

Keep the ctlstat design harness-neutral as decided (R12.8), do not fork any harness, and run the two PoCs: pi first, because it alone satisfies G-a, G-b and G-d with documented extension points and no patch, and opencode second, because it alone gives a server plus attachable TUI/web/desktop clients, which is the cheapest way to defer our own UI. Decide the controller host (R12.10) after those results; Claude Code stays the controller and Codex the worker harness in the meantime. If the PoCs pass, the likely end state is: Claude Code or pi as controller, opencode server as the operator console and unattended agent host, Codex and reasonix as workers, ctlstat adapters for all five.
