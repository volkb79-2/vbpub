# ctlstat: one-call controller status (requirements, 2026-11-09)

Origin: operator 2026-11-09: the controller needs a big picture of agents, hosts, releases and branches in ONE mechanical call instead of 5-8 tool calls per tick; the prototype `codex/ctl-status.sh` (22 s, noisy) already proved the value (its first run exposed a failed release the controller had not yet noticed). The operator wants it to be a real tool, discoverable through a skill. These requirements come from what the controller actually checks every tick; open decisions carry a default.

## 1. Purpose and users
- Primary user: the controller session (Claude), at the start of every tick and before launching, merging or releasing. Second user: the operator (human, terminal, width 120). Third: scripts (`--json`).
- Question it answers: "what needs my action right now, and what is the state of everything else?" Attention items first, then the picture.

## 2. Hard constraints
- READ-ONLY. Never starts, stops, merges, pushes, kills, pulls or writes outside its own state dir. No secrets in output (hosts by name only; no keys, fingerprints, tokens, IPs).
- Cockpit-light: stdlib Python (or POSIX shell + python3), one process tree, no docker, no ssh unless an explicit flag asks for it; default run <= 3 s, every section has its own time budget and fails soft (`unavailable: <reason>`), never aborts the whole report.
- Never touches <protected-host>. Remote probes only through the identity-checked wrapper (host name + provider id guard) and only for hosts in the configured list.
- Output width 120 by default (`$COLUMNS`/TTY width otherwise), default <= ~100 lines even with 30 worktrees; `--full` lifts the caps; `--json` is the stable machine interface; no colour needed (words carry meaning).
- Nothing hard-coded in the tool: paths and names come from one config (TOML or env) with defaults owned by the tool; the program-directory layout (`logs/`, `reports/`, `codex/runs/`, `HANDOFF-*.md`, `.worktrees/`) is configuration, not code.
- Exit code: 0 = nothing needs attention, 1 = attention items exist, 2 = tool error. (Lets a loop prompt `ctlstat || act`.)

## 3. Information wanted (sections, in display order)
A. ATTENTION (always first, empty = "none"): each item = what, why, suggested next action. Sources: finished impl job without review; review verdict MERGE not yet merged; FIX-FIRST without a fix job; failed or finished release (EXIT seen); release running (merge freeze reminder); run stalled (no write for > N min while no `.done`) or dead (no process); host queue loop dead or paused longer than M min; memory anon over the hold line (5.0 GB) or PSI high; origin/main moved since the last call; worktree dirty with no live process; unmerged docs/backlog branch older than K hours; agents-per-model imbalance (see 3K); handoff older than T minutes; operator decision pending (a file or marker list).
B. CONTROLLER HOST: memory anon/file/swap/limit/high/PSI, load, free disk of the program dir; the anon hold line status; top memory by owner (VS Code server, extension host, Pylance, file watcher, claude sessions, codex, opencode, git) from /proc PSS/anon/swap (optional `--mem`).
C. RELEASES: running release (project, version, log, age, last log line), last N releases (EXIT, project, version/tag if tagged, age), retained failed candidates (path + abandon command), merge-freeze indicator.
D. IMPLEMENTATION / REVIEW JOBS (Codex luna, Codex deepseek, opencode, Claude subagents): one row per job: name, route+model, role (impl/review/fix/prep/host), state (running/done EXIT/stalled/dead), age and last-write age, size, worktree, branch, head commit + subject, commits ahead of origin/main, dirty files, report path present?, verdict line if it is a review (MERGE / FIX-FIRST / REJECT parsed from the report), session id (for resume).
E. WORK-ITEM PIPELINE: derive per work item (a branch/worktree family) the stage: impl -> review -> fix -> re-review -> MERGE-ready -> merged, from run names, reports (`*-REPORT.md`, `*-REVIEW*.md`, `*-fix*-REPORT.md`), branch state and `merge-base --is-ancestor` against origin/main; show round number; flag cycles beyond 3 rounds.
F. MERGE QUEUE: branches with MERGE verdict (or reviewed-OK) not yet in origin/main, with predicted conflicts (`git merge-tree --write-tree origin/main <branch>`: files), ordering hints (declared dependencies), and whether a release currently blocks merging.
G. HOSTS (<host>, <host>; controller counted as a host for shards): queue loop alive/paused (flag files)/in-flight lane/age, last N results (PASS/FAIL/INFRA counts, durations), pending lane count; with `--remote`: ONE identity-checked ssh per host returning load, memory, swap, disk, containers by name prefix (lane/cockpit), cockpit uptime, cgroup slice memory, running remote-gate jobs and their phase markers (e.g. `ASSAY_GATE_PHASE=...`, `lane exited rc=`).
H. REMOTE-GATE / RELEASE-GATE DETAIL: newest remote gate job: lane, host, sha, state, phase markers, failing test ids summary when finished.
I. CAMPAIGNS / SHARDS (R2 mutation): per shard: host, state, judged/total, killed/survived/other, resume identity, report path.
J. BRANCHES AND WORKTREES: only those with work (ahead, dirty, recent commit); stale ones counted, not listed (`--full` lists); total count and size; shared checkout drift vs origin/main; untracked leftovers list.
K. ROUTING POLICY CHECK: counts of running jobs by route/model (luna, deepseek, opencode, sonnet, opus) against the operator rule (sonnet/opus sparingly, luna/deepseek preferred; 6-8 agents kept running): print the mix and warn when below 6 running or above the Claude-model share limit.
L. HANDOFF + DECISIONS: last handoff entry age and its last 3 lines; open operator decisions list (from a small `decisions.md` the controller maintains) with age.
M. DELTA: `--since-last` (default on for non-first calls): compare with a snapshot of the previous call in the tool's state dir and print "changed since <age>": new/finished jobs, verdicts, commits, queue results, release state, origin/main; the full picture follows only on `--full`. A tick that finds nothing changed prints one line.

## 4. Companion verbs (small, same tool)
- `ctlstat register <id> --role R --model M --route X --purpose "..." [--worktree W]`: appends one line to the agent registry at launch (the controller currently loses the mapping from Claude subagent task ids to purposes). Section D reads the registry; Claude subagents get liveness from their transcript/output file mtime (`$TASKS/<id>.output`), never by reading its content.
- `ctlstat note "<text>"`: timestamped one-liner appended to the handoff (replaces hand-written heredocs; keeps the entry format uniform).
- `ctlstat decision add|close <text>`: operator decision list for section L.
- `ctlstat explain <job|branch|release>`: everything known about one item (run files, report heads, verdict, commits, log tail) in one response, so drilling into an attention item is also one call.

## 5. Skill (discoverability)
- A skill `ctl-status` in the repo's `.claude/skills/` (frontmatter `name`, `description` with trigger words: "check progress", "status of all tracks", "what is running", "big picture", start of every controller tick) whose body says: call `ctlstat` FIRST at every tick, read ATTENTION top-down, use `explain` for drill-down, `register` right after every agent/job launch, `note` instead of ad-hoc handoff edits, never run the many individual checks the tool already covers. Includes the section legend, flags table (`--remote`, `--mem`, `--full`, `--json`, `--since-last`), exit codes, and the registry/decision file conventions. Also referenced from AGENTS.md (controller section) and from the memory index.
- The wakeup prompt text used by `/loop` ticks references the skill instead of listing checks.

## 6. Design questions to decide in the design step (defaults in brackets)
1. Language/layout [single-file stdlib Python under `scripts/ctlstat/ctlstat.py` + tests + README + skill; not a new service; installed as `ctlstat` shim on PATH for the controller].
2. Reuse vs new: evaluate `scripts/codex/*`, `scripts/controller-launch.sh`, `host-sat-queue.sh status`, nyxloom's pipeline/state tooling, `cmru status`, `run-gate`/`remote-gate` status commands: call them as data sources where they already give the answer; do not duplicate their logic [thin aggregator].
3. Where program state lives: the release-program directory is outside the repo [config points at it; tool ships a documented layout; run names/report names follow conventions parsed with a small table].
4. Verdict extraction from reports [first line matching `Verdict: **MERGE|FIX-FIRST|REJECT**` or `Verdict line` or final `Summary:` line; unknown = "no verdict"].
5. Stalled thresholds [900 s no write while running; queue pause > 30 min; handoff > 45 min] configurable.
6. Snapshot/delta format [JSON in `$XDG_STATE_HOME/ctlstat/last.json`].
7. JSON schema stability [versioned `schema: 1`; additive only].
8. Testing [golden outputs from a synthetic program directory fixture at COLUMNS=120/80/non-TTY, fail-soft tests per section, no host or docker access in tests, hand-mutation of attention rules].
9. Remote probes [one ssh per host with a single composite command, 10 s timeout, reuses the existing identity-check wrapper; never default-on].

## 7. Acceptance
- A fresh controller session can run `ctlstat` with no arguments and in <= 3 s get: attention list, controller memory, releases, jobs table with verdicts, merge queue, host queues, handoff age.
- Replaying the 2026-11-08/09 session (fixture) flags: attempt-c failure the moment its log shows EXIT, a finished impl job without review, a MERGE verdict waiting behind a running release, a stalled run, the dead-session `RUNNING` runs from earlier days as `dead`, and <host> pause flag age.
- Skill present, discoverable by the trigger words, and listed in AGENTS.md; the `/loop` tick prompt shrinks to "run ctlstat, act on ATTENTION".

## 8. Prior art and what it changes (web research 2026-11-09; the design step must address each point)
Sources: Hermes Agent Kanban docs (hermes-agent.nousresearch.com/docs/user-guide/features/kanban), "state is truth, events are rumors" (hexisteme.github.io/notes/pull-vs-event-bus-agent-fleet.html), Zylos cross-instance aggregation note (zylos.ai/research/2026-06-07-cross-instance-state-aggregation-agent-fleets), Claude Code agent view (`claude agents`, `claude logs/attach/stop <id>`, v2.1.139+), community hook-based dashboards (disler/claude-code-hooks-multi-agent-observability, simple10/agents-observe).
1. PULL FROM ON-DISK EVIDENCE, not events: an event exists only if the emitter survives; a crashed job leaves a stale file and a dead pid. Derive status from run files, git state, logs, queue files; no producer instrumentation. (Already the design; make it an explicit rule.)
2. SCORE EFFECTS, NOT SELF-REPORTS: "liveness without progress" is our deepseek/opencode stall (process alive, jsonl growing or exit 0, no commit, no report). Hermes calls exit-0-while-task-running a `protocol_violation`. Add per-job `progress age` (last commit / dirty-file change / report written) next to `liveness age` (last write / process alive); a finished run with no commit and no report = `PROTOCOL-VIOLATION` attention item; sources that only self-report are labelled `self-reported`.
3. DETERMINISTIC PRIORITY, no LLM in the ranking: BLOCKED > FAILED > STALE/DEAD > READY-FOR-ACTION (review MERGE, finished unreviewed) > NEW; hard facts from disk only.
4. FRESHNESS STATES per source/value (Zylos TTL ladder): FRESH, STALE (> T), UNREACHABLE (> 2T), PRESUMED-DOWN (> 3T); computed from the aggregator's own receive time; idle/unreachable/down kept distinct; a failing source never fails the report; if many sources fail at once, suspect the aggregator first; the output says which sources are missing and why.
5. DEPENDENCIES AND READINESS (Hermes: a task with parents is not ready until they finish; `max_in_progress` caps concurrency): section E/F carry explicit edges (merge order, "blocked by running release", "waits for hc-1b-s merge") and the tool computes READY / BLOCKED-BY.
6. CHEAP, FILTERED VIEWS for the model's context (Hermes `kanban_list` filters + limit, `stats` counts, `show`; summary short, evidence as pointers not raw logs): default output is a computed summary + ATTENTION; `ctlstat list --role --state --limit`, `ctlstat stats` (one line of counts by state/route/model), `ctlstat explain <item>`; logs are referenced by path, never inlined.
7. LET THE MODEL SLEEP (the real efficiency lever, not a nicer dashboard): a mechanical, LLM-free watcher: `ctlstat wait [--timeout S] [--interval S]` blocks, polling cheaply (file mtimes + the same derivations), and EXITS when ATTENTION changes (a new item appears, a job finishes, a verdict lands, a release gets an EXIT, a queue dies) or the timeout hits; the controller runs it via the Monitor tool / background command so the harness re-invokes the model only on change instead of fixed-interval ticks (replaces most `ScheduleWakeup` polling; keep one long fallback tick). `--since-last` delta (section M) is the same idea for explicit calls. Print the suggested next-check delay.
8. OPTIONAL DATA SOURCES: `claude agents --json` / `claude logs <id>` for Claude `--bg` sessions (note E-020: Agent-tool subagents are NOT listed there: they stay registry + transcript-mtime based); Hermes-style `diagnostics` idea: a `ctlstat doctor` that checks the tool's own sources (paths exist, queue loops alive, registry readable).
9. NOT NOW: hook-instrumented event streaming and a web UI (disler / agents-observe style) are for humans watching live and need per-producer hooks; revisit only if the operator wants a browser view (the JSON output already allows it). Persistent store (Hermes SQLite board) is a task board with its own state; our truth is files and git: no new store beyond the snapshot/registry/decision files.

## 9. Additions after operator feedback (2026-11-09)
ClaudeLink (claudelink.ai, github.com/RBJGlobal/claudelink: MCP server, one SQLite mesh, agents register + send messages, 30 s heartbeat with `kill -0` pruning, tmux/iTerm "auto-nudge" keystroke wakeups, Command Center web UI with fleet context occupancy / cost per turn / handoff freshness sorted most-urgent-first, Recovery Watcher for rate-limit errors, consent-gated compaction) is a peer-messaging mesh for interactive terminals, macOS/iTerm2/tmux and Node oriented: NOT adopted (our controller is single, workers are headless `codex exec`/subagent processes, truth is files + git). Ideas taken: per-agent context/cost columns, urgency-sorted attention, dead-agent detection by pid, rate-limit/overload detection with a suggested resume, handoff freshness; it has no low-token coordinator summary, which is the gap this tool fills.
1. STALL / PROTOCOL-VIOLATION DETECTORS (derived from the real incidents; each is an attention rule with a test): (a) TOOL-CALL-AS-TEXT: the last `agent_message` of a finished Codex run contains `<exec_command>`, `<cmd>`, `<tool_call>` or `<function=` (seen 2026-11-08: deepseek run `cmru-changes`, harness `codex exec` with CODEX_ROUTE=deepseek, Open Design gateway; the model printed its next tool call as text, Codex treated it as the final answer, exit 0, no commit, no report); (b) INTENT-ONLY-ENDING: final message announces future work ("I'm adding...", "Next I will...") with no completion marker (seen: `cmru-changes-r2`); (c) EXIT-0-NO-EFFECT: exit 0 and no new commit and no report file for an impl/fix job; (d) NO-FINAL-MESSAGE / EMPTY run (no events: e.g. `cmru-changes-r3` "thread already has an active writer"); (e) rate-limit / provider-error exits (Hermes uses 75/78) and `.err` patterns (`justification requires an explicit sandbox_permissions`, 429, overloaded); (f) liveness without progress (alive process, growing jsonl, no new commit/dirty change for N min). The opencode jsonl format differs from Codex (no `agent_message` items): the parser is per-harness with a format table, unknown format = "no verdict", never a false stall. Each flag proposes the next action (resume via `codex-impl.sh ... resume <sid>` if no process holds the session, else finisher or move to luna).
2. PLAN MODEL (the controller currently keeps the dependency graph, parallelism and ordering in its head and in prose handoff entries: it can forget or mis-order things; examples this wave: follow-ups sat only in the handoff until the operator asked, backlog ids collided across branches, a failed release went unnoticed until the status script ran): a small versioned plan file `plan.toml` (outside the repo, next to the handoff) with work items {id, title, kind (impl|fix|review|release|host|docs|decision), deps[], status (todo|ready|running|blocked|done), route/model, est_minutes, owner (run/agent id), blocks (merge freeze/host exclusivity), notes}; `ctlstat plan` computes READY now, BLOCKED-BY (with the blocker), what can run in PARALLEL (respecting exclusivity: one release at a time, one gate lane per host, merge freeze, anon-memory budget, route concurrency caps), the CRITICAL PATH, and an ETA range per item and for the whole plan; estimates are CALIBRATED from history (median/p80 wall time per kind and route computed from run `.jsonl`/`.done` mtimes and gate logs; show confidence and sample size); items are auto-created from the pipeline stages (impl done -> review item; review FIX-FIRST -> fix item; fix done -> re-review item; MERGE -> merge item; merged -> release-candidate hint) so the plan cannot silently omit the mechanical follow-ups; `ctlstat plan add|done|dep|est` verbs edit the file; the status call shows the top READY items and the critical-path head.
3. FINDINGS LEDGER (nothing forgotten): parse every review/triage/analysis report for numbered findings (blocking / non-blocking / "gaps", "not filed") and track each to a disposition: fixed-in-commit, filed-as-backlog-id, deliberately-closed (with reason), or OPEN; attention rule: any finding of a report older than N minutes without a disposition. The controller records dispositions with `ctlstat finding close <report>#<n> --fixed <sha>|--backlog <id>|--wontfix <why>`; the fix reports' per-item tables are parsed to close findings automatically where they cite the finding numbers.
4. Context/cost columns: per Codex run tokens from `turn.completed` usage events, per Claude subagent transcript size as a context-fill proxy, elapsed time; rolled up per model/route for the routing-policy check (section 3K).

## 10. Stage and goals (operator 2026-11-09: REQUIREMENTS AND DESIGN DISCUSSION ONLY, no implementation yet)
Status: the luna job `ctlstat` was STOPPED (exit 143) on 2026-11-09; what exists is a draft `scripts/ctlstat/DESIGN.md` commit (3a718eba2) and an untracked partial `ctlstat.py` in `.worktrees/ctlstat-20261109`: exploratory, NOT to be merged; the design is re-opened from the requirements.
GOALS (ranked, each measurable):
G1 EFFICIENCY: fewer tool calls and fewer tokens per controller tick: one call replaces the 5-8 per-tick checks (target: a tick that finds nothing changed costs one tool call and < 300 output tokens; a busy tick one call and < 2k tokens), and the model SLEEPS between changes (watcher + wake, section 8.7) instead of polling on a fixed interval.
G2 DETERMINISM: everything derivable mechanically is derived mechanically (states, verdict extraction, stall/violation detection, readiness, conflict prediction, id-collision checks, finding dispositions, estimates from history), so the model spends tokens on judgement (what to do about it), and the same inputs always give the same attention list and ranking; no LLM in the status path.
G3 NOTHING FORGOTTEN: plan graph, findings ledger and follow-up creation are mechanical and persistent (survive compaction/crash of the controller session); the controller state that matters lives in files, not in the conversation.
G4 PER-AGENT STATE INCLUDING CONTEXT WINDOW and guided, pressure-based COMPACTION (section 10.1).
G5 ENVIRONMENT STATE: controller host, <host>, <host> (never <protected-host>), containers, queues, slices/cgroup limits, memory/swap/PSI, disk, image digests, pinned versions, pause flags, release freeze, tool versions installed vs released (cmru venv vs released wheel, run-gate default vs 25.4.0 venv, cgprofile version/endpoint record state per host), so "what would break if I started X now" is answerable in the same call.
G6 DISCOVERABILITY: skill + AGENTS.md pointer; the tool teaches the controller how to use it (`ctlstat help ticks`).
10.1 CONTEXT WINDOW STATE AND GUIDED COMPACTION (the issue nyxloom started but never worked out):
Prior work to build on, not re-derive: `nyxloom/docs/design-context-lifecycle.md` (patterns: checkpoint -> designed compact -> resume; snapshot chain), `design-context-lifecycle-experiments.md` (E-001..E-020; E-008: 9/11 real agents never reach 300k, so the old 300k trigger was wrong), `design-controller-checkpoint-reset.md` (settled facts F1-F11 incl. F6 no model-callable compaction tool exists, F7 PreCompact cannot steer a compaction, F9 `asyncRewake` hook: a background process can WAKE an idle Claude on exit code 2, F10 `claude agents --json` = poll-able registry with status busy/idle/waiting), `research-external-compaction.md`, `mitmproxy-compaction-trace-howto.md`, `nyxloom/tools/jsonl-metrics.py` (measurement), the current checkpoint doctrine in <checkout>/CLAUDE.md ("ARM at ~120k or ~60 tool calls, CUT at the next coherent boundary: green gate > commit > report write > edit-cluster end, never on a red gate; continuation brief + retention prompt; successor seeded by brief"), LESSONS L23 (successor brief).
WANTED STATE per agent (all derived from transcripts/jsonl, no model call): context fill now (last turn input tokens incl. cache read+creation, as % of the model's window), fill trend (tokens/turn, tokens/min), tool-call count since start / since last boundary, turns, cost so far, time since last boundary, last semantic boundary type and age (commit, green gate, report written, review verdict, file-edit cluster end), whether the agent is AT a boundary right now (just committed, tool-free idle, gate green), whether it is mid-edit/red-gate (do NOT cut), compaction count so far and the size of its last handoff/brief file, "handoff freshness" (age of its last continuation brief vs its last boundary).
WANTED COMPACTION-PRESSURE MODEL (rising pressure as the window fills): a deterministic pressure score p = f(fill%, tool-calls, trend, boundary-availability) with configurable bands, e.g. SOFT (~35-45%: note only), PREPARE (~55-65%: next boundary should write the continuation brief), CUT-AT-BOUNDARY (~70-80%: act at the next semantic boundary, never mid-edit/red gate), FORCE (~90%+ or auto-compact imminent: stop at the next safe point, write brief, hand to a successor). Rising pressure changes what the controller is TOLD, never what it silently does. Per agent kind the available levers differ: Codex runs (no compaction control: checkpoint = a "write continuation brief + commit + stop" instruction via `resume`, then a fresh successor job seeded with the brief); Claude subagents (SendMessage "checkpoint now"; successor by brief; ids are not session ids: F11); CLI children with `--session-id` (headless `claude -p --resume <sid> "/compact <designed text>"` works: F1); the CONTROLLER itself (interactive: `/compact` is user-submitted, so the tool generates the ready-to-paste designed retention prompt from the plan/ledger/state files and `asyncRewake` can wake the idle controller when pressure crosses a band; the controller's own state is already in files, so a compaction costs little).
GUIDED COMPACTION on SEMANTIC BOUNDARIES = the tool (a) detects boundary events from the jsonl/git/log evidence (commit landed, gate verdict, report file written, review verdict line, release EXIT, queue result), (b) knows each agent's safe/unsafe state, (c) emits the checkpoint request text (what to KEEP: current work item, plan/ledger pointers, file:line seams, gate state; what to DROP: resolved sub-threads, per-agent chatter, release attempt logs) so the retention prompt is mechanical, not hand-written each time, (d) records the compaction events (before/after fill, cost, time) to calibrate the bands from data (nyxloom E-series measured these once; ctlstat keeps the running record).

(read-only rule vs convenience: proposal: tool stays read-only, verbs that act live in a separate `ctlctl` command). ## 12. Interview 2026-11-09 (operator answers to Q1-Q4; requirements only, nothing implemented)
**Overall goal (operator):** reduce the number of tool calls and keep the agent's picture of the world state ALWAYS current.
- **R12.1 Source (Q1):** ctlstat works on the SESSION LOG (like `nyxloom extract`): derive context fill, tool-call counts, boundaries and compaction events from the transcript JSONL; no model call. Not a choice among sources: the transcript is the base.
- **R12.2 Automatic injection:** the harness (hooks) should inject the current ctlstat output into the agent's context automatically, e.g. after tool calls, with an unmistakable divider, so the agent is informed without calling the tool. To investigate: hook contract (PostToolUse/UserPromptSubmit additionalContext), throttling and change-only injection (diff, not repeat), the prompt-cache and context-growth cost of repeated injection, whether the hook sees session id / transcript path / live token usage. (Feasibility question out to the Claude Code docs expert; answer goes below.)
- **R12.3 Self-compaction at semantic boundaries:** an agent that knows its pressure (context size / limit) writes a SELF-COMPACTION PROMPT at a semantic boundary (as an extractable final response or a separate handover file) and then terminates; a controller or ctlstat-monitor picks up that prompt and performs the compaction, REUSING THE WARM SESSION CACHE (resume with the prompt), instead of a cold successor.
- **R12.4 Per-task context policy (Q2):** each model/session is started with a task-dependent INTENDED max context size; the controller knows how each harness/session is started, which context limit applies, and therefore which compaction pressure applies. Bands are a function of the intended limit, not of the model's maximum window. Anti-pattern to prevent: many tool calls at ~500k context with almost no context growth; those should run after a PRE-COMPACTION at ~150k from a detailed summary. Mixed mechanical rules plus intelligent decision (tool proposes with reasons, controller decides).
- **R12.5 Controller self-compaction (Q3):** the controller itself is compacted the same way: it terminates and is compacted by the service controller (the ctlstat monitor/ctlctl). Running sub-agents/sessions must NOT be affected, so they must run as independent processes (detached jobs like codex-impl `nohup ... & disown`); Claude Agent-tool subagents and session-bound background tasks are the unsafe case to check (does terminating/resuming the controller session kill them?).

### 12.1 Claude Code facts for R12.2-R12.5 (docs research 2026-11-09; UNVERIFIED items must be tested before any design relies on them)

### 12.3 Experiment + research results (2026-11-09; Claude Code 2.1.319, headless `-p` only; reports/ctlstat-EXPERIMENT-compaction-hooks.md, reports/ctlstat-RESEARCH-compaction-endpoints.md)

- **PreCompact stdout steers the summary:** a handover text printed by the hook appeared in 8/8 summaries (1 manual, 7 auto); hook input has `trigger`, `custom_instructions` (null for auto), `transcript_path`; PostCompact gets `compact_summary` (includes an <analysis> block). - **Injection works and throttles:** PostToolUse `additionalContext` reaches the model; stored as `hook_additional_context` attachment; cost = payload + ~79 chars wrapper per call; a state-file throttle keyed on session_id injected only on change. Hook stdin carries no token usage. (E3)
- **Context fill from the transcript:** `input_tokens + cache_read_input_tokens + cache_creation_input_tokens` of the last assistant message `message.usage` (dedupe entries by `message.id`); matches `compactMetadata.preTokens` once the last message's output_tokens is added; postTokens excludes ~21k fixed system/tool overhead. (E4)
- **Survival:** `nohup` and `setsid nohup` children survive SIGTERM of claude and a later `-p /compact`; a `run_in_background` Bash task blocks `-p` until it ends and dies with claude. => independent jobs must be nohup/setsid detached (as codex-impl already is). (E5)
- **Surprises:** recently read files are re-attached after /compact (file-held facts survive, chat-held facts are dropped); auto compaction fires well below nominal (~70k for a 100k setting); `claude --bg` needs interactive workspace trust (E6 untested).

Recommendation: HYBRID = mechanical skeleton written before compaction and re-injected after + short LLM prose layer on the warm resumed session + lint of prose against skeleton/git; opaque endpoints only for workers. Evaluation plan: replay the real compaction points across 5 arms (bytes kept, entity recall, probe QA, re-orientation tool calls, cost).
