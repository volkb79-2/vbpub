**Decision: O3' (one platform, working name `hostobs`).** It has three parts:
- `hostobs-probe`: unprivileged. It collects, stores and serves.
- `hostobs-act`: privileged. It handles DAMON, BPF, cgroup writes, `cgroup.kill`, D-Bus attach and peak-fd minting.
- `hostobsd`: the Python cli-extended front.

Evidence (sessions and windows) is a **mode, a socket level and a store class inside the probe**, not a separate daemon. The same binary can be run as a second unit (`--role evidence`) if checkpoint C-ISO measures interference (§6.4). Migration is per contract with no dual serving: observer contracts 2 and 3 move first, then control contract 1. cgprofiled is retired at the end. CP-24 is implemented **once**, in the platform, not first in Python.

## 1. (b) cgroup v2 peak files, per-fd reset, and how each tool uses them

**What they are** (`docs.kernel.org/admin-guide/cgroup-v2.html`, fetched 2026-11-07) [V]:
- `memory.peak` exists on non-root cgroups. It holds "the max memory usage recorded for the cgroup and its descendants since either the creation of the cgroup or the most recent reset for that FD". "A write of any non-empty string to this file resets it to the current memory usage for subsequent reads through the same file descriptor."
- `memory.swap.peak` is the same for swap.
- `pids.peak` is "the maximum value that the number of processes ... has ever reached". It has no reset.
- Each peak is a kernel high-water mark maintained on every charge. **It is exact whatever the sampling rate.** A sampled max of `memory.current` misses spikes between reads.

**Per-fd reset, and its kernel floor.**
- The write handlers arrived in **Linux 6.12** (kernelnewbies 6.12: "memcg: memory.swap and memory.peak write handlers", commit c6f53ed8f213) [V]. cgprofile's own comment says the same (`C:src/cgprofile/observer_windows.py:199-205`) [V].
- Each *open file description* gets its own watermark. An `O_RDWR` open followed by a write of `reset` starts a private peak, and other descriptors are unaffected. So a lane resetting its own fd cannot disturb the observer's.
- Before 6.12 the file reads only the lifetime peak. cgprofile then reports `PEAK_RESET_UNSUPPORTED` and never passes the lifetime value off as the window's (`:764`) [V].
- `memory.peak` first appeared in 5.19, `memory.swap.peak` in 6.5 and `pids.peak` around 6.1 [U: version history not fetched; irrelevant on the estate's ≥6.12 kernels].
- A reset needs **write permission on the file**, and the file is `root:root 0644`. Read-only `pids.peak` is `0444`. Observed on 7.2.11, where `misc.peak` and `rdma.peak` also exist [V, local `ls -l /sys/fs/cgroup`]. In practice this means root: whether systemd delegation chowns `memory.peak` is [U], but delegation covers `cgroup.procs`, `cgroup.subtree_control` and `cgroup.threads` per its docs, so assume it does not.
- Holding fds open on a cgroup's files probably keeps a removed cgroup *dying* (`cgroup.stat nr_dying_descendants`) until they close [U]. Every holder must close on `cgroup.events` populated=0 or rmdir.

**Kernels on the estate.**

**How each tool uses them.**

## 2. (c) cgprofiled vs a sampler: intrinsic requirement vs design choice

| Property | How cgprofiled does it | Why the sampler cannot today | Intrinsic requirement | Design choice (movable) |
|---|---|---|---|---|
| Exact window boundaries | reads start counters (`cpu.stat`, `io.stat`, PSI totals, `memory.current`) inside `window-open` and again at close (`observer_windows.py:420-431`). The deltas are exact to the request. | one global tick; values are tick-quantised | a boundary read synchronous with the request, against **pre-opened** subject fds (a `pread` of µs, no path walk) | putting it in a separate daemon. A probe with a subject scheduler does the same. |
| Per-fd peak reset | holds a writable fd per window | read-only, no subject state | a writable fd whose open description outlives the window | who opens it (the actuator) and who holds it (the probe) |
| Crash-safe evidence | **not implemented.** CP-24 is parked on `park/stash-2026-10-17-...` (`f3657994a`). Windows are lost on restart, answered `window-lost` via an epoch (`:26-27`). | frames drop oldest under writer pressure and the drop is counted (`S:sampler/src/writer.rs:6-7,81-93`); hard events are never dropped | finality semantics: commit records, a terminal manifest, budget reserved at admission, no silent drop | store *class*, not process (§6.2) |
| Host writes | placement through `busctl AttachProcessesToUnit` (`C:src/cgprofile/placement.py:108-118`), leaf mkdir, `cgroup.kill`, DAMON sysfs. All run as root, with RW on `/sys/fs/cgroup` and `/sys/kernel/mm/damon` (`C:src/cgprofile/data/cgpd.service.in:36`). | read-only by design | **least privilege**: these writes must not sit in the process that parses tenant data | the actuator split, which cgprofiled lacks too |
| Not 1 Hz | per-session interval of 0.25-30 s, windows at 100-5000 ms, each on its own schedule (`observer_windows.py:46-50`) | `tick_ms` is configurable (`S:sampler/src/cfg.rs:18,113`) but global | sub-second rates only for *subjects*. Whole-host sub-second is waste. | a per-subject earliest-deadline scheduler beside the host scan |

**Verdict.** None of the five needs a separate *evidence daemon*.
- Two need a **separate privileged process**: host writes, and the per-fd reset write. O3' has one, the actuator.
- Three are **scheduler and store features**.

## 3. (d) Liveness must fail safe: the contract, and the bug it exposes

**Concession.** cgprofiled has exactly the hazard V1 attributed to "a sampler" [V by reading]:
- `LivenessTracker.observe` adds the whole wall gap `dt` to the idle clock (`C:src/cgprofile/liveness.py:483,500`).
- The CPU window drops every entry older than 30 s (`:522`). After a monitor gap, the CPU growth made *during* the gap is invisible, and `cpu_seconds_recent` becomes 0.
- So a CPU-only lane, with no progress stream and no IO growth, reads `stalled` after a monitor gap that covers the rest of its idle bound. With `--on-stall kill`, `kill_requested` (`:639`, `KILL_STATES` `:108`) leads to `cgroup.kill`.
- What causes a gap: a blocked read, `CPUQuota=50%` throttling, the serial accept loop (CP-33), a SIGSTOP, or a host stall below the memory-PSI pause threshold.
- The memory-PSI pause (`:490-498`) covers only one cause.
- **File it as CP-60 in the cgprofile backlog** (cross-repo rule). The fix is WP CGP-FS.

**Fail-safe contract (binds every implementation: Python now, the platform later).**
- **FS-1 Readings carry provenance.** Each reading carries `seq`, `mono_ns`, `due_ns` and `fresh` (taken within 2× its interval). A gap longer than `max(3×interval, 5 s)` is `monitor-gap`. The gap span goes to `paused_for_seconds` (`pause_reason: "monitor-gap"`) and never to the idle or cadence clock.
- **FS-2 Activity is measured over the true span.** Cumulative counters (`cpu.stat usage_usec`, `io.stat` bytes, stream identity) are exact across a gap. Activity is the delta over the elapsed span, scaled to the 30 s rule, never a count of samples.
- **FS-3 The monitor's health gates actuation.** If, in the confirm span, the monitor's own cgroup was throttled (`nr_throttled` delta > 0) or it had readings that were not fresh, verdicts are still reported but `kill_requested` is false (`degraded-monitor`).
- **FS-4 Kill needs fresh, confirmed evidence.** Required:
  - an authenticated `on_stall=kill` grant;
  - a kill state over ≥ 3 consecutive fresh readings spanning ≥ 60 s;
  - **the actuator's own confirm read** immediately before `cgroup.kill`: two reads of the target's `cpu.stat`/`io.stat` ≥ 30 s apart, plus the stream identity, with no growth.

  FS-4 also applies asymmetric trust: probe data alone can never kill.
- **FS-5 Unknown is not stalled.** An absent or stalled monitor yields liveness `unknown`, and nothing is killed. The backstops are the consumer's own wall timeout and `over_ceiling`, which is judged on the actuator's clock from the authenticated start.
- **FS-6 Restart and tests.** After a restart, a session is finalised as `daemon-crash-recovery` (CP-24 vocabulary) and is never killed on resumed clocks. Property tests inject SIGSTOP, throttling and blocked reads into the monitor and assert that no kill follows.

**What remains real from V1's argument.**
1. **Failure-domain sharing.** Console load (5k-PID scans, large `current` replies, 8 clients) shares a process, and therefore a memory and CPU envelope, with evidence ticks. This is measurable. §6.4 handles it with separate schedulers and admission pools, plus the split option.
2. **A privileged act triggered by unprivileged data.** FS-4's confirm read solves it.

Neither argues for a separate evidence *daemon*.

**Residual tamper vector.** A lane controls its progress-stream path, which is read through `/proc/<pid>/root` (`RG55:625`). FIFOs are handled (`liveness.py:281-288`). A regular file on a lane-controlled FUSE mount could still block the read [U: whether lanes can mount FUSE]. The platform reads streams on a helper thread with a timeout, never on the evaluation thread.

## 4. (h) When the stdlib-only rule applies

- **The rule (P-7, `M:docs/PLAN-2026-11-HOST-SERVICE-SOCKETS.md:115-125`).** Install verbs run from the wheel itself through zipimport, *before any venv exists*. "The install and doctor modules may import only the stdlib and cli-extended; a test enforces this." The operator already narrowed it: "P-7 only binds the bootstrap stage" (`HANDOFF-STATE-20261107.md:151`).
- **It binds** only the modules imported by `<name>d install|uninstall|doctor|unit print|config check` while running from the `.whl` on `sys.path`, plus cli-extended itself (also zipimported, CX-D3).
- **It does not bind** anything after `install` has built `/opt/<svc>/<ver>/venv` (`--no-index` from shipped wheels). That covers daemons, clients and extras: cgprofile `report` with pandas/plotly, topos Textual, `orjson`. Compiled artifacts and static binaries are fine there.
- **Hard limit.** "ZIP import of dynamic modules (`.pyd`, `.so`) is disallowed"; "importers are only invoked for `.py` and `.pyc` files" (`docs.python.org/3/library/zipimport.html`) [V]. A C-extension or PyO3 wheel can never sit in the bootstrap path. It may sit in the venv.
- **Rust daemon plus Python installer.** The binary is a **payload, never an import**.
  - Decision: ship it as a separate release asset, `hostobs-<ver>-x86_64-linux-musl.tar.zst` plus sha256.
  - The pure `py3-none-any` front wheel `hostobs` carries the expected sha256 in `hostobs/_pins.json`, written by cmru in the same release transaction.
  - `hostobsd install --binary-source <dir|url>` (stdlib: `urllib`, `hashlib`, `tarfile`) verifies the asset, copies it root-owned 0755 to `/opt/hostobs/<ver>/libexec/` and verifies again after the copy.
  - This keeps the wheel zipimportable and makes the platform-tag question from V1 6.2 moot. Wheel-embedding is rejected because the `musllinux`/`linux` tag acceptance on glibc trixie is [U] and a mislabelled `any` wheel is a trap.

## 5. (e) The privilege split: a shared platform component

### 5.1 Processes and units

| Unit | User / privilege | Does | Never does |
|---|---|---|---|
| `hostobs-probe.service` | user `hostobs`, not root. `CapabilityBoundingSet`/`AmbientCapabilities=CAP_DAC_READ_SEARCH` (+`CAP_SYS_PTRACE` only if PROBE-CAPS finds no alternative). `NoNewPrivileges`, `ProtectSystem=strict`, **`ProtectControlGroups=yes`** (cgroupfs read-only to it), `ProtectKernelTunables`, `PrivateNetwork`, `RestrictAddressFamilies=AF_UNIX` (+`AF_NETLINK` if taskstats), `SystemCallFilter=@system-service ~@debug ~@mount ~@privileged`, `MemoryDenyWriteExecute`. | `hostobs-act.service` | `User=root`. `CapabilityBoundingSet=` empty, plus `CAP_BPF CAP_PERFMON CAP_NET_ADMIN` only when a BPF feature is configured. Root uid suffices for root-owned `0644/0600` cgroupfs and sysfs files without `CAP_DAC_OVERRIDE` [U: verify DAMON sysfs in the VM lane]. `ReadWritePaths=/sys/fs/cgroup /sys/kernel/mm/damon /var/lib/hostobs/act /run/hostobs/act`, no `/etc`. `PrivateNetwork`, AF_UNIX only. | narrow verbs (§5.2), its own journals (kill intent/receipt, placement, DAMON pool provenance = CP-26) and confirm reads | parsing cmdlines, `memory.stat` of the host, docker configs; any verb not in §5.2; `io.cost.*` or sysctl writes (iogovmon's, §8) |
| `hostobsd` (Python, cli-extended) | the invoking user, root for install | `install|uninstall|doctor|unit print|config check` (-t delegates to `hostobs-probe -t --json` and `hostobs-act -t --json`); `serve --role probe|act` does `os.execv` of the binary | stay resident |

**The probe's residual (an honest statement).**
- A probe holding `CAP_DAC_READ_SEARCH` is a *read-anything* principal, bounded by Landlock and `ProtectHome`.
- With `CAP_SYS_PTRACE` it could also read `/proc/<pid>/mem` and `environ`. `io`, `environ` and `mem` are `0400`/`0600` and are checked against ptrace access [V modes].
- PROBE-CAPS tries, in order:
  - (a) `taskstats` netlink for per-PID IO without `CAP_SYS_PTRACE` [U whether `GENL_ADMIN_PERM`];
  - (b) per-PID IO from BPF through the actuator;
  - (c) `CAP_SYS_PTRACE` + `~@debug`, with the residual documented.
- Even (c) is a strict improvement on today: cgpd and Python toposd are root with cgroupfs RW.

### 5.2 Actuator verbs (the whole list; anything else is refused)

| Socket (group) | Verb | Guard |
|---|---|---|
| `control` (`hostobs-control`; run-gate, cgprofilectl) | contract 1 `start/stop/status/watch/host/version/gc/export` | Admission, policy grant, placement, kill and finalisation proof run in the actuator. Read verbs are relayed from the probe as size-bounded opaque JSON. CP-24 state machine (§6.3). |
| `operator-act` (`hostobs-operator`; topos gated actions) | `damon.start/stop` (vaddr pidfd, paddr cgroup), `bpf.enable/disable` (compiled-in program ids only) | duration and concurrency caps, a lease, operator confirmation in the client, audit journal |
| `internal` (probe uid only, `SO_PEERCRED` uid check) | `peak-open(window|bucket, pidfd or cgroup id)` returns an fd over `SCM_RIGHTS`; `kill-request(session, verdict, seq)`; `bpf.fds(id)` returns map and ringbuf fds | The actuator re-derives every target itself. Verbs called by the probe are checked against grants written only by authenticated `control` and `operator-act` clients. A compromised probe can therefore cause at most:
- false *data*;
- a kill request that FS-4's confirm read refuses on a live lane;
- peak fds for cgroups it could already read.

### 5.3 BPF and DAMON placement

- **BPF.**
  - The loader, attach and detach live in the actuator: fixed CO-RE programs, BTF present on the estate (`M:topos/docs/PLAN-2026-11-CONSOLE.md:66-71`).
  - The probe consumes the data from `BPF_F_MMAPABLE` array maps and ringbufs passed as fds, through `mmap` with no `bpf()` call [U: spike BPF-FD on 7.2 with `unprivileged_bpf_disabled=2`]. Fallback: the actuator drains and pushes aggregates to the probe's ingest.
  - First programs: Track C per-cgroup block latency and the `cgroup_skb` network counters (`M:topos/docs/BPF-NETWORK-ACCOUNTING.md`). Later: run-queue latency and cgroup mkdir/rmdir/oom tracepoints, which give exact event times instead of polling.
- **DAMON.**
  - Both control and result reads need root. The kdamond files are root-only [V], and reading regions takes a `state` write (`update_schemes_tried_regions`).
  - So DAMON lives entirely in the actuator, which pushes region snapshots into the probe store as a `damon` series of the subscription.
  - Analysis stays in clients: cgprofile's vendored `_damon` under an optional extra (CP-51), and topos views.
- **Single-writer DAMON lease.**
  - The actuator is the only platform writer of DAMON sysfs, so arbitration among platform clients is solved by construction.
  - The host lease `/run/lock/damon-owner.lock` (flock) + `/run/damon-owner.json` from `R:hostcfg-AUGEAS-AND-BOUNDARIES-DESIGN.md:495-502` stays: it guards against `damo`, Python cgprofiled and topos during migration.
  - The actuator holds it from its first DAMON acquire and records CP-26 pool provenance (boot_id, slot, owner, `off-confirmed`).
  - The controller currently shows 16 kdamond slots allocated (`/sys/kernel/mm/damon/admin/kdamonds/0..15` [V]): the reserved pool of cgprofile.

### 5.4 Shared by topos, cgprofile and iogovmon
- topos and cgprofile are clients (§6.5).
- iogovmon stays a separate host-tuning actuator with its own write guard and journal (`R:iogovmon-DESIGN.md:52-55`).
  - Per its asymmetric-trust rule H2, platform probe data may only make iogovmond *less* active. Its enabling decisions keep in-process root reads.
  - Its reports and episode analysis read platform history (IG-CTX).
  - The platform actuator never writes `io.cost.*`, sysctls or `io.weight`: ownership matrix, `R:iogovmon-DESIGN.md:57-66`.

## 6. Evidence vs telemetry after the discounts; the O3' shape

### 6.1 What is truly different, and what it needs

| Property | Telemetry (console, focus) | Evidence (sessions, windows) | Needs a process? | Mechanism in O3' |
|---|---|---|---|---|
| Can the workload influence the evidence? | tenant data parsed | the subject *is* the workload. It writes its stream and marks, can spawn PIDs to slow scans, and can move PIDs out of its leaf. | no | parsing in the unprivileged probe for both; foreign-PID detection gives `SHARED_CGROUP`; FS-1..FS-5 |
| Can it read the evidence? | console levels are operator-only | only its own windows | no | `observer` level is peer-bound (`SO_PEERCRED`, cgroup derived from the host, `C:src/cgprofile/resource_observer.py:1-6`) |
| Who may start, stop, kill? | nobody kills | authenticated control clients; kill only through a grant | **yes, for privilege**: the actuator, which exists anyway | §5.2 |
| Retention and finality | rollups, drop-oldest counted, a 1 GiB cap | pinned per session (200 / 14 d), commit records, terminal manifest, budget reserved at admission (refuse at `start`, never drop later) | no | store class `session` with its own dir, writer thread and budget (§6.2) |
| Deterministic replay | not needed | Summary reproducible from raw rows by the RG55 §7 rules (`RG55:399-414`) | no | raw rows in the session store + pure crate `hostobs-eval` + `hostobs-replay` |
| Contract stability for the assay judge | free to evolve | contracts 1/2/3 with goldens; "both implementations MUST agree" | no | per-socket schema versions; RG55 goldens run against `hostobs-eval` |
| Timing | tick-quantised is fine | exact boundaries, per-fd peaks, 100 ms-30 s | no | subject scheduler + held fds (§2) |
| Failure isolation | a console overload is tolerable | must not starve | **maybe** | separate schedulers, admission pools and memory budgets; split option C-ISO (§6.4) |
| Rigor | cargo test + conformance | estate rigor (coverage + R2) | no | per crate: `-eval`, `-store`, `-act`, `-kernel` judged; the TUI is not |

Only failure isolation could need a second evidence *process*, and it is measurable. Evidence is therefore a mode, a level and a store class, with the split pre-built.

### 6.2 One engine, four subscription kinds

| Kind | Selector | Rate | Store class | Socket level |
|---|---|---|---|---|
| host scan | all cgroups, PIDs, host, devices | `tick_ms` (1 s) | `tier` (hot/warm/cold, `S:sampler/sampler.example.toml:36-66`) | `observe` (no cmdlines), `operator` (full) |
| focus | prefix, `docker:NAME`, unit, PID tree | 1-5 s | `tier`, own retention (CP-28: 5 s × 7 d) | `observe`/`operator` |
| session | one subject from an authenticated `start` | 0.25-30 s | `session` (rows, `tick-commits`, Summary, manifest) | `control`, via the actuator |
| window | a peer's process tree or leaf | 100-5000 ms | result only, epoch-bound (`window-lost` after a restart, as today) | `observer` |

Threads:
- the host-scan thread;
- the **subject scheduler**: earliest deadline first over pre-opened fds, `pread` only;
- the cmdline helper pool (`S:sampler/README.md:83-92`);
- **two writer threads**, `tier` and `session`, so a tier backlog never delays an evidence commit;
- serving threads with per-level admission pools.

The sampler's `stalled` beat (`S:sampler/src/serve.rs:171-176`, 3 ticks) becomes per scheduler and feeds FS-1/FS-3.

### 6.3 Sessions across the two processes (CP-24, once)

- **The actuator owns lifecycle and cleanup proof**: placement, DAMON stop proof, kill intent and receipt.
- **The probe owns data commit**: rows, `tick-commits.jsonl` and the Summary.
- `stop` runs in this order: the actuator asks the probe to seal (fsync the series, then the Summary); the actuator proves cleanup; the actuator commits the terminal manifest and frees capacity.
- The D-33 state, response, recovery and upgrade rules in CP-24 apply unchanged, with "sampler" read as "probe". Start from the park ref (`f3657994a`), whose fixtures need re-authoring at contract 2 (its "Landing status").

## 8. cmru, run-gate and assay requirements for Rust

**How topos analyses and DAMONs a process later.**
1. In the TUI, the operator picks a PID. topos `pidfd_open`s it [U: no ptrace check] and asks the probe for a **focus subscription** on its process tree (unprivileged; per-process series, PRB-TREE).
2. On a confirmed action, topos sends `damon.start{vaddr, pidfd, duration ≤ cap}` on `operator-act`.
3. The actuator checks the lease, verifies the pidfd's start time, journals intent, starts the kdamond and pushes snapshots to the probe.
4. The TUI and `cgprofile analyze` read the same series.
5. The actuator stops on the duration limit, an explicit stop, process exit (pidfd poll) or lease loss, and journals `off-confirmed`.
