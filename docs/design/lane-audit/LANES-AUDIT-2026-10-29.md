### Where CoW is likely to help

1. **Per-run VM disks — strongest candidate.** MDT documents a read-only golden image and per-run `cp --reflink=always` copies (`mdt-cockpit/docs/BTRFS-COW.md:351-354`). The repo already has VM lanes in MDT and modern-debian-tools (`mdt-cockpit/run-gate.toml:75-100`, `modern-debian-tools-python-debug/run-gate.toml:56-62`). **[G]** This is likely the easiest way to get meaningful I/O and storage savings, subject to a live benchmark for random guest writes and compression.
2. **CMRU mutation fixtures.** Its two `copytree` calls make a direct copy-cost candidate (`cmru/tools/mutation_campaign.py:717-723,761-767`). **[G]** A reflink-backed copy adapter could preserve ordinary-copy fallback when no CoW root is configured; verify symlinks, modes, sparse files, and independent mutation.
3. **Assay R2 warm base/snapshots.** MDT proposes a self-contained clone as a warm base and Btrfs subvolume snapshots per run (`mdt-cockpit/docs/BTRFS-COW.md:286-334`). Current Assay instead materializes P22 snapshots in temporary scratch, so this requires an Assay snapshot-backend design, not merely swapping a temp directory. **[G]** Potential benefit is high for cold I/O-bound materialization but must be benchmarked against P22 on this estate.
4. **Warm test environments and caches.** MDT's proposal includes venvs and caches, but copied virtualenv scripts can retain absolute shebangs to the base path; the docs recommend `python -m`, recreating the venv, or verifying relocatability (`mdt-cockpit/docs/BTRFS-COW.md:336-342`). **[G]** A CoW directory will not automatically warm Docker's BuildKit/image-layer cache; those are separate storage systems.
5. **Rollback of candidate trees/state.** Deleting a per-run snapshot is a useful rollback primitive, but mutation state and progress files are resumable evidence. BTRFS-COW-OPTIONS flags that restoring/reflinking can invalidate inode/device identity and break resume (A9), and that a store must not be removed while any stopped or running container still has it mounted (A4; `mdt-cockpit/docs/BTRFS-COW-OPTIONS.md:219-225`). Do not snapshot/restore active `.assay` or `.run-gate` state until identity, locking, and lease behavior are designed.
6. **CIU worktree scratch.** A separate ignored scratch store could help later, but do not relocate or symlink CIU-managed checkouts in the first phase. The Btrfs options explicitly defer CIU-managed symlink stores and reject whole-worktree CoW (`mdt-cockpit/docs/BTRFS-COW-OPTIONS.md:89-95,271-280`).

### Proposed interface and absence behavior

- Add no new required path. In the consumer's own namespace, read `MDT_COW_ROOT`. **Unset** means the optional CoW optimization is unavailable and existing scratch/copy behavior continues. Do not guess a path or create the bind source.
- If set, verify the directory exists, is writable by the gate uid, and `stat -f -c %T "$MDT_COW_ROOT"` reports `btrfs`; also use `findmnt -T` to confirm the expected mounted filesystem. Run those checks inside the process/container that will consume the path; do not validate a translated host path from the container kernel.
- A set-but-missing, wrong-filesystem, or unsafe mount should fail before allocation rather than silently using the root filesystem. This resolves an ambiguity in the current prose: `mdt-cockpit/docs/BTRFS-COW.md:270-273` says unset means “feature off” and also says a missing root must fail. Define “unset” as opt-out; “configured but invalid” as refusal.
- Keep one shared root variable and let each tool derive a project/run-specific subdirectory. The MDT guide suggests an Assay opt-in such as `snapshot_backend="btrfs"`, while the root stays in `MDT_COW_ROOT` (`mdt-cockpit/docs/BTRFS-COW.md:268-282`). Run-Gate's tester-unified env currently forwards only the background slice and release receipt, so a new consumer must explicitly mount and forward the CoW area (`run-gate.root.toml:12-30`).

### Staged plan

**Stage 0 — implement and validate without a CoW mount.** Define the optional storage interface and owner manifest; preserve current temp-directory and copy implementations when the env is absent. Add tester-unified oracles for unset-env fallback, invalid configured root refusal, safe path derivation, concurrent allocation, cleanup after child failure, and evidence identity. Benchmark current Assay P22 materialization, CMRU `copytree`, and VM-disk copies on ordinary storage as baselines. The cockpit can edit and inspect; any tests belong in the registered tester-unified gate per `AGENTS.md:162-181`.

**Stage 1 — mount validation in a new devcontainer.** After host setup creates the per-user Btrfs area, enable the documented same-path bind and `MDT_COW_ROOT` env in the new devcontainer config; leave this active cockpit alone. Run the documented scratch self-check and live acceptance for snapshot/reflink/delete, uid permissions, dual host/container path visibility, and an absent/unmounted filesystem refusal (`mdt-cockpit/docs/BTRFS-COW.md:362-370,419-434`). The docs say the actual cockpit template path and Dev Containers substitution were not yet exercised on the reference scratch VM.

**Stage 2 — low-coupling consumers first.** Prototype per-run VM disk reflinks and CMRU fixture reflinks behind opt-in flags; benchmark wall time, exclusive space, concurrent writes, cleanup latency, and behavior when unset. Keep ordinary-copy fallback as the correctness path when the optimization is absent.

**Stage 3 — Assay warm base.** Only after resolving the editable-install wrong-code risk (A5), resume identity (A9), and VM compression question (A23), prototype a self-contained warm clone plus exact-commit snapshots. Never seed from a Git linked worktree or copy `.git` wholesale; the MDT guide explains the path/alternates and cache hazards (`mdt-cockpit/docs/BTRFS-COW.md:306-327`). Defer CIU-managed stores and automatic eviction per the options plan (`mdt-cockpit/docs/BTRFS-COW-OPTIONS.md:269-280`).

### Open design questions

1. Does the shared helper belong in neutral library code, Assay, Run-Gate, CIU, or MDT? Who owns the root's schema and owner manifest?
2. How are stores keyed across multiple clones/worktrees, and how is deletion proven safe? BTRFS-COW-OPTIONS recommends family/workspace identity plus allocation nonce and owner manifest, not a repo/name key (`mdt-cockpit/docs/BTRFS-COW-OPTIONS.md:145-153`).
3. Which data is volatile, a regenerable cache, or retained evidence? Who accounts for asynchronous subvolume deletion, quotas, and disk pressure? The design explicitly refuses auto-eviction in v1 (`mdt-cockpit/docs/BTRFS-COW-OPTIONS.md:231,269-280`).
4. How will mutation resume identities survive snapshot/reflink/restore? A9 already identifies inode/device pinning as a risk (`mdt-cockpit/docs/BTRFS-COW-OPTIONS.md:224`).
5. What exact mount and uid mapping will tester-unified and nested VM/gate containers receive? The area is per-user, but root or `SYS_ADMIN` is not a security boundary (`mdt-cockpit/docs/BTRFS-COW-OPTIONS.md:228-230,243`).
6. Should VM disks use compression? The options review flags random-write amplification and requires a benchmark before selecting the property (`mdt-cockpit/docs/BTRFS-COW-OPTIONS.md:100-104,238-239,282-284`).
7. Which immutable inputs are worth warming first? The COW guide's 273 MB clone-vs-checkout comparison and small parallel snapshot test are dated measurements, not a vbpub lane benchmark (`mdt-cockpit/docs/BTRFS-COW.md:288-334`).
