## CIU-QOL-2: Implement `ciu.exit_on` as a closed-vocabulary exit policy

**Priority:** High (dead-key fix + QoL)
**Effort:** Low
**Status:** ✅ IMPLEMENTED (commit pending)

Replaces the previous boolean `fail_fast` with a single closed-vocabulary key:

```toml
[ciu]
exit_on = "WARN"    # "WARN" | "ERROR" | "NEVER" (default: "ERROR")
```

- `"WARN"`: exit on any warning OR error (strictest)
- `"ERROR"`: exit on errors only; warnings logged (**default**)
- `"NEVER"`: log all findings without ever aborting

Resolution: config → `$CIU_EXIT_ON` env var → default. Config always wins.
Invalid values are configuration errors naming the key and vocabulary.

**Files:** `warn_policy.py`, `deploy.py`, `CONFIG.md`, `SPEC.md S10.6`

## CIU-QOL-6: Add `ciu status` verb

**Priority:** Medium (operator QoL)
**Effort:** Medium
**Status:** ✅ FIXED (ciu-P16)

No single command shows "which stacks are running, healthy, what images"
across a profile selection. `diagnose` shows failures; `provenance` shows
commit alignment; `health` gates. None give a dashboard summary.

**Proposed surface:**
```bash
ciu status [--profile NAME] [--json]
```

Read-only. Lists selected stacks → compose projects → running containers →
health status → image reference. JSON output uses a versioned envelope
consistent with worktree/provenance documents.

**Evidence:** `deploy.action_status` (new) resolves the exact `ciu up
--profile` selection chain (`load_global_config` → `resolve_profiles` →
`build_selection`), reuses the extracted `deploy._stack_compose_project`
per-entry helper (shared with `_stack_compose_projects` so the two branches
can never drift), and consumes `diagnose._inspect` + `health_pkg.classify`
read-only — no second docker ps/inspect round trip, no compose
up/down/build/exec anywhere in the path. `cli._status` wires `ciu status
[--profile NAME] [--json]` into the verb dispatch/`_USAGE`/`_VERB_HELP`. A
stack directory missing on disk gets a named row (`compose_project: null`,
empty `containers`) rather than vanishing from the report; a resolved
project with zero containers is reported as a legitimate "not started"
result. A Docker daemon that cannot be reached raises out of
`diagnose._inspect` uncaught by `action_status`, is turned into a clean
`[ERROR] ciu status: <reason>` + exit 2 by `cli._status`, and is NEVER
rendered the same as an empty/healthy report (the false-PASS "absence for
emptiness" anti-pattern this package's review focus names). See
`docs/SPEC.md` S7.10, `docs/CONSUMERS.md` §13 for a worked `--json` example,
and `nyxloom-trove/reports/ciu-P16-status-verb-LOG.md` for the full oracle
proof and gate output.

## CIU-QOL-7: Unified `ciu bake` respecting selection model

**Priority:** Medium (consistency)
**Effort:** Medium
**Status:** ✅ FIXED (ciu-P17)

Two build paths existed:
- Public `ciu bake [targets...] [--no-cache]`: passes targets straight to
  buildx; ignores profiles/phases/requires.
- Internal `deploy.action_build` (`--build` flag): filters targets by
  selected stacks under applications/tools/.

**Fix:** make public `ciu bake --profile core` resolve the selection and
build only matching targets. Remove internal action_build path.

**Evidence (ciu-P17):**
- Target-resolution unification: `ciu bake --profile NAME` resolves targets
  via the SAME chain `ciu up --profile` uses (`load_global_config` →
  `resolve_profiles` → `build_selection`, then
  `deploy.collect_bake_targets_from_selection`), feeding the SAME `docker
  buildx bake ... --load` invocation the no-`--profile` path already
  builds; `ciu bake [targets...]` with no `--profile` stays byte-identical;
  `--profile` and explicit positional targets are mutually exclusive
  (prefix-aware, catches `--profile=NAME` too). See `src/ciu/cli.py`'s
  `_bake`, SPEC S7.11, `tests/tests/test_ciu_cli_bake.py`.
- Dead-code removal: `deploy.action_build` (and its `--build`-flag docstring
  references) deleted from `src/ciu/deploy.py` — re-confirmed at deletion
  time it had zero callers and no CLI flag routing anywhere in `src/ciu/`.
  Its 3 dependent tests (`tests/tests/test_ciu_deploy_deeper8.py`, whole
  file, and
  `test_ciu_deploy_actions_remaining.py::test_build_uses_selected_application_targets_and_propagates_docker_failure`)
  were unique to that unreachable code path (own private
  `procutil.docker`/print-message contract, never produced by the real CLI
  path) and were deleted rather than ported — nothing reachable regressed.
  One coverage GAP found in the process was closed instead of silently
  dropped: the real `ciu bake` path's shared `subprocess.call` tail never
  had a test proving what happens when the `docker` binary itself is
  missing; `tests/tests/test_ciu_cli_bake.py::TestCliBakeDockerUnavailable`
  now pins that it propagates uncaught rather than silently succeeding.
  scope.touch was widened (handoff amendment, controller-authorized) to
  cover the 2 dependent test files before this deletion shipped. Full
  before/after evidence and gate output in
  `nyxloom-trove/reports/ciu-P17-unified-bake-LOG.md`.

## CIU-QOL-10: Preflight check for silently-empty rendered values

**Priority:** High (correctness)
**Effort:** Medium
**Status:** DEFERRED TO V8 (§2.5 of proposal)

empty string without error. A typo like `{{ contoller.name }}` produces
empty output that passes TOML parsing and may pass compose rendering until
the container fails at runtime.

**V8 approach:** wrap Jinja2 `Undefined` to raise on attribute access.

that exist or use `{% if x is defined %}` explicitly.

## CIU-QOL-12: Extend `ciu check` to full config validation with hook preflight

**Priority:** High (closes the "typos surface at runtime" gap)
**Effort:** Medium
**Status:** ⚠️ FIXED-partial (ciu-P18) — proposal §2.7 stages 1–6 and 8–12
shipped; **stage 7 (registry Pydantic models) is explicitly deferred to
ciu-P19** and is documented as absent in SPEC S13.4a, FEATURES.md and
CONSUMERS.md §14. `ciu check` must NOT be read as validating registry shapes.

Currently `ciu check` only validates the provisioning graph. It does NOT:
- Walk hooks to verify they load and export the right interface
- Call optional `validate_config()` on hooks that define it
- Validate registry shapes against built-in models
- Render configfiles or compose templates for validation

**Design:** see V8 proposal §2.7. The `validate_config` hook contract is
additive (hooks that don't define it are skipped), so it can ship now.

**Implementation plan:**
1. Add `validate_config` to HookContext documentation (S9) — ✅ done (S9.5)
2. Extend `action_check` in deploy.py to walk stages 1–12 from §2.7 — ✅ done
   for 1–6 and 8–12; stage 7 deferred (item 3)
3. Add built-in Pydantic models for PostgreSQL/Redis/MinIO/Consul/Vault
   registries — ⛔ NOT done; this is ciu-P19's whole scope (five model classes
   + a new optional dependency)
4. Add `--json` output with versioned envelope — ✅ done

This eliminates the need for consumers to run `ciu up --dry-run` as a
validation tool.

**Evidence (ciu-P18):**
- `deploy.action_check` walks stages 2, 3, 5, 6, 8–12 per selected+rendered
  stack, reusing the SAME functions `engine.main_execution` calls at each
  step: `config_model.validate_stack_shape`, `secrets.directives.discover` +
  `find_misplaced`, `governance.resolve_stack_governance`,
  `composefile.guard_config` + `render_compose` + `leak_scan` +
  `validate_consumption`. Stage 4 keeps the existing `lint_graph` path
  unchanged.
- **Side-effect-freedom is the load-bearing property** and is proved by a
  test that snapshots the whole `tmp_path` tree (paths, modes, sizes, bytes)
  before and after a check of a stack that on a real `ciu up` would create a
  hostdir, materialize four secrets, render a configfile + compose + overlay
  and execute three hook `run()` bodies — and asserts the tree is IDENTICAL
  (`test_check_leaves_the_filesystem_byte_for_byte_unchanged`), with a
  companion test proving the snapshot helper is not vacuous. Building this on
  `engine.main_execution(dry_run=True)` was rejected and is pinned as a
  negative test: dry-run still creates hostdirs and still runs hooks.
- Bytecode writing is suppressed during hook imports — CPython otherwise
  drops a `__pycache__/` beside every imported hook, which the tree snapshot
  caught as a real write into the consumer's tree.
- New `hooks_runner.load_hook_for_check(path) -> (run, validate_config|None)`
  loads a hook module ONCE and extracts both entry points; `load_hook` now
  shares the same extracted `_load_hook_module`. A per-run cache keyed by
  resolved path means a file declared at several points, or by several
  stacks, is imported exactly once.
- New optional hook entry point `validate_config(config, ctx) -> list[str]`
  (SPEC S9.5): called only by `ciu check`, never by `ciu up`; `run()` is
  located but never invoked; a bool/str return is a contract violation, not a
  verdict; an exception is that hook's own finding and never aborts the run.
- Exit-code discipline held: every new stage's failure is exit 2; exit 1
  remains reserved for `--live`'s probe failures, which are not attempted
  once a static stage is red.
- Named decisions: `ctx.secret_file` raises `KeyError` for EVERY name during
  check (nothing is materialized), and a declared-but-unconsumed secret stays
  a WARNING (matching `engine.py` Step 14's own precedent) rather than exit 2.
  Both are documented in SPEC S13.4a / S9.5 and in the ciu-P18 LOG.

- Render fidelity: the PURE halves of two steps the check does not run are
  applied in memory so templates still render — `engine.auto_generate_values`
  (Step 7, called directly, read-only) and a hostdir declaration→path rewrite
  (Step 8's path half only; nothing is created, seeded or chowned). Verified
  against the real dstdns workspace: before this, five real stacks failed
  compose-render with `'auto_generated' is undefined` and one crashed the run
  with an uncaught `yaml.YAMLError` from a hostdir inline table rendered as a
  Python dict repr. After: all stages green except three genuine pre-existing
  graph-lint findings, and `git status` in that workspace stayed clean.

**Follow-ups filed:**
- CIU-QOL-12a — extract the two blocks ciu-P18 had to mirror because their
  home modules were outside its scope: the S5 configfile
  declaration-shape/existence checks inlined in
  `composefile.render_configfiles` (a rendering, disk-writing function), and
  the hostdir path resolver inlined in `engine.create_hostdirs` (a
  directory-creating function). Both should become side-effect-free helpers
  that the real pipeline and `deploy.py`'s check path share.
- CIU-QOL-12b — `ciu check --json` writes its document to stdout after the
  orchestrator's own `[INFO]` prose, because `ciu check` routes through
  `deploy.main`. `ciu status --json` is clean because `cli.py` calls its
  action directly. Consider giving `check` the same direct handler so the

## CIU-QOL-13: Hook template library with revision tracking

**Priority:** High (enables config check + consistent adoption)
**Effort:** Medium
**Status:** OPEN — planned before v8

All hooks currently in use by consumers (dstdns) must exist as versioned
templates in CIU upstream. Each template carries a `template_revision`
integer that increments on every behavioral change, enabling adoption
tracking: a consumer can query "am I running the latest revision of this
hook?" without comparing file hashes.

**Proposed structure:**

```
ciu/src/ciu/hook_templates/
  post_compose_db.py            # template_revision = 1
  post_compose_vault.py         # template_revision = 1
  post_compose_consul.py        # template_revision = 1
  post_compose_redis.py         # template_revision = 1
  post_compose_authentik.py     # template_revision = 1
  pre_compose_tailscale.py      # template_revision = 1
  ...
```

Each template implements:
- `run(config, ctx)` — the normal S9 execution entry point
- `validate_config(config, ctx) -> list[str]` — the §2.7 preflight contract

`ciu init --hooks db-core,vault,consul,...` copies the selected templates
into the consumer's stack directories, stamping the current
`template_revision`. A future `ciu config check` stage can compare the
consumer's stamped revision against upstream and report outdated templates.

**Adoption flow:** dstdns migrates from hand-maintained hook scripts to
CIU-managed templates. When CIU updates a template (new revision), dstdns
sees the drift during config check and can adopt selectively.
