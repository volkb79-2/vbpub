## Design answers given 2026-09-03 (to be written into draft.5; reasoning here)

### A. Does ciu v8 need a canonical instance exclusive-access primitive? — Yes; it already has the object, it lacks the verb and the documented key.
Today nyxloom's `Stack: exclusive` and dstdns's run-gate caller `flock` each derive their own lock key from ciu's identity outputs (`${REPO_NAME}-${INSTANCE_ID}`, the project string) — the same re-derivation-of-identity class v8 removes everywhere else (P1, P6). v8 draft.4 already defines the lock object and the classes: the **checkout root directory** `flock` (S14.4: mutating verbs exclusive, gate and readers shared) and the **stack directory** `flock` of the owning Realization for exclusive use of one Realization (S16.5.3, `resources.shared`). What is missing is (1) a stated rule that these two directories ARE the canonical keys every consumer must use — a third party without ciu can `flock <checkout root> …` / `flock <stack dir> …` with util-linux and be correctly serialized against ciu itself, in v7 and v8 alike (the v7 fix for RG-39 can adopt the checkout-root key today); (2) a verb that wraps them and records the holder: `ciu lease acquire [--exclusive | --shared] [--realization <r>] [--purpose <text>] [--wait D] -- <cmd>` (holds the lock for the command's lifetime, like `flock(1)`; `--exclusive` on the instance blocks every other gate and mutating verb, which is what nyxloom's `Stack: exclusive` means; `--shared` is what a gate run takes), `ciu lease status` (holders with pid, purpose, since — read from `/proc/locks` plus a holder record in `ciu.instance.json`), `ciu lease wait`; the gate's own admission (S16.6) stays the coordination between shared holders. No new lock file, no lock-key naming scheme: the key is a directory git tracks. Not adopted: a name-based lease against `[resolved.identities.<r>.<svc>]` — a lease must survive a rename of the identity and must work before a render exists; directories do, derived names do not.

### B. Monorepo-wide shared governance defaults + worktree-scoped tester stacks — two asks, and only the first needs a mechanism.
(1) **Shared policy values.** draft.4 has `[testing] inherit` (S16.2.1, recursive, cycle-checked, paths relative to the declaring file). Generalize it once, explicitly, to `[ciu] inherit = "<path to an ancestor ciu.toml>"` with a **closed list of inheritable tables**: `governance`, `testing.environments`, `project.health`, `testing.judge`, `testing.cgroup_slice`. Lanes, services, realizations, bundles, layouts, secrets never inherit. Explicit path, not walk-up: `standalone_root` / nearest-ancestor-wins semantics are untouched, nothing is inherited that a file did not name (P3, defaults-are-hazards), and `ciu testing flatten` (→ `ciu show effective`) prints the merged result. This removes the governance drift the prompt describes (nyxloom missing `[governance]`) with one line per project.
(2) **Shared tester stacks per worktree.** A tester is a Realization of the project that uses it; sharing its *definition* is a shared stack directory, not a meta-root: the monorepo keeps `vbpub/tester-unified/ciu.stack.toml` + `ciu.compose.yml.j2` once, and every project declares `[realization.tester] kind = "ciu_stack" location = "../tester-unified"` — draft.5 relaxes S5.4's "repo-relative" `location` to "a path inside the same git repository" (checked). Each project's instance then gets its own tester (own network, own identity from its own instance id), governed by the (inherited) `[governance]`; a `test` bundle selects it; `[testing.environments.tester] exec_in = "tester"` uses it; `ciu instance init && ciu up --bundles test` in a worktree is the per-worktree tester. No `autostart` key: bundles already say what `ciu up` brings up and `enabled` says what a stack contains; a root file "aware of every nested project's stacks" is rejected — it conflicts with nearest-ancestor root resolution and with P3, and it would make one file the owner of every project's deploy set.
(3) **Zero-instance mode needs no monorepo variant.** A project with host lanes only stays zero-instance; a project that wants a governed container lane either declares the tester Realization (then it has an instance) or uses an `ephemeral` environment, which draft.4 already runs in the governance slice with the lane's caps (S16.6.2) — the CIU-native, governed replacement for run-gate's raw `docker run`.
