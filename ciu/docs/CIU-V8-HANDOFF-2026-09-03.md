## Design answers as they landed in draft.5 (and where they differ from the first version of this note)

### A. Canonical exclusive-access primitive — landed as written
S14.4.7 declares the checkout root directory (the instance) and a Realization's stack directory (exclusive use of its containers) the **only** lock keys; a third party takes the same `flock` with util-linux. S14.4.8 adds `ciu lease acquire (--exclusive|--shared) [--realization r] [--purpose] [--wait] -- cmd`, `lease status`, `lease wait`, with holder records in `ciu.instance.json` `leases[]`. S16.5.7 makes every `exec` lane hold its target's stack-directory lock for its duration — one lane per container, run-gate RG-39's rule lifted — which also dissolved half of round-2's T2-07 (no reservation ledger is needed for exec targets). A name-keyed lease stays rejected.

### B. Monorepo governance and per-worktree testers — one point changed
- `[ciu] inherit = "<path>"` (S3.1.5) with the closed inheritable list `governance`, `project.health`, `testing.environments`, `testing.judge`, `testing.cgroup_slice`; recursive, cycle-refusing, paths relative to the declaring file, `ciu show effective` marks sources; `[testing] inherit` withdrawn; S16.11.1 relaxed so a zero-instance monorepo root may carry `[governance]` for its inheritors. As planned.
- **Changed:** the first version of this note proposed relaxing S5.4 so several projects could share one stack `location` (`../tester-unified`). Writing the rule showed that a stack directory holds the stack's rendered artifacts (`ciu.compose.yml`, `ciu.rendered/`, `ciu.state.toml`, `ciu.secret-copy.*`, S2.2) and is the Realization's lock key (S16.5.3) — two projects, or two worktree instances of one, would alias them. What a monorepo shares is the **image build**: each project keeps a two-file stack (`ciu.stack.toml` + `ciu.compose.yml.j2`) whose `build.context` is the monorepo's `tester-unified/` directory (S6.2 lets a context leave the stack directory but not the checkout), and every worktree instance gets its own governed tester from it. `location` stays under the checkout and unshared (proposal X83).
- No meta-root, no `autostart`, zero-instance mode unchanged — as planned.

## The v7 question (what to do with `vbpub/tester-unified` today)
Nothing in ciu v7 gains a mechanism; v7 is maintenance-only by the ciu8 decision, and both halves are consumer edits in v7:
- **Governance drift** (nyxloom's and pwmcp's roots carry no `[governance]`, dstdns's site file does): copy one `[governance]` table into `nyxloom/ciu.global.defaults.toml.j2` and `pwmcp/ciu.global.defaults.toml.j2` now; v8's `[ciu] inherit` removes the copy later. Filed as nyxloom backlog NL-6.
- **Per-worktree tester**: today every vbpub gate already runs per lane in a fresh `tester-unified:local` container through run-gate's central `[environments.tester-unified]` (ephemeral mode) — per-worktree by construction. A project that wants a *persistent* exec-mode tester in v7 does what dstdns's `tools/test-runner` does: a `tester/` stack whose compose builds from `../../tester-unified` (or references the pre-built `tester-unified:local` image), `ciu worktree add` for the instance, run-gate exec mode with the derived container name. No new ciu v7 feature, no meta-root.
- **RG-39** (run-gate self-serialization around `docker exec`): buildable as described, with the refinements recorded in its backlog row (exec mode only; lock after the sorted shared-infra locks, released in the same `finally`; key on the owning stack directory once RG-37 reads `ciu.resolved.toml`, so v7 run-gate and v8 ciu take the same lock). Proposal §4.11 N22.
