Reviewed the full `main...HEAD` diff at `9a69f22a5e6574e9712185fdab20b6b5056d5394`. I found five material defects:

1. **High — Managed `ciu up` can use an unverified network.** [workspace_env.py](/workspaces/vbpub/.worktrees/ciu-overlay-intent-20261013/ciu/src/ciu/workspace_env.py:915) accepts any existing network with the requested name. The create CLI then recommends `cd <checkout> && ciu up` ([cli.py](/workspaces/vbpub/.worktrees/ciu-overlay-intent-20261013/ciu/src/ciu/cli.py:1987)), which bypasses `worktree up`’s ownership check. If an unlabelled same-name replacement appears, direct `ciu up` can deploy onto it; the same race exists between `worktree up`’s check and its child. **Fix:** verify the managed record’s network ID or owner label in the network-use path itself before accepting an existing network.

2. **Medium — An explicit non-root path silently selects the Git root.** [cli.py](/workspaces/vbpub/.worktrees/ciu-overlay-intent-20261013/ciu/src/ciu/cli.py:718) returns no CIU root when `--root-folder` names an existing directory without a CIU marker; [cli.py](/workspaces/vbpub/.worktrees/ciu-overlay-intent-20261013/ciu/src/ciu/cli.py:1962) substitutes the Git root. In a nested-root repository, a mistyped path can make `create` write a rootless record at the wrong offset or make `inspect` report a real instance missing. **Fix:** refuse an explicit path that resolves to neither a CIU root nor the Git family root.

3. **Medium — A requested network claim can succeed without claiming an object.** [worktree.py](/workspaces/vbpub/.worktrees/ciu-overlay-intent-20261013/ciu/src/ciu/worktree.py:4311) returns the unchanged record when the network is absent. `adopt --adopt-existing-network` then reaches `ready` through [worktree.py](/workspaces/vbpub/.worktrees/ciu-overlay-intent-20261013/ciu/src/ciu/worktree.py:5432) with `network_id: null`; an incomplete `ensure` has the same path. The flag promises an assertion about an exact existing object, but none was observed. **Fix:** require a present, verified object before an explicit claim may succeed, including during recovery.

4. **Medium — Unknown network ownership is recorded as a proven collision.** For an unlabelled existing network with no saved ID, [worktree.py](/workspaces/vbpub/.worktrees/ciu-overlay-intent-20261013/ciu/src/ciu/worktree.py:4336) says ownership cannot be proved. [worktree.py](/workspaces/vbpub/.worktrees/ciu-overlay-intent-20261013/ciu/src/ciu/worktree.py:4814) records `runtime-collision` anyway, even when that network belongs to the adopted checkout. **Fix:** distinguish unverified ownership from a conflicting label or duplicate identity; reserve `runtime-collision` for demonstrated conflicts.

5. **Medium — A corrupt sibling can be excluded from a uniqueness certification.** [worktree.py](/workspaces/vbpub/.worktrees/ciu-overlay-intent-20261013/ciu/src/ciu/worktree.py:2059) warns and omits an unreadable sibling record, while [worktree.py](/workspaces/vbpub/.worktrees/ciu-overlay-intent-20261013/ciu/src/ciu/worktree.py:4201) checks only the returned records. A new allocation can therefore become `ready` when the omitted sibling owns the same runtime ID or network; its identity is unknowable from the failed read. **Fix:** keep best-effort inventory for listing, but make allocation identity admission fail as indeterminate when a sibling record cannot be authenticated.
