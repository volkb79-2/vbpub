# Nyxloom primary CLI reference and adoption audit

This is the canonical current-state inventory of the installed nyxloom
command (nyxloom.cli:main), including nested actions. It does not describe
nyxloomd, nyxloom-agent-cli, or nyxloom-controller.

**Snapshot:** source revision 253125a696301c2f6df17561fc2af4f7179f6d80.
The grammar is derived from src/nyxloom/cli.py::_build_parser() and main()
dispatch, not help output alone. Recommendations are proposals unless marked
approved. This audit changes no runtime or packaging code.

The parser has 35 top-level choices, 55 parser nodes, 45 dispatchable leaf
actions, and one empty reserved gate path. There are 37 positional
declarations, 158 action-local option declarations (168 spellings), and two
root global options; implicit help actions are listed separately.

The option matrix records parser types, choices, aliases, arity, parser
defaults, and help. The action table records handler effects and safeguards.
An argparse default of None means the handler/configuration supplies the
effective omitted behavior. Where no authoritative effective default was
found, the audit says so instead of inventing one.

## Invocation and output contract

| Invocation | Current accepted form and behavior | Adoption status |
|---|---|---|
| Top help | nyxloom --help and nyxloom -h; exit 0, grouped help on stdout. Bare nyxloom exits 2 and prints grouped help to stderr. | All paths initialize logging first and create logs/nyxloom.jsonl. Violates cli-extended's side-effect-free display contract. `-h` removal is approved (D-001), not yet implemented. |
| Nested help | nyxloom PATH --help or -h; exit 0, nested help on stdout. There is no help VERB route. | Also creates the log file. Adoption requires help [verb]. `-h` removal is approved (D-001), not yet implemented. |
| Version | nyxloom --version prints nyxloom VERSION; nyxloom version prints only VERSION. Both exit 0. | Both create the log file and output strings differ. Adoption requires identical identity output and no filesystem side effect. |
| Global --debug | Accepted only before the first verb (for example, nyxloom --debug status); not accepted after a verb. Enables traceback behavior in the outer exception path. | Approved target (D-006): cli-extended verbosity semantics, with traceback moved to --traceback; not yet implemented. |
| Parser errors | Unknown verbs, malformed arity, invalid choices, and parser-declared conflicts exit 2. Top-level errors use grouped help; nested errors print nested usage. Handler errors generally use exit 1 or 2 and stderr. | cli-extended command-local errors include complete command help; current nested errors do not. |
| Ordinary output | Text by default. JSON exists only on selected extraction/events commands. | Keep output options command-scoped where a schema exists. |
| Bootstrap | main() calls _bootstrap_logging() before parsing. log.configure() creates its directory and file even for help/version/error paths. | Move side-effecting bootstrap after display/error classification or make those paths side-effect free. |
| Version source | nyxloom.__version__ reads installed distribution metadata; a source checkout without metadata reports 0.0.0+unknown. | Bundled library identity must use Nyxloom distribution metadata, not a guessed cli-extended version. |

Global options currently precede the verb. Per-command options follow the
complete command path. For example, nyxloom --debug version parses;
nyxloom version --debug and nyxloom --project-id p status do not.

## CLI ownership boundaries

The installed package currently exposes one console script,
`nyxloom = nyxloom.cli:main`. `nyxloom daemon` starts the resident daemon
through that same entry point; there is no separate `nyxloomd` console script
in `pyproject.toml`. The primary CLI dispatches to local Python handlers and
host state. It is not currently an HTTP client of the daemon.

| Surface | User and data target | Current execution/trust boundary | Split signal |
|---|---|---|---|
| `extract`, `extract-lossless`, `extract-debug`, `extract-report`, `extract-sessions` | Agent/session reviewer; reads Claude Code, Codex, OpenCode, or Reasonix session files and stores under user-owned paths. | Local file/database reads and terminal output. It does not need a registered Nyxloom project. Current `main()` still initializes Nyxloom host logging before dispatch. | Approved target: move every session command to `nyxloom-harness` in the same wheel. It must not initialize host state or require a daemon. |
| `init`, `onboard`, project-local `lint`, `backlog *` | Project author; reads or writes a project's trove/config/backlog inside its checkout. | Local project filesystem operations. These paths use cwd discovery and do not require project registration. | Approved target: keep project-local work under `nyxloom`; add an optional schema-validated interactive backlog create/edit flow. |
| `project`, `status`, `doctor`, `resync`, `tick`, `pause`, `resume`, `merge`, `reject`, `decide`, `leases`, `render`, workflow/intake/finding commands | Host operator/controller; selects registered project roots and shared host state, then inspects or changes workflow state. | Local process calls Nyxloom config/storage/reconcile modules directly. Workflow mutations carry existing actor/event and state guards. Most branches do not request the running daemon. | Approved target: move all local host-control commands to `nyxloomctl` now. Remote transport, endpoint, credential, and error contracts are a later design. |
| `auth`, `routes`, `free-models`, `capability-map`, `route doctor`, `migrate-store` | Nyxloom host administrator; manages host credentials, routes/catalogs, runtime diagnostics, or storage. | Local host state; some commands make outbound provider probes. `auth` manages the credential the HTTP control surface validates. | Approved target: place these local admin commands under `nyxloomctl`; remote operations remain out of scope. |
| `nyxloomd` HTTP/SSE and static dashboard | Human operator using a browser or a script reading the dashboard surface. | GET endpoints expose registered-project/task/event/log views on the configured trusted network. POST config/decision/intake mutations in `_CONFIG_POST_PATHS` require the operator bearer credential before the body is read. | This is the existing daemon client boundary. The dashboard is a client of the daemon; the `nyxloom` CLI is not. |
| Registered/client projects and dispatched agents | Project repositories provide trove/config/handoff/git inputs; dispatched agents work in scoped project worktrees/containers. | Daemon consumes registered filesystem roots and dispatches adapters. No project-scoped HTTP identity/client contract was found. `POST /api/intake` uses the operator-authenticated control API, not a project credential. | A project-consumer API would be a new product capability, distinct from the dashboard/control API and from the operator CLI. Require a concrete client journey and per-project authorization/audit model first. |

These are separate choices: logical command grouping, separate user-facing
console scripts, a service-specific `nyxloomd` entrypoint, and separate
distributions. Adding scripts to the existing wheel does not reduce that
wheel's dependencies. Separate distributions add versioning/release
coordination and require code/dependency ownership changes. The initial
parser-adoption decision applies to the current primary `nyxloom` entry point.
The approved target has three user-facing console scripts in the same wheel:
`nyxloom` (local trove authoring), `nyxloom-harness` (AI-harness workflows),
and `nyxloomctl` (all local host-control, administration, and developer
diagnostics). `nyxloom` and `nyxloom-harness` must work with the daemon
unavailable. The dashboard remains the current HTTP/SSE client; remote
`nyxloomctl` transport/operations require a separate design. D-009 approves a
service-only `nyxloomd` console script for the existing daemon container.
These target entrypoints are not implemented in this audit. D-013 approves
removing the old host-control spellings from `nyxloom`; the adoption must
publish an old-to-new command migration table and must not keep forwarding
aliases in a second registry.

| Installed command | Command families after adoption |
|---|---|
| `nyxloom` | `init`, `onboard`, project-local `lint`, and `backlog`; each operates on project-local trove files and does not require daemon availability. `lint` with no paths discovers the current project and checks its handoffs. |

## Command-design review and backlog recommendations

The table distinguishes shipped behavior from the operator-approved adoption
target. Decisions D-001 through D-016 now record the approved grammar,
command boundaries, compatibility break for moved commands, optional shared
prompt API/extra, daemon launch surfaces, managed backlog create/edit as the
first interactive authoring workflow, exact create/edit spellings, and the
project-local versus host-wide lint boundary. None has been implemented in the
runtime yet.

### Journeys checked

- **Project author:** `init` or `onboard` scaffolds a project, `project add`
  registers it, `lint` checks handoffs/configuration, and `backlog` maintains
  project work. Init and onboard have distinct setup depths; registration is
  a separate explicit step. NL-19's context-pack workflow overlaps author and
  carver preparation but remains in `tools/pack.py` with unresolved root and
  score inputs.
- **Operator and recovery:** `status`/`doctor` diagnose, `resync` plans or
  applies task state, `pause`/`resume` guard operation, and `tick` or `daemon`
  drive reconciliation. The verbs separate observation, repair, control, and
  scheduling. Unknown project filters and ignored safety options are the
  defects proposed in D-003/D-004.
- **Manual controller:** `project list`, `status`, `merge`, `reject`, `decide`,
  and `backlog` support inspection and recording controller work. NL-18
  identifies a gap: a task created outside daemon dispatch has no command to
  enter the state model, so it is absent from those read paths.
- **Automation:** selected commands expose JSON (`extract`, `extract-report`,
  `extract-sessions`, and `events`); other commands are text only. Parser
  errors use 2 while handler failures commonly use 1 or 2, so a follow-up must
  preserve command-specific exits and pin JSON schemas. No interactive prompt
  is a general authorization contract; operation-specific safeguards remain
  the consent boundary.
- **Inspection:** `routes`, `free-models`, `capability-map`, findings, events,
  leases, digests, and session extraction cover configuration, model/catalog,
  workflow, and transcript views. Capability JSON is not a global format;
  session reports and event output have distinct schemas. NL-20's process
  history would overlap run-gate/cgprofile and extract-report.
- **Release operator:** the installed Nyxloom CLI has no release/publish verb;
  the repository's CMRU workflow releases the Nyxloom wheel. Do not fold
  build/publish or OCI lifecycle into the project-operator CLI as a side effect
  of parser adoption. NL-15/NL-16 remain release-boundary decisions.

| Surface | User journey and evidence | Recommendation / migration / compatibility |
|---|---|---|
| Flat workflow verbs | Operator/manual-controller flows use tick, decide, discuss, intake, reject, merge, pause, resume, digest, events, status, resync, and leases. Handlers distinguish display from mutation; tests encode these direct routes. | Keep names and boundaries. Grouping would break existing automation without evidence of confusion. ## cli-extended boundary and package plan

The root repository marks libraries/cli-extended independently packageable.
Nyxloom pyproject discovers packages under src/ and currently does not include
or depend on cli_extended; nyxloom/cmru.toml releases only the Nyxloom wheel.
Thus cli-extended is not in the current wheel. The approved target bundles
its import package into the Nyxloom wheel, without a separate library release
or runtime distribution dependency.

| Library contract | Current mismatch | Follow-up requirement |
|---|---|---|
| Help | -h/--help at parser levels, custom grouped top help, no help VERB, nested parser errors omit complete help. | Registry-generated --help, help [verb], bare invocation, and command-local errors. Remove -h as approved in D-001. |
| Version | Flag prints nyxloom VERSION; verb prints VERSION. Both bootstrap logging first. | Use CliIdentity.from_distribution("nyxloom"), same line for both, and side-effect-free display paths. This follows approved full alignment. |
| Global options | --debug currently means traceback-on-exception, not verbosity; NYXLOOM_LOG_LEVEL is env-only. --version is an argparse action. Both root options must precede verb. | D-006 is approved: adopt cli-extended --log-level/--debug verbosity, preserve current traceback behavior under --traceback, and give the explicit option precedence over the environment. |
| Aliases/nesting | Option aliases work; no Nyxloom verb aliases. Top help group map is handwritten separately. | One registry owns nested paths/help/dispatch; do not reparse or maintain parallel command lists. |
| Mutation/confirmation | mutating=True enables --yes and states confirmation is required. Nyxloom mutations already rely on explicit verbs, state checks, --apply/confidence opt-ins, role checks, or store protections. | Library API must separate “mutates state” from “requires interactive confirmation/--yes”. Existing safeguards are approved consent; do not misdeclare or add a second prompt. |
| JSON/progress | Nyxloom JSON is command-specific; it has no general progress output. cli-extended VerbSpec defaults include_json and include_progress to true. | Set both false where no real schema/progress contract exists; enable only defined machine-readable or progress surfaces. |
| Color | ANSI/Markdown belongs mainly to session extraction. Other commands are plain output. | Keep per-action output policy and NO_COLOR behavior; document CliOutput.color_enabled(stream) boundary. |
| Shared options by action | --log-level applies to all commands; JSON currently applies only to extract, extract-report, extract-sessions, and events; color only to extract renderers; progress has no current implementation; confirmation has no generic prompt call. | Add logging verbosity globally. Do not inherit JSON/progress/--yes on unrelated actions. Keep command-specific output schemas and existing state safeguards. |
| Errors/cancellation | Parser uses exit 2; handler failures are usually 1/2; --debug changes exception presentation. Cancellation is not a uniform command contract. | Map current refusals deliberately; cancellation should use 130 without swallowing application errors. |
| Identity/package | Source sentinel can be 0.0.0+unknown; wheel metadata is authoritative. | Bundle library in Nyxloom wheel and use Nyxloom metadata. |

The follow-up installed-wheel oracle must build Nyxloom's wheel, install it in
an isolated environment outside this checkout, make the checkout unavailable
on sys.path, then run nyxloom --help, nyxloom version, representative nested
help, and import cli_extended. Assert cli_extended.__file__ is inside the
installed wheel and identity is Nyxloom distribution metadata. This audit
does not change packaging.

## Dispositions

|---|---|---|
