## Confirmed findings, most severe first

**1. High, blocks the CIU release. CIU's Run-Gate wheel check no longer compares any bytes, and its own tests should fail.**
- **Where:** `ciu/scripts/check_run_gate_wheel.py`, function `verify_module_file` (lines 13–24) and lines 57–66.
- **What happened:** commit `08632f747` ("close release-wave followup findings") inserted new functions in the middle of `verify_module_file`. The missing-source check and the `read_bytes()` comparison now sit after `return scripts` in `_source_console_scripts`, where they can never run.
- **Impact:** `verify_module_file` now only checks that the module is inside the venv. Both CIU release steps (`ciu/cmru.toml:73,79`) still print "modules and console entry points match the selected checkout", even when the image holds an old Run-Gate. The check reports a pass it never tested.
- **Tests that should fail:** `test_byte_mismatch_is_rejected_with_module_name`, `test_missing_checkout_module_is_rejected` and `test_main_rejects_only_stale_admission_module`. The first also expects the text `RUN_GATE_TESTER_VERSION` in a message that `1fa737782` removed.
- **Why it wasn't caught:** the only gates run at `af537c9` were Run-Gate's and CGProfile's. CIU's gate was not run.
- **Fix:** move the two checks back into `verify_module_file`, update the stale message assertion, and run CIU's registered gate before any merge.

**2. High. Run-Gate's release-candidate build stamps an unproven stable version into the shared tester image.**
- **Where:** `run-gate-project/tools/release_candidate.py`, `prepared_release_version` (line 45) and `prepare` (line 184).
- **What it does:** it takes the first dated stable heading in `CHANGES.md` as the version and builds with that version forced. It then rebuilds the shared `tester-unified:local` with labels and a receipt claiming that version.
- **What it never checks:** that no `run-gate-v<version>` tag exists yet, or that HEAD is the commit CMRU generated by moving the `[Unreleased]` notes into a dated section (folding).
- **Realistic trigger:** this already happened according to the gate facts you gave. Outside the release transaction, candidate source was labelled as the published 23.10.0, and the image every project's gates use now carries that false label.
- **Second problem:** inside the transaction, the shared mutable tag is overwritten mid-release. If any other agent rebuilds `tester-unified:local` between the gate and the build step, `verify` fails and the release tag is rolled back. That fails safe, but it is fragile on a shared host.
- **Why it wasn't caught:** tests cover receipt and digest matching, not whether the chosen version is genuinely unreleased.
- **Fix:**
  - Refuse when the tag already exists locally or on origin, or when HEAD lacks CMRU's prepared-release commit. Outside a transaction, use a `.devN+g<sha>` style version.
  - Gate on a receipt-specific image tag, and retag `:local` only after publication.
  - Rebuild the estate's tester image from a correctly identified wheel now.

**3. Medium-high. CMRU's release gate never ties the tester image to a published Run-Gate.**
- **Where:** `cmru/tools/run_release_gate.py`, `_check_run_gate_identity` (lines 94–232).
- **What it checks:** that the devcontainer's `run-gate` is a stable release of at least 24.0.0, and it records a hash of its files.
- **What it doesn't check:** that the hash matches the published `run-gate-v24.0.0` asset, or that the `tester-unified:local` image (which CMRU's lanes run in) holds that same wheel. The docs say "rebuild tester-unified from the exact published wheel", but nothing enforces it.
- **Trigger:** a plain `24.0.0` wheel left in `run-gate-project/dist/` by a failed or rolled-back Run-Gate release passes the version floor.
- **Fix:** compare both the devcontainer's distribution hash and the image's `org.vbpub.run-gate.wheel-sha256` label against the published asset's digest.

**4. Medium, confirmed in code; real-world impact needs pilot evidence. Assay's resource-event rules can wreck or abort long mutation (R2) campaigns.**
- **Where:**
  - `assay/src/assay/resource_limits.py`: `limit_hit` (lines 205–216) and the ancestor rule (lines 345–352).
  - `assay/src/assay/mutation.py`: `_resource_limit_bucket` (lines 3075–3081) and `_candidate_resource_limit_evidence` (lines 2938–2950).
- **Memory pressure counted as failure:** `memory.events` "max" is treated as a limit hit. The kernel raises it whenever a charge reaches `memory.max`, including when page cache is reclaimed without any failure. In R2 lanes capped at 2 GiB, once page cache fills the cap, candidates are marked `crashed` and the R2 result becomes an infrastructure error. Examples are CMRU's `mutation` lane and Run-Gate's `assay-r2`, whose 2 GiB cap is new in this wave.
- **Sibling events abort the whole campaign:** the ancestor rule is new in `90dc9078d`. A local event on a shared ancestor, such as the gate slice, while the candidate itself is quiet aborts the entire lane with ERROR/EXEC_FAILED. So a sibling gate pressing the shared slice can abort every R2 campaign running at the time. It fails safe, but it reports host contention as an execution failure instead of a retryable infrastructure result.
- **Why it wasn't caught:** no R2 campaign has run at this candidate. KI-79 postpones CMRU's, and gate-full has no R2.
- **Fix:**
  - Count only `oom`, `oom_kill`, `oom_group_kill` and `pids.max` as limit hits, and keep `max` as telemetry.
  - Turn an unattributable ancestor event into a per-candidate retry or INCONCLUSIVE, not a whole-lane ERROR.
  - Make the required B105 and analysis pilots report these counter changes under the declared caps.

**5. Medium. The bootstrap CMRU controller is only documented, not enforced (prior N1 still open).**
- **What's there:** `cmru/docs/RELEASE-TRANSACTIONS.md` §"Bootstrap…" now describes building a non-editable CMRU wheel from the merged commit.
- **What's missing:** nothing in `cli.py` or `transaction.py` refuses an editable or dirty `cmru` install, and the transaction does not record the controller's identity. The devcontainer's `cmru` is editable from the shared checkout.
- **Fix:** have `cmru release` refuse a controller installed editable or from source, and record its distribution hash in the transaction log.

**6. Low-medium. The intended release order exists only in prose.**
- **Order conflict:** `cmru.orchestration.toml` puts `cmru` before `run-gate-project` and `cgroup-profiler`. A multi-project `cmru release` would start with CMRU, whose gate needs Run-Gate 24, so it fails before tagging. That is safe but unworkable. In practice, every step must be a separate single-project release with manual installs in between.
- **Missing prerequisites:** the order CGProfile → Run-Gate → CMRU → CIU/Assay leaves out deploying the CGProfile daemon (`ciu up`) and re-applying MDT host-setup for the observer group and `/run/cgprofile`. Run-Gate/Assay observer lanes and the pilots depend on both. They fail closed (`fail_infra`), but they are unscheduled.
- **Fix:** write a wave runbook with explicit deploy steps, or encode a dependency override for this wave.

**7. Low. debian-install-v2 ships as soon as it merges, and doesn't belong in this wave.**
- **Not released by CMRU:** it isn't a CMRU-orchestrated project.
- **Unpinned code:** the ISO launcher downloads `bootstrap-remote.py` from a moving branch at boot and runs it as root with no hash pin (`iso_builder.py:35-70`, prompt at `:277`).
- **Effect:** merging this wave to `main` effectively deploys the new installer to every existing ISO. Its registered gate evidence isn't among the gate results you listed.
- **Fix:** split it into its own merge with VM-harness gate evidence, and add an optional pinned commit plus SHA-256 bootstrap mode.

## Can the release sequence complete?

It can, if findings 1 and 2 are fixed first and the steps run one at a time:

1. Provisional merge.
2. Install a bootstrap CMRU, non-editable, from the merge commit.
3. Release CGProfile with `--set-version 1.0.0`.
4. Deploy the CGProfile daemon and re-apply MDT host-setup.
5. Release Run-Gate. CMRU folds the 24.0.0 section, `prepare` builds and receipts the wheel and image, selftest checks the running image, the tag is pushed, the build is re-verified against the receipt, then it publishes.
6. Install the published Run-Gate 24.0.0 wheel and confirm the tester image's digest label matches it, by hand, because of finding 3.
7. Release CMRU. Its KI-79 provisional gate correctly accepts only the prepared 6.2.0 section, and the folding step does produce 6.2.0. R2 stays deferred.
8. Release CIU (after finding 1), then Assay after the B105 and analysis pilots.

Each step is CMRU's own verb. The only unsupported manual steps are installing the controller and Run-Gate wheels, the daemon and host-setup deployment, and the check in step 6.
