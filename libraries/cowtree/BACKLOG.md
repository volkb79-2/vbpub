# cowtree backlog (COW-BL)

Open work. Each item names what it needs and what closes it. Consumers: `ciu worktree` (CIU-159) and run-gate R2 clones.

* **COW-BL-01 declaration schema for CoW-managed gitignored paths.** Cowtree defines and validates the schema; the consumers read it and stay agnostic of what the paths hold (`artifacts/vm-lab`, `downloads` and the like are the project's business, never a ciu or run-gate constant).
  * **Where it lives.** The project declares it in a tracked file (one table per path). The consumer passes the parsed declaration to cowtree; cowtree refuses an unknown key, a duplicate path, an absolute path, a `..` segment and a path that is tracked content other than its committed placeholder.
  * **Keys per path.**
    * `path`: repo-relative, gitignored.
    * `mode`: `clone-from-main` is the only value today. A worktree gets a writable snapshot of main's content after checkout.
    * `compression`: a btrfs compression name (for example `zstd`) or `none`. Applied to the new subvolume; ignored by the reflink and copy backends.
    * `fallback`: what a plain host does. The value is `empty` (an empty folder, plus exactly one INFO line naming the path and the reason). Any other value is refused.
  * **Placeholder contract.** Every declared path is a committed placeholder directory: a `README.md` and a `.gitignore` (`*`, `!.gitignore`, `!README.md`), force-added. The validator checks both files exist in the tree and that the `.gitignore` has exactly that shape.
  * **No overrides.** No `MDT_*` or other environment variable relocates a declared path, and there is no mount-over: the declared path is a subvolume of the checkout itself.
  * **Closes when.** The schema has a SPEC section with oracle ids, a `validate_declaration()` API and a CLI verb with a stable exit code, and tests cover each refusal above; CIU-159 and the run-gate R2 clone code read the declaration only through it.

* **COW-BL-02 provision operation (main) and snapshot operations (worktree).** Primary model: the checkout, with `.worktrees/` inside it, lives on the CoW filesystem. Worktrees still come from git. Only declared paths become CoW snapshots of main's.
  * **Provision in main (`cowtree provision`).**
    1. Move the committed placeholder contents aside (a subvolume create needs a non-existing path).
    2. Create the subvolume at the declared path with the declared compression.
    3. Move the placeholder files back, so `git status` stays clean.
    * Idempotent: a path that is already a subvolume is left alone. A plain non-empty directory with content beyond the placeholder is refused, with its size and top-level entries; a `--migrate` flag copies with reflink, verifies, then replaces. `--migrate` refuses while a process holds files there.
  * **Snapshot for a worktree (`cowtree snapshot-declared`).** After `git worktree add`, replace each declared path with a snapshot of main's subvolume, then restore the tracked placeholder files from the worktree's own branch (so a branch that changed the placeholder keeps its version and `git status` stays clean).
  * **Remove for a worktree (`cowtree remove-declared`).** Delete each declared subvolume with the subvolume-delete ioctl (not `rm -rf` into it), then report remaining protected state as before. Refuse when a foreign mount sits under the worktree (see the worktree library item WT-OW-01).
  * **Persistence.** Anything a worktree keeps is copied (reflink where possible) to main's declared path by an explicit operation; there is no automatic merge back.
  * **Fallback.** On a plain host (no btrfs, or a checkout not on the CoW area) every operation degrades to the declared `fallback`: an empty folder, one INFO line, exit 0.
  * **Closes when.** The three operations exist on the btrfs backend with FakeBackend coverage for the ordering (aside, create, back; snapshot, restore; delete), a live btrfs test on the tester host proves a clean `git status` after each, and the plain-host fallback prints exactly one INFO line per path.

* **COW-BL-03 ZFS dataset backend (design note only; no ZFS host to test).** **Superseded 2026-11-05 by COW-BL-07** (a ZFS pool now exists on v1001 and was measured).
  * **Today.** Cowtree has btrfs, reflink and copy backends. ZFS is reachable only through block-cloning reflink on a ZFS version that supports it; there is no snapshot or subvolume semantics there.
  * **Design.** A persistent `dataset` operation set (`create`, `mount`, `destroy`, plus `snapshot_clone` for the worktree case) would be the new backend interface, beside the existing per-run `clone` interface. Provision and the worktree operations of COW-BL-02 call it instead of calling btrfs directly, so a ZFS backend adds one class.
  * **Not decided.** Dataset naming under the pool, mount point management when the checkout is not under the dataset's mount point, and the destroy ordering (clones before origin).
  * **Closes when.** Written into DESIGN-GUIDE as an interface sketch the btrfs backend already satisfies, implemented only when a ZFS host exists to run the live test. Until then nothing is built.

* **COW-BL-04 persistence expectations under relaxed fsync (default for disposable CoW trees, clones and VM runs).** **FIXED 2026-11-04 (3f7ebe27b)** — SPEC "Persistence declarations" P1-P4, DESIGN-GUIDE paragraph, test `test_truncated_owner_manifest_is_untrusted_and_never_collected`. Note: a truncated manifest is retained and reported (`manifestless-or-invalid`), not reclaimed; automatic reclaim of manifestless dirs was deliberately not added (mid-creation runs look the same). Operator direction 2026-11-04: tests, mutation campaigns and VM runs on the CoW setup run with fsync disabled by default (run-gate RG-149 owns the lane switch; the Q4 decision of 2026-10-30 already set VM disks compressed and no fsync). Cowtree declares which of its own writes need durability, so a consumer under the preload knows what a host crash can cost.
  * **Rule.** Page cache survives a process or container kill, so every operation stays correct across those. Only a host crash or power loss loses unsynced data. Disposable CoW state is regenerable by construction; the declarations below say what is not.
  * **Declared per write.**
    * Clone creation (btrfs snapshot, reflink, copy): no fsync. A clone after a host crash is discarded and recreated.
    * Sealed trees: no fsync of content; the seal marker is written last by atomic rename, so a reader sees either a complete seal or none. After a host crash an unsealed or missing marker means rebuild.
    * `owner.json` manifest and lease files: atomic replace stays (correct for every process-level failure). The file and directory fsync that exist today are kept only when cowtree is not under the preload; under it they are no-ops, and the declaration is that a lease or manifest lost on host crash means the clone is orphaned and is reclaimed by the normal expiry sweep, never trusted without a readable manifest.
    * Declared gitignored paths (COW-BL-02 snapshots): regenerable from main; `persistence` copies to main are explicit and fsync the destination (the one durable write cowtree makes on purpose).
  * **Code and tests.** A read of the manifest that is empty, truncated or unparsable is treated as "no manifest" and reclaims the clone; a test truncates `owner.json` and checks the sweep. The DESIGN-GUIDE manifest-fsync paragraph (`_write_manifest`) gets a paragraph with the table above.
  * **Closes when.** SPEC states the table with oracle ids, the truncated-manifest test passes, and no cowtree path assumes a manifest fsync for correctness under the preload.

* **COW-BL-05 VM disk cache modes in the vm-lab layout and the VM harnesses.** Same direction as COW-BL-04, for QEMU disks under `artifacts/vm-lab` (run-gate already forwards `[resources.vm] disk_cache` `unsafe|writeback` as `VM_DISK_CACHE` for host-mode VM lanes).
  * **Rule.** Two classes of disk, declared where the disk is created, never inferred:
    * **Disposable run disks** (overlays and clones used for one run or one test): `cache=unsafe`, no fsync from the guest reaching the host, compressed CoW subvolume (Q4).
    * **Installed-base and golden images** (the bases that runs clone from, must survive the host): `cache=writeback`, or `cache=none` where the harness needs direct IO; never `unsafe`. Built once, sealed, and checked (checksum recorded next to the image) before any run clones it.
  * **Harnesses to align.** The per-project vm-lab layout, the pwmcp harness, and the debian-install-v2 harness (`testing/vm/vmctl`). Each reads the class from one place (the disk's declaration in vm-lab), not from a per-harness flag default.
  * **Failure semantics.** A host crash may corrupt an `unsafe` run disk; the harness deletes and recreates it, and never boots a run disk it did not create in the current run. A golden image is never opened writable by a run.
  * **Closes when.** The vm-lab layout names the two classes and the cache mode for each, the three harnesses use them, a test asserts the QEMU command line carries `cache=unsafe` for a run disk and not for a golden image, and a golden image opened writable by a run is refused.

* **COW-BL-06 estate documentation line for the relaxed default.** One line goes into the AGENTS.md "Directory conventions and VM files" section, under the placeholder rule: "Relaxed fsync is the default for disposable CoW worktrees, clones and VM runs (run-gate `io_sync`, cowtree COW-BL-04/05); durable only by explicit declaration (iobench, durability and crash-consistency tests, installed-base and golden VM images)." The cowtree README and run-gate README link to the same sentence instead of restating it.

* **COW-BL-07 native ZFS dataset backend: evaluated 2026-11-05, deferred; design sketch and reopen criteria.** Supersedes the "no ZFS host to test" premise of COW-BL-03 (a ZFS pool `zp` now exists on v1001; OpenZFS 2.4.4 under kernel 7.2.11; `reports/zfs-eval-REPORT.md` of the release program, assay B225).
  * **Measured.** Steady state per candidate on the Assay materialization loop: per-worker dataset with `zfs rollback -r` 0.01 MB read, 0.30-0.35 s materialize, 0.11-0.14 s rollback; `zfs clone` per candidate 0.02 MB (only with the ARC minimum pinned to the cap; 36 MB with a bare 300 MiB cap), 0.44-0.50 s; clone+mount 33 ms, destroy 41 ms. It is not faster than the primed btrfs snapshot (0.31 s), so nothing is built now.
  * **Design (sketch, when built).** Backend name `zfs`, detected by `statfs` ZFS magic on a dataset root. Tree = dataset `<area>/<run-id>-<tree>`; `clone_tree` = `zfs snapshot` + `zfs clone`; `seal` = `@seal` snapshot + `readonly=on` (clone sets `readonly=off`); `delete_tree` = `zfs destroy -f` with clones before origin; new `reset_tree` = `zfs rollback -r @pristine` (unprivileged on a mounted dataset). Space admission from `zfs list -Hp -o available`. GC destroys the run's datasets then its `cow-<run>-*` snapshots. Full table in the report, section 9.
  * **Privilege.** `zfs allow` delegates snapshot, rollback and destroy to the runner user, but mounting a new dataset needs root on Linux (measured: "may only be mounted by root"). So either pre-mounted per-worker datasets (root once, rollback unprivileged) or a root helper with an allowlisted verb set shared with the overlay helper of assay B221. ZFS operations run on the host side, never in a lane container.
  * **Reopen when.** A workload needs ZFS-specific properties (see assay B225) or a host standardises on ZFS. Closes when the sketch is in DESIGN-GUIDE (as COW-BL-03 asked), a `FakeBackend` ordering test covers create, snapshot, clone, seal, destroy-clones-before-origin and rollback, and a live test on a ZFS host proves a clean `git status` after rollback.

* **COW-BL-08 reflink-on-ZFS is a measured trap for tree clones: warn or refuse in `detect()`, and correct the documentation.** README, DESIGN-GUIDE ("ZFS uses the reflink backend") and CONSUMERS currently present reflink as the ZFS path. On v1001 (OpenZFS 2.4.4, block cloning enabled) `cp -a --reflink=always` of the 7.6k-file tree read 111 MB from disk per candidate even with a 1 GiB ARC (block-cloned files miss the source's ARC entries) and took 8.2 s per candidate against 6.0 s on the current btrfs snapshots; the new inodes also defeat a primed git index.
  * **Change.** `detect()` logs a WARNING (once) when the root is a ZFS dataset and the consumer asks for `clone_tree`; consumers that need trees are told to use `COWTREE_MODE=off` (plain copy, no cache hazard) until COW-BL-07 exists; the three documents state the measured cost instead of "uses the reflink backend".
  * **Closes when.** The warning exists with a FakeOps test (ZFS magic in `statfs`), and the three documents carry the measured numbers with a link to the report.
