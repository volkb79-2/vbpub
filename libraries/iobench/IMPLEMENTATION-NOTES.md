## Deviations, assumptions and resolved items (no BLOCKED id remains)

* RESOLVED by ruling (SPEC now says 282.8 / 312.4 GiB) - was: IOB-CAL-01 (numbers): the oracle text gives the densification rungs for the 270 GiB cliff scenario as 299.3 and
  322.7 GiB "log-equispaced between 256 and 345 GiB". Log-equispacing 256..345.04 GiB with two interior points gives 282.8 and 312.4 GiB
  (299.3/322.7 correspond to log-thirds between about 277 and 348 GiB, not to the stated bounds). Implemented the stated RULE
  (`plan.densification_rungs`); the test asserts 282.8 / 312.4. Controller: either fix the numbers in SPEC or tell me the intended bounds.
* RESOLVED by ruling (SHP-04 wins; PLA-11 text aligned) - IOB-SHP-04 vs IOB-PLA-11 (poor fit): SHP-04 says model keys are `absent` (stage_failed-style) with `unproven: shape_fit_poor` for the
  dependent QoS; PLA-11 says "model keys unproven: shape_fit_poor". Implemented SHP-04 (model keys absent: stage_failed; QoS `max`
  unproven: shape_fit_poor); the PLA-11 check is recorded as `fail` with `degrades: [iocost_model, iocost_qos]`.
* IOB-CAL-06 says "sequential 1 MiB QD16 cell of S6", IOB-SHP-01 says every S6 cell runs at QD32. Implemented SHP-01 (QD32); the
  sequential 1 MiB QD32 rewrite cell is the BPS basis.
* IOB-SHP-01 anchors: "anchors repeated at start, middle and end" is costed in the section-15 table as 60 s of anchor repeats. Implemented:
  the four anchors are measured first (inside the 22 cells), the two WRITE anchors are repeated at the middle and at the end as 15 s cells
  (4 x 15 s = 60 s); the read anchors are measured once. The repeated write anchors also feed `windows.write_seq1m_bps` (best/worst for
  R6 `max` when there is no ceiling history).
* Observation runs log at 1 s (the other jobs at 2 s) so that a 2 s burst is visible to `reduce_series`; the median smoothing would hide a
  one-sample burst. SER-01 allows <= 2 s.
* The fio `--io_size` with `--time_based`: SPEC dictates io_size as the byte cap. Whether fio stops at the earlier of runtime and io_size
  when `time_based` is set must be confirmed in the r1002 acceptance probe (P4); FakeFio implements "earlier of the two".
* Dry run (`--dry-run`) cannot measure S1: it uses `--assume-r-est` or the R_est READ from an existing calibration.json, else refuses
  (never invents a rate).
* The sweep REF cell runs the formula triple (R2, R3 candidate, R1), so "chosen triple's REF probe" (R4) is evidence about the proposal itself.
* File targets: `free` for `WS_max = min(size - fresh - tail, 0.85 x free - margin, ...)` is the space that was free BEFORE the file was
  preallocated (`fs.free + size`). Where a file-target cache is hit-like without a cliff the reason is `device_smaller_than_cache_margin`
  (IOB-TGT-10 text) instead of `no_cliff_hit_like_mode`.
* `check` ignores unknown KEYS but refuses a newer schema minor and an unknown major (IOB-RES-02; changed by the P3 review wave, B-B5).
* Reporting threshold for `mean_overstates` (PLA-04, info only): 1.10 x steady.

## Final state (IOB-03 P3)
All SPEC ids have a named test or are listed in `tests/probe_oracles.txt` (IOB-ACC-01, IOB-GATE-01, IOB-REL-01); `test_doc_01_ids_anchors` enforces it.
Branch coverage is 100 % over `src/iobench` with `host.py` and `__main__.py` omitted (`.coveragerc`). Nothing was run against a real device, gate, docker or the r1002 host.

Weak spots, for the reviewer:
* `host.py` (RealHost) is exercised only by the argv/sysfs guards and by the future r1002 probe (IOB-ACC-01); FakeHost parity is by construction, not by a shared contract test.
* CLI review cases (`docs/cli-review.toml`, 173) are GENERATED, not hand-reviewed: they were generated by running each candidate invocation on FakeHost and recording the observed exit and output markers; the
  rationale strings are templated per candidate kind. They pass the cli-extended surface check and audit, but they are not an independent semantic review.
* The FakeFio cache model is the oracle for every cache-state scenario; CCH-08 #1 is analytic (see deviation above), not a dynamic simulation.
* Wheel plus sha256 only (coordinator ruling: no zipapp; IOB-REL-01 is no longer blocked); `cmru release --dry-run` and `cmru status` were not run (probe).
* The estate venv is not touched: the surface/audit tools were run with `PYTHONPATH=src:../cli-extended/src` plus a scratch dist-info for the version.
* A focused pytest run needs `--cli-case-partial` (the cli-extended plugin otherwise demands every reviewed CLI case be collected); the gate runs strict.


Accepted deviation IOB-CCH-08 #1 (two_tier_e1_good_but_wrong): the FakeFio ladder reads [0, ws) of a sequentially filled device, so a two-tier model gives a RISING
ladder there and the dynamic simulator never produced E1 `good` with R_E1 >= +30 %. The fixture is therefore generated analytically from its header
parameters (ladder over the most recently written ws GiB) and fed to `cache.e1_fit` / `classify_cache` / `read_value`: E1 `good` (r2 0.977, leave-one-out 0.133),
R_E1 14.6k (+49 %), cap from R_cold. The SPEC rung list includes 324 GiB; with it the leave-one-out error is 0.158 > 0.15 and E1 is `poor`, so the header lists
the rungs without 324 (recorded in the fixture header).
Accepted deviation IOB-CCH-08 #2: `R = min(R_cold, R_E2)` (CCH-05) with `R_E2 = steady(QD32) x (1 - h2)` (CCH-03) yields ~7.3k, not the 9.8k the fixture text states, because the
largest rung mixes 77 % cache hits; the cap is conservative (<= R_cold). Asserted as 0.7..1.06 x 9.8k.
Resolved IOB-CCH-08 #5: was a logic flaw (a bare flat cap read as hit-like); fixed by `rate_cap` for any flat cold probe and the new `no_cache_observed` state (R-11).

Coordinator rulings applied (second commit): REL-01 wheel only; CAL-01 numbers 282.8/312.4 GiB (allotment sum unchanged); SHP-04 wins over PLA-11; CCH-08 #1 analytic and #2 range documented
