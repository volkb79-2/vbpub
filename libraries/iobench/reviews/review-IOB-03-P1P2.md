## BLOCKING

### B-1 The working-set plan, PLA-02 and the r1002 replay cannot all hold (SPEC:38, :42, :108, :182)
`IOB-CAL-01` caps the largest rung at `WS_max = min(0.85 x usable, R_est x fill_budget_s)` = 345 GiB on the 406 GiB r1002 vda7. But (a) the CAL-01 oracle lists rungs "... 256, 406" (406 > 345); (b) the CAL-05 replay oracle uses post-cliff rungs 300/350/400 GiB (350 and 400 are beyond `WS_max`); (c) the 14.2 example writes `extent_written [[0, 435852271616]]` (the whole device) although CAL-02 writes only `[0, WS_max)`; (d) `IOB-PLA-02` fails when the cap-basis rung is below `max(0.85 x usable, 1.2 x cliff)`. With the r1002 cliff at 300 GiB (`cliff_bytes` 322122547200 in the example), `1.2 x cliff` = 360 GiB > `WS_max` 345 GiB, so PLA-02 fails by construction on the one device the whole design was calibrated on; with `WS_max` taken literally the 3-point fit hypothesis the design hinges on (DG:54-61) cannot even be gathered (rungs 300, 331 midpoint, 345 only).
**Fix.** Pick one rule and derive the others from it: e.g. `WS_max = min(usable_less_reserved, R_est x fill_budget_s)` (usable already excludes the tail marker), and define the ladder to include the full-usable rung; state PLA-02 as `largest rung >= min(usable, max(0.85 x usable, 1.2 x cliff))`. Say in DG why 1.2 (IO-BENCH-01 report line 195 says `2 x cliff`, impossible when the cliff is 53 % of the device). Make the CAL-01 oracle assert the exact rung list for 406 GiB, and make the CAL-05 replay run through the planner, not a hand-fed list.

### B-2 No-cliff and short-ladder devices get no cap basis (SPEC:41, :43, :99, :211)
CAL-04 assigns `cached_tier`/`post_cliff` classes only relative to a detected cliff; with `cliff_bytes = null` the class is undefined. CAL-06 and DER-08 forbid `cached_tier` as a basis, and `cached_ref` is "median of the first three rungs", which for `quick` (a 3-rung ladder, SPEC:211) is the whole ladder, so no cliff can ever be found. Consequences: (a) a flat provider-capped disk without any cache (the gstammtisch 14 MB/s class, the headline use case) has no cliff and, if all rungs default to `cached_tier`, yields null proposals; if they default to `post_cliff`, a cache larger than the ladder is accepted as a basis, the opposite error; (b) the installer profile (`quick`, CONS:114) can never produce caps. The CAL-04 oracle names a "no cliff" scenario but asserts no consequence.
**Fix.** Define the no-cliff state explicitly: `cliff_not_observed` + largest rung >= the PLA-02 threshold => class `post_cliff`, `cap_basis` from the largest rung, `cache_proof: working-set`, flag `no_cliff_observed`; largest rung below the threshold => `cache_proof: none`, no basis, proposals null with reason. Say what `quick` yields (a labelled `budget-limited` result, or null caps) and add a CAL-04/06 oracle case per outcome (flat capped disk; uncached local disk; cache larger than the ladder).

### B-3 The cache-fit rule does not fail safe if the fit is wrong, degenerate or merely thin (SPEC:42-43, :116; DG:54-61)
What the SPEC says: fit `iops(ws) = R / (1 - C/ws)` on >= 3 post-cliff rungs; `good` iff `r2 >= 0.95`, >= 3 rungs, `C` in [0.1, 0.95] of the device; caps = `min(measured_largest, R_iops)` when good, else `measured_largest` plus `cache_residual_possible`.
1. **Three points, two parameters, one degree of freedom.** `1/iops` is linear in `1/ws`, so a 2-parameter fit on exactly 3 monotone points reaches `r2 >= 0.95` for almost any convex decreasing triple (I recomputed the r1002 rungs 300/350/400: R ~ 9.8k, C ~ 237 GiB, residual at the middle rung ~2 %). The `good` label therefore carries no evidence at the minimum count, and it is conferred at exactly the minimum count the standard plan produces. The oracle `..._poor_on_random_data` is not defined for 3 points.
2. **The model does not use `F`.** The text takes `F` = mean of the cached-tier rungs, then drops it from the formula. The model that matches the stated mechanism (a hit fraction `C/ws` served at `F`) is `1/iops = (C/ws)/F + (1 - C/ws)/R`, which for r1002 gives R ~ 11k, outside the oracle window [8.5k, 10.5k]. Either the formula or the window is wrong; choose and state which.
3. **Nothing bounds the fit.** The SPEC is silent when rungs are non-monotone, when `C >= smallest post-cliff ws` (log of a non-positive number), when `R` exceeds a measured rung, or when two rungs are equal. Each must be `poor`, never an exception or a number.
4. **A true plateau is reported as poor.** Post-cliff rungs that are flat within noise (no residual cache, the best case) fit `C ~ 0`, which fails "C within [0.1, 0.95]" and becomes `poor` => `cache_residual_possible`. The strongest cache-free evidence is flagged as the weakest.
5. **The failure branch is the unsafe branch.** `fit != good` => caps from `measured_largest`, the exact figure the model says can be 2.5x a cache-free rate (DG:58), flagged only at info level (PLA-10, SPEC:116). Info keeps `quality.plausible` true => `check` exit 0 (see B-4), so a consumer cannot tell "cache-free proven" from "cache residual possible" except by reading a flag the wizard contract (CHK-03) does not mention.
6. **BPS caps have no basis at all.** `cap_basis` is IOPS only (SPEC:43, :186). `RBPS`/`WBPS` (DER-04) then come from an unstated S6 cell and are not covered by the fit.
**Fix.** (a) Require >= 4 post-cliff rungs for `good`, or three plus a leave-one-out prediction within 15 % and `R <= min(measured post-cliff steady)` and `C < smallest post-cliff ws`; (b) add a state `plateau` (last two post-cliff rungs within 10 %) => cache-free observed, no flag; (c) fix the model equation and the oracle window together; (d) for `poor`/`insufficient`, either emit `confidence: cache-unverified` on `caps.*` and `S7` load points with a distinct `check` signal (B-4), or take the next-lower measured rung as the basis; never ship the unverified figure under the same label as a verified one; (e) state the BPS cap basis (the S6 sequential 1 MiB cell at the cap-basis set, with the ladder-derived `R/measured_largest` ratio applied, or an unconditional `cache_residual_possible`); (f) controlled-wrong oracles: non-monotone triple, flat plateau, C above the smallest rung, two-rung input, a 3-point random-noise triple (assert `poor`), and "fit wrong by 3x in R => caps still do not exceed the measured rate".

### B-4 `quality.plausible` and exit 0 collapse unverified results into "current and plausible" (SPEC:103-126, :144)
Real-world conditions that all land on `check` exit 0: a fully proven cache-free result; `cache_residual_possible` (PLA-10 info); `limited-by-budget` (PLA-02 "passes with that label"); a `quick` result with `budget-limited` proposals; `single-run` history (worst = best); `recalibrate_recommended`. Per CHK-03 the wizard takes the benchmark over the configured value "when check == 0" with no further qualifier. In the other direction exit 7 (`plausible == false`) is a single bit for the whole result: a poor `linear_model_fit` (PLA-11, affects the model keys only) or a sweep noise floor > 4 (PLA-12, affects the sweep only) would reject writeback proposals and caps that are perfectly valid. A check that cries wolf on a healthy result is switched off; one that certifies a budget-truncated figure issues a false certification (AGENTS: "a check is only as strong as what it compares").
**Fix.** (a) Make plausibility per proposal group: `quality.sections.{writeback,caps,iocost_model,iocost_qos}` each `{plausible, limits[]}`; each PLA check declares the groups it gates; `check --section S` returns the exit for that group; exit 7 only when the requested group is implicated. (b) Add `limits[]` to the `check --json` output (it already exists in `quality`), define `limited-by-budget`, `cache_residual_possible`, `quick-profile`, `single-run` as limits that keep exit 0 but make CHK-03 precedence "benchmark with limits => shown as a suggestion that needs operator confirmation", and extend the DOC-02 vocabulary check to them. (c) PLA-02 under `limited-by-budget` must be `info`, not `pass`. (d) Put the "real-world conditions per status" table itself in the SPEC (CHK-01 names `test_chk_01_status_collapse_audit` but the table is not here; an oracle that audits a table nobody wrote down cannot go red for a missing row).

### B-5 The S6 grid reads fresh (discarded) blocks, contradicting the core cache-proofing rule (SPEC:39, :66, :114)
SHP-01 defines `{read, write} x {rewrite, fresh}` cells. A read of a discarded extent is the zero-page read DG:50 cites as the reason to "read only data written by this calibration" (99.9k IOPS, [M r1002]), and PLA-08 makes any read of an unwritten extent a hard error. Either the `fresh` x `read` cells can never run (the grid has 20 impossible-or-forbidden cells) or the rule is violated. Also unstated: where the discard extent lives (it must be disjoint from `[0, WS_max)`, otherwise discarding it makes later ladder reads hit zero pages), how many bytes ~40 saturated 30-s cells consume (a fresh write cell at 1 GB/s needs 30 GB of never-written space per cell), and that blocks written by a fresh cell become non-fresh (extent map update).
**Fix.** Fresh cells for `write` only; state the discard extent location (inside the 15 % remainder above `WS_max`, excluding the tail), its size, its re-discard between cells, and the extent-map update; add an oracle that the grid plan contains no `read` x `fresh` cell and that no discard overlaps `[0, WS_max)` or the reserved tail.

### B-6 `--installer` weakens the destructive-operation guard; the tail-protection oracle covers fio only (SPEC:24-25, :44, :134; CONS:117)
IOB-CAL-07: `blkdiscard` runs "where the target is an iobench-marked device **(or `--installer`)**". Read literally, `--installer` alone authorizes a destructive discard without the marker/size/PARTUUID verification of IOB-TGT-04. IOB-TGT-03's oracle (and IOB-ARC-05's "fio only through builders") cover fio jobs; `blkdiscard`, fill, any mkfs or mount, and `wipefs` have no builder rule and no reserved-tail oracle. This is the one path in the SPEC that could plausibly write to something other than the verified target.
**Fix.** State: `--installer` relaxes only the live-host refusals of SAF-05; it never relaxes TGT-01..05. Delete "(or `--installer`)" from CAL-07. Extend ARC-05 to every device-touching subprocess (`blkdiscard`, `wipefs`, `mkfs`, `mount`) through typed builders; give the FakeHost device a reserved-tail model that raises on any write or discard (not only fio) overlapping the last 1 MiB; one oracle per writer type. Add `Host.write_range`/`discard_range` choke points that take the verified (devno, partuuid, size) and re-check the live values.

### B-7 The headline SER-02 oracle cannot pass under the SPEC's own algorithm (SPEC:31)
`test_ser_02_noisy_tail_knee`: 10 samples at 100000 then 30 alternating 16000/24000 "around 20000", expecting knee within +-10 s of 50 s. The rolling median (window 5) of a strictly alternating series is the majority value of each window: 16000 (-20 %) or 24000 (+20 %). Neither is within +-15 % of steady (20000), so "the first index after which the rolling median stays within +-15 %" never exists and the knee is `None`. The tail coefficient of variation is 0.20 (population) or 0.21 (sample), i.e. at the `unsteady` boundary of SER-03. The finding it protects (B-01: noise counted as burst) therefore has an oracle that is unsatisfiable (or silently flips to `unsteady`), so the implementer must bend either the algorithm or the test.
**Fix.** Make the scenario noise that the algorithm tolerates (e.g. +-10 % random about 20000, or the 16/24 alternation with a window-5 band of +-25 % and CV explicitly < 0.20), and state the exact expected `state`, `knee` and `burst_units`. Run the oracle numerically in the SPEC review before accepting it.

### S-2 Cache-proofing claims overreach (DG:43-52; SPEC:32, :40)
- `steady_certified` is true for `flat` (SPEC:32) while the same sentence says the reason "does not prove" a burst absence. A 30 s rung with a 5 s warm-up and a 7.5 s tail is ~3 samples; it certifies nothing about a token bucket longer than ~30 s, yet DG:49 lists token buckets as "defeated". The report's own seq write shows a ~430 s timescale (IO-BENCH-01 item 4c) that no `standard` rung can see (the 20-min tail run is `thorough` only).
- **Fix.** Record `observation_s` per rung and `quality.limits += ["bucket_exclusion_s<=N"]`; certify `flat` only above a stated duration; add one >= 5 min steady run at the cap-basis rung to `standard` (or label the result `short-observation`); reword DG row 3 to "bursts shorter than the rung".

### S-3 CAL-02 "in production, an error" is not implementable as worded (SPEC:39)
fio chooses the random offsets; the Host cannot intercept an unwritten read. What is enforceable is the argv: `offset + size` of every read job within the recorded written extent. Also unspecified: a fill that is cut short (budget skip, signal, provider slowdown; the report shows seq write varying 0.9-3.2 GB/s) must record the bytes actually written, not `[0, WS_max)`. **Fix.** Say "argv-level confinement + extent map = bytes confirmed written by fio's own report", and add the interrupted-fill oracle.

### S-4 PLA-07 and PLA-13 fire on a moving provider ceiling (SPEC:113, :119)
"Random 4 KiB bytes/s exceeds sequential by > 5 %" and "`fresh_iops > 1.5 x rewrite_iops` (impossible without a cache effect)" compare numbers measured minutes apart. DG:20 documents 18/16/14/6 MiB/s on one day on the target class; a drift between the two measurements fires both with no cache involved, and the message ("impossible without a cache effect") states a conclusion the comparison does not support. **Fix.** Measure the pair interleaved (A B A B), compare against the within-pair spread, and turn the result into `info` with `not_comparable: ceiling_moved` when the spread exceeds the threshold; construct the healthy "moving cap" scenario as the oracle's passing case (AGENTS: a refusal needs its legitimate state built first).

### S-5 `check` exit-code details (SPEC:143-144, :222)
- Exit 5 folds truncated JSON, an unknown major schema, EACCES and EIO. The actions differ (restore file, upgrade tool, fix permissions, check disk). Keep exit 5 but make `reasons[]` a closed vocabulary (`corrupt|schema_unsupported|unreadable|calibration_missing`) and add it to DOC-02's vocabulary list.
- Unspecified: a `result.json` whose `calibration_id` has no calibration file; a `failed` record (only `aborted` maps to 6); a good record plus a newer aborted one (should be exit 0 plus warning `last_run_aborted`); exit codes of `show` for absent/corrupt/stale files (CHK-02 only defines unknown section => 2).
- Exit 3 "identity mismatch" includes `kernel major.minor`, `root_source` and `fs.uuid` of the work-dir filesystem (RES-03). A kernel point release or re-mkfs of /bench invalidates a 30-75 min calibration of a raw disk whose behaviour did not change: a superset refusal. Either demote these to advisory warnings or document why each changes the measurement.
- The reverse collapse: on a virtio disk with `model: null, serial: null` (SPEC:162) "identity current" asserts only devno + partuuid + size; a provider-side move to another storage class keeps all three. Emit `identity_strength: weak` in the `check` JSON and document that `recalibrate_recommended` needs ceiling history that nothing populates until D-011.

### S-6 Derivation rules: gaps and shadowed facts
1. **R3 is not normative** (SPEC:94): "max_sectors_kb per DESIGN-GUIDE s5". The normative rule lives in the WHY document; move R3 text into the SPEC (the 10 ms constant is `[I]`; label it).
2. **R1 ratchet** (SPEC:92): the clamp "25 % of the kernel's effective dirty threshold" read from the live system on a host where host-setup already applied `vm.dirty_bytes = 16 MiB` yields a 4 MiB proposal on the next calibration, then the floor; each run lowers the next. Fix: derive the threshold from `vm.dirty_ratio` x available memory with `dirty_bytes` ignored (the journal records the originals), and record both.
3. **R1 order and negative argument**: R1 consumes the proposed `nr_requests` and `max_sectors_kb` (R2, R3 first: the CONS example does that) but the SPEC never says so; if `inflight >= W x R_drain` the clamp silently yields 4 MiB. Add the order and a flag `inflight_exceeds_budget`.
4. **R2 direction and resolution**: QD90 "at the largest rung" does not say read, write or both, and with QD in {1, 8, 32} (`thorough` adds 64) `2 x QD90` can only land on 8, 16 or 64. State the direction rule and that intermediate depths are untested.
5. **R5 basis versus R6 basis**: caps use `U x cap-basis steady ceiling`, the model uses the worst plateau. In the CONS example `WBPS 9800000` is above the model's `wbps 6291456` and above the worst plateau (6 MiB/s) it should protect against, so when the provider drops to the worst plateau the cap never binds. C-1 fixes U and "no per-tier caps"; the basis is open. State the basis choice and why (or use worst x U).
6. **`wbps` is defined twice** (SPEC:69 vs :96): SHP-04 `wbps = 1e9/c_byte` from the S6 fit; DER-05 `wbps = worst write plateau`. CEI plateaus from the benchmark come from the 4 KiB random ladder rung (CEI-05), so for a non-byte-metered device the "plateau_bps" is `iops x 4096`, not a bandwidth. Define the plateau workload per direction (sequential 1 MiB for `*bps`) and give DER-05 one rule per metering class.
7. **`max` (vrate)** is one number per device but DER-06 does not say which direction's best/worst applies; it must cover both: `max = ceil(110 x max(best_r/worst_r, best_w/worst_w))`.
8. **`single-run` fallback** (DER-05): "else the run's lowest steady window" substitutes a fact that does not exist (the worst observed plateau over time) with the run's own window; with a flat run that gives `min 100, max 110`. Fix: tag `iocost_model`/`iocost_qos` with a flag `worst_from_single_run` and cap `confidence` at `measured` (never `measured+confirmed`).
9. **Rounding of `rlat`** is unspecified (only `wlat` is rounded to 5 ms).
10. **Fresh/rewrite feeds nothing**: CAL-07 measures `fresh_penalty`, but no proposal consumes it other than the metering label; by DG:65 ("a stage nothing reads is not run") either derive something (e.g. a `fresh_write_penalty` note on `caps.dev_aggregate`) or drop the stage from `standard`.

### S-7 Metering detection does not use what the README and brief claim (SPEC:68; README:16)
Detection is "from flat bytes/s across IO sizes and seq vs rand, never assumed" but SHP-03 compares only across sizes (CV rules), never seq vs rand. Also: (a) `fresh-penalty` is one enum value with precedence over `byte`, so a byte-metered disk that also has a fresh penalty loses the byte classification and its `seqiops = randiops = bps/4096` rule; make `metering` and `fresh_penalty` independent fields; (b) with a moving cap (DG:20) the CV across 5 sizes measured at different minutes cannot reach <= 0.15; add an order-shuffled grid with repeated 4 KiB and 1 MiB anchors to estimate drift and return `undetermined: ceiling_moved`; (c) D-IOC Q4 says "asked only when undecidable"; the SPEC and CONS:86-93 have no `undetermined` handoff or typed override (`--metering byte|iops` stored as override); add both, and say what the model keys are when `metering == undetermined` and the fit is `good`.

### S-8 Budgets are not shown to fit, and the budget-limited outcome has holes (SPEC:50-53, :58, :83-85, :211-213)
- **`standard` does not fit ~30 min on the reference disk.** Using the SPEC's constants for r1002: fill 406 GiB at ~1.36 GB/s ~5 min; 11-12 rungs x 2 directions x 35 s ~13 min; QD1/QD8 at the largest rung ~2 min; fresh/rewrite ~1 min; S6 ~32 cells x 30 s ~16 min even with write-only fresh cells; S7 4 points x 2 directions (duration not specified) ~4 min; total ~40 min. Under SLO-04's priority order S6 and S7 are dropped first, so `standard` on its flagship disk yields null `iocost_model` shape and null QoS latency. `r1002 uses thorough` is decided, but the `standard` row (SPEC:211) and CONS:37 promise otherwise.
- **Fix.** Put a stage allotment table in the SPEC (seconds per stage as a share of the budget), a dry-run oracle that sums the allotments for the r1002 geometry and asserts <= budget with S6 and S7 included for `standard`, and give S7 a per-point duration. If it does not fit, state which stages `standard` drops and say so in CONS:37.
- `fill_budget_s` (SPEC:38) has no definition or default; `R_est` is measured by a buffered 20 s write in the work dir on a different partition (vda6) while the fill is a direct write to vda7 (SLO-01 says "work dir (or direct write to the target)"). Choose one and say what `R_est` bounds.
- SLO-02's `1.2 x R_est x stage_seconds` bound is tested only with a constant 14 MB/s scenario; the same document records a 3x variation of the provider rate within a day. Add the "actual rate 3x R_est" scenario and say what happens to the series (too few points => SER-01 raises) when the byte cap truncates a stage.
- **Honesty of budget-limited results.** `complete` is not defined in CAL-09 (all stages `ok`, or the required ones?): with S6 skipped for budget, is `calibration.json` written? Make the rule explicit: write it with the skipped stage recorded and dependent proposals null (DER-08), and set `quality.limits += ["stage_skipped:S6"]`. A ladder truncated before the cliff (not a slow-disk case, so SLO-03 does not apply) is not covered at all.
- **Matrix cell count and time**: SWP-01 lists up to five neighbours but enumerates six (dirty x2 and /2, nr_requests /2 and x2, max_sectors_kb each way); REF + 6 + REF = 8 cells, MAT-02 and the README/DG say 6 cells ("6-8" in DG:73). With 60-90 s cells and a <= 60 s gap, even 6 cells + S0 + S3 (60-90 s) + S5 exceed the 15 min bound at the stated maxima. Fix the count and make the oracle assert the worst-case sum.

### S-9 Safety on the target: smaller gaps (SPEC:22-26, :130-137)
- **Mount/mkfs lifecycle is undefined.** TGT-03/04, 14.4 and VM-01 mention an iobench-made ext4 (`fs_uuid`, "mkfs/mount"), CONS:110-115 passes a `--mount-dir` next to the same partition `target init` marked, and TGT-04 explicitly permits {marker, that ext4} as the signature set. Nothing says whether iobench ever runs `mkfs`/`mount`/`umount`, in which stage order, whether raw ladder writes may run while the ext4 is mounted (TGT-01 refuses a mounted device only for `target init`), or whether the journal records mounts for restore on abort. Coordinator context (vda6 work dir, vda7 raw) suggests the simple model: mount-dir is always a pre-existing fs on a different partition and iobench never creates a filesystem. If so, delete `fs_uuid`, the ext4 signature allowance and the VM mkfs/mount sentence; if not, specify the lifecycle and add raw-write refusal when the target (or a holder) is mounted at the time of every raw write stage.
- **Marker location contradiction**: CONS:19 says the marker is in the target's "first MiB"; SPEC:24 and :204 say the last 1 MiB. An operator following CONS and inspecting the first MiB will conclude there is no marker. Fix CONS.
- **No identity beyond size**: TGT-02 allows `--expect-partuuid` or `--expect-serial`; a whole-disk device with neither reports only its size. State that such a device is refused (FAIL), not accepted on size alone.
- **Restore can clobber a newer setting** (SAF-02, :131): "restore at the start of the next invocation if a journal exists". If host-setup or an operator changed the knob after the crash, the old `original` overwrites it. The journal holds `applied` too: restore a knob only if its current value equals `applied`; otherwise report `restore_skipped: changed_by_other` and drop the entry (exit 9 or a warning, say which).
- **Leaked work files**: a SIGKILLed run leaves multi-GB files in the work dir; the next run refuses because the dir is non-empty (TGT-05) and the free space stays consumed. Record created file names in the journal and have `restore` remove them.
- **Work-dir filesystem type**: TGT-05 checks free space but not type; a tmpfs/overlay work dir turns "3 x planned volume" into RAM on a live host. Refuse tmpfs/ramfs (and overlay unless `--installer`).
- **Work-dir disk vs target disk**: S3-S5 derive knobs from the work dir's disk and calibrations from the target; nothing requires they be the same physical disk (on r1002 vda6 and vda7 are). Add a check (same parent disk) or label the derivation cross-disk.
- **Namespace**: the mounted/swap checks read `/proc/self/mountinfo` and `/proc/swaps` of the caller's namespace (AGENTS: "never validate a namespace-translated path with a local filesystem call"). Compare with `/proc/1/mountinfo` and refuse when they differ, or document that iobench must run in the host namespace.
- **SAF-06**: `--protect-cgroup` and `--abort-psi` have no stated defaults; say that a live-host run without them is refused (not "abort disabled"), and that abort kills the child fio and waits for the device to quiesce before restoring.
- **SAF-05**: only containers are detected. Production workloads under systemd units (the wings/game servers) are not; `--confirm-quiet-window` is the only guard. Say so explicitly.

## Answers to the seven questions

1. **Oracles that can go red.** Mostly well formed (named tests, controlled-wrong cases for TGT, CHK, PLA). Not able to go red or not satisfiable as written: SER-02 (B-7), PLA-01 (S-1), PLA-03/04 (assertions of excluded inputs), PLA-15/16/18 (not runtime), LAT-02 (no fixture), DER-07 (inputs incomplete), DOC-01 (REL-01, GATE-01 have no test), CHK-01 collapse audit (table absent), VM-01 (no lane runs it). Hollow-risk oracles named without an assertion value: ARC-05, SER-05, SLO-01, SWP-01/02, MAT-02.
2. **Plausibility checks.** `cache_residual_possible` collapses {no cache, cache residual, thin 3-point fit, plateau mislabelled poor, budget truncation} into one info flag and exit 0 (B-3, B-4). Exit 0 hides `limits`; exit 7 is a global bit that a section-scoped failure (PLA-11/12) trips (B-4); exit 3 includes non-disk identity (kernel, root source, fs uuid); exit 5 folds four causes; 6 handles only `aborted`, not `failed`; `show` codes unspecified (S-5). PLA-07/13 fire on a moving ceiling (S-4); PLA-01/03/04/15/16/18 cannot fire or are not runtime checks (S-1).
3. **Cache-proofing.** The ladder, steady tail, written-only reads and flat-line detection are sound ideas; their claims overreach in three places: a `flat` 30 s rung is certified (S-2), reads of discarded blocks are in the grid (B-5), and the fit rule fails unsafe (B-3). The fresh/rewrite measurement is not consumed by any derivation (S-6.10).
4. **Derivation vs D-IOC-1..4.** min = 100 and max = 110 x best/worst, `wlat = 2 x p90` (round to 5 ms, [10, 50]), `rlat = 2 x p95` ([2, 20]), `rpct 95`/`wpct 90` match D-IOC-1/2/3, and D-IOC-4 is honoured by CONS:88. Gaps: which direction sets `max`; the single-run worst fallback; `wbps` double definition and a 4 KiB plateau used as a bandwidth; byte-metering detection ignores seq vs rand and has no `undetermined` handoff; the dirty-threshold ratchet; R3 not in the normative SPEC (S-6, S-7).

6. **Target safety.** The guard design (marker, size, PARTUUID, per-stage re-verify, never-overridable mounted/swap/root, `io.max` never written) is good. Remaining paths: `--installer` in CAL-07 and non-fio writers outside the tail oracle (B-6); undefined mount/mkfs lifecycle (S-9); restore overwriting a newer setting; leaked work files; tmpfs work dir; namespace of the mount check.
7. **Budgets.** `standard` does not fit ~30 min on the flagship disk with the SPEC's own constants (S-8); the skip rule is honest (`skipped: budget`, DER-08 nulls) but PLA-02 turns `limited-by-budget` into a pass and `check` shows exit 0 (B-4); `complete` is undefined (S-8); a 3-point fit is labelled `good` at the minimum rung count (B-3).
