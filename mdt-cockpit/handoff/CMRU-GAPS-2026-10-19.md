# cmru gaps found by MDTC-02 (to be filed into cmru's latest worktree during the release program)

Measured 2026-10-18/19 with the installed `cmru 6.1.1.dev579+g03c2f5bab` (`cmru --version`), against
Docker Hub (`docker.io/library/python`, `docker.io/library/node`) and `ghcr.io`. Nothing here was filed in
cmru; the evidence below is what to put in each item. Context: tester-base pins its `FROM` digest and
tester-unified pins a node stage digest, and the operator wanted the 14-day vetting buffer to come from
`cmru versions` instead of a hand-typed digest. The shape that works is documented in
`tester-base/cmru.toml` (rolling target on a literal patch tag).

## G1 - a rolling OCI target refuses while the tag's CURRENT digest is younger than the window

`[versions.targets."oci.python.314.trixie".oci] tag = "3.14-trixie"`, `selection = "rolling"`,
`constraint = "*"`, estate `age_window_days = 14`:

    [ERROR] CMRU versions: target 'oci.python.314.trixie' rolling OCI tag '3.14-trixie' is newer than the
    14-day age cutoff (2026-10-11T10:33:59Z > 2026-10-04T23:34:39Z)

The tag had moved to 3.14.8 seven days earlier; its previous digest (3.14.7, created 2026-09-19) was
already eligible. A rolling target can only judge the digest the tag points at now, so it cannot express
"the newest digest of this tag that is at least N days old" - the vetting buffer's actual meaning.

Wanted: for `selection = "rolling"`, fall back to the newest digest that satisfies the window (needs the
tag's history, e.g. the sibling immutable tags), or a documented way to declare it.

## G2 - a semver OCI target's record carries no digest

`tag = "{version}-trixie"`, `constraint = ">=3.14.7,<3.15"` resolved correctly to `3.14.7`, but
`versions/oci-images.json` has `image, tag, version, released_at, age_source, reason` and NO `digest`
(`versions.py` writes `digest` only when the candidate has one, which only rolling selection provides).
A Dockerfile pins by digest, so the record cannot be compared to the literal.

Wanted: record the index digest of the chosen tag for semver OCI targets too.

## G3 - semver enumeration fails on large repositories: `listed more than 5000 tags`

`tag = "{version}-trixie"`, `image = "docker.io/library/node"`, `constraint = ">=26.9.0,<27"`:

    [ERROR] CMRU versions: target 'oci.node.26.trixie': OCI registry listed more than 5000 tags for library/node

Wanted: filter by the tag template/prefix server-side or page with a bound derived from the template
instead of refusing; or make the limit a documented, configurable field.

## G4 - design constraint: Docker Hub allows 100 anonymous manifest pulls per hour per IP

`ratelimit-limit: 100;w=3600` (`docker-ratelimit-source` was this host's address). Every manifest GET AND
HEAD counts. `cmru versions` over a semver OCI target fetches a manifest per candidate tag (and per
platform for the age evidence), and this host shares one address with the other sessions and with
production pulls: the quota read `remaining=0` for about an hour (23:47-00:00) and every resolve and
`docker build` of a Docker Hub base failed with `429 Too Many Requests` meanwhile
(`docker buildx build ... failed to resolve source metadata ... 429`). A rolling target on a literal tag
costs one manifest request and worked at once when the quota returned.

Wanted: document it as a design constraint of OCI targets; support `token_env`/credentials by default
for Docker Hub; fetch the minimum (list tags, fetch only candidates inside the window); and cache.

## G5 - `oci-image-push` cannot push an already-built, tested image, and both handlers log in even for a local build

`cmd_oci_image_build` calls `_check_prerequisites()` and `_docker_login()` (requires `REGISTRY`,
`GITHUB_USERNAME`, `GITHUB_PUSH_PAT`) before `docker buildx bake --load`, so a purely local build needs
push credentials. `cmd_oci_image_push` runs `docker buildx bake --push`, which REBUILDS from floating inputs
(`apt-get update`, unpinned registries): the image that reaches the registry is not the one the gate
tested, and the registry digest differs from the tested image's. The session login also writes the
ambient docker credential store.

tester-base therefore ships a small project-owned release command (`tester-base/scripts/release_image.py`,
the cmru FEAT-02/KI-02 precedent that mdt-cockpit's `build-push.py` already follows): one build, the
tested image id recorded, `docker tag` of that image once cmru wrote `VERSION`, an isolated-config login
with the PAT on stdin, push `:latest` then `:<VERSION>` last, and a served-digest check.

Wanted: an `oci-image-push` mode that pushes an existing local image by name/id (`--image`, no rebuild),
verifies the registry digest, never logs in for `oci-image-build`, takes the credential on stdin into an
isolated config, refuses to overwrite an existing version tag, and documents the partial-publish outcome.
