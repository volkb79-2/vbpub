## Evidence

### 1. code_mode_only vs the gateway

- `tool_mode` is NOT a `config.toml` key. Neither `~/.codex2/config.toml` nor `~/.codex-opendesign/config.toml` contains it
  (key names printed: `model`, `model_provider`, `model_catalog_json`, `model_providers.opendesign.{name,base_url,env_key,wire_api}`,
  `web_search`, `model_reasoning_effort`, `sandbox_mode`, `approval_policy`, `sqlite_home`, `projects.*`, `tui.*`).
  It is a per-model field in the model catalog.
- Route `~/.codex2` (OpenAI account, gpt-6-luna): `~/.codex2/models_cache.json` has `tool_mode = "code_mode_only"` for all 8
  models. So on the OpenAI route code mode is the ONLY tool interface, and the companion is mandatory there.
- Route `~/.codex-opendesign`: `model_catalog_json` points to `~/.codex-opendesign/catalog/opendesign-models.json` (14 models),
  generated by `catalog/gen-catalog.py` from `catalog/template.json`. The template has `"tool_mode": "code_mode_only"`
  (template.json:98); `gen-catalog.py:63-67` overrides it with `tool_mode=None` and records the measurement ("code mode FAILS - the
  model's `exec` call arrives with a payload Codex rejects (incompatible payload)"). All 14 generated entries have `tool_mode: null`
  and `shell_type: unified_exec`, `apply_patch_tool_type: freeform`. The string "incompatible payload" is present in the
  codex 0.167.0 binary, consistent with the report.
- So on the gateway route code mode is already OFF in the catalog; what `codex exec` does there is plain `unified_exec` shell +
  freeform `apply_patch`. The failure only returns if someone regenerates the catalog from the template, or points the gateway
  provider at an OpenAI-style catalog.
- Guard status: `codex/codex-impl.sh` (controller tooling in the release-program dir, not in the repo) only has a comment
  ("do NOT enable tool_mode code_mode_only there"); nothing refuses or warns. `gen-catalog.py` has no assertion.

### 3. Packaging

- `install_ai_cli_tools.py:178-185`: `install_codex` = `staged_version("CODEX_VER")` + `npm install -g @openai/codex@<ver>`.
  Nothing after it checks anything (compare `install_opencode`, lines 333-347, which does `require_file` + `require_command`).
- Installed layout (this devcontainer, `/opt/mdt/npm`):
  - `/opt/mdt/npm/bin/codex` -> `../lib/node_modules/@openai/codex/bin/codex.js` (node launcher; `execve`s the native binary).
  - Native payload: `@openai/codex/node_modules/@openai/codex-linux-x64/vendor/x86_64-unknown-linux-musl/`
    with `bin/codex` (320 MB), `bin/codex-code-mode-host` (79 MB), `codex-path/rg`, `codex-resources/{bwrap,voice/...}`,
    and `codex-package.json` (`layoutVersion: 1`, `entrypoint: bin/codex`, `resourcesDir`, `pathDir`).
  - The platform package arrives as an `optionalDependency` alias (`@openai/codex-linux-x64`). If optionals are omitted,
    `codex.js` fails at run time with "Missing optional dependency ... Reinstall Codex".
  - `codex-code-mode-host` is NOT on PATH and not in `/usr/local/bin` or `/opt/mdt/bin`. Codex works anyway (reporter: code
    mode works), so Codex finds it beside its own binary in the vendor `bin/`. I did not run Codex, so the lookup rule itself is
    inferred (the binary contains the name; `scripts/codex/codex-unify.sh:43` pgreps for a running `codex-code-mode-host`,
    confirming Codex spawns it as a process).
- Where "the top-level path the installer expects" comes from: `install_binaries_from_archive` (installer lines 128-138) and its
  tests (`test_install_ai_cli_tools.py:70-93`, destination `usr/local/bin/codex-code-mode-host`) plus the report. Production
  never calls that function (`git grep`: only the tests use it; `find_binary`/`install_binary_from_archive` remain for
  Antigravity). Staging no longer verifies a Codex archive either: `stage_tool_artifacts.py:592-605` only resolves a version
  number (from the GitHub release tag, not npm); the companion check (`expected_companion_binaries`) now exists only for rga
  (line 1385).
- History: `ad46d4fa1` ("baseline fork", the first commit of this tree) already has the npm install. The MDT-P01 archive flow
  (`0a4c999b`) belonged to the legacy predecessor project and was never the behaviour of this tree. The
  report was copied in stale.
- `MDT-P01-REPORT.md`: line 9 "Stage and install `codex` plus `codex-code-mode-host`: Pass", line 10 "Preserve upstream Codex
  checksum verification: Pass" (npm integrity is the only check now), line 11 "Fail clearly for corrupt or incomplete Codex
  packages: Pass" (nothing does), lines 22-25 "extracts it once and copies both runtime executables to `/usr/local/bin`".
  Rows 12-13 (`opencode-ai`) are also out of date (platform package, and `@opencode/cli` locally). Only
  `CHANGES.md:821` and the MDT-P01 handoff files still repeat it.

  `Dockerfile:1146-1150`, `echo "codex=$(codex --version 2>&1 | head -1)"`. That never fails, so an image with a broken Codex
  (missing platform package, missing companion) still builds and records an error string as the "version".

- User-update interaction (`DESIGN-GUIDE.md:558`, `README.md:225`): `codex update` and `npm install -g @openai/codex@latest`
  rewrite the whole `/opt/mdt/npm` Codex tree. A companion copied to `/opt/mdt/bin` or `/usr/local/bin` would NOT be updated, so

- Same pattern elsewhere: `nyxloom/infra/agent-cli/Dockerfile:60` installs `@openai/codex@0.145.0` (and the `opencode-ai`
  meta-package that mdt-cockpit moved away from) with plain `npm install -g` and no verification. `tester-unified` does not
  install Codex at all (no hits), so the operator's `tester-unified:local` result does not bear on this.

## Is there something we should do for our image? Yes, but small, and it needs no copy of the companion

The image is not broken: the companion ships inside the npm package, next to `codex`, and Codex finds it. The real defects are
(a) nothing verifies it, so a future Codex layout change or an `--omit=optional` build would ship silently broken, (b) the
tests and report describe a flow that no longer exists, so they give false assurance.
