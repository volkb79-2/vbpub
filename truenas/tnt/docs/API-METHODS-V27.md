# TrueNAS v27 API method evidence

This file records the API contract used by the v27 adapter and core workflows. The reference was checked against the
official [TrueNAS API v27.0 method reference](https://api.truenas.com/v27.0/api_methods.html) and the matching middleware
source branch `release/27.0.0-RC.1`, commit
[`d83c3bf89aa4226c8fd1ef25dd273bdf447eb777`](https://github.com/truenas/middleware/commit/d83c3bf89aa4226c8fd1ef25dd273bdf447eb777).
Source links below use that immutable commit. The API model files define the websocket argument and result schemas;
plugin files expose the corresponding methods. `query(filters, options)` and `get_instance(id)` are the standard
middleware CRUD reads for the relevant service.

## v27 adapter contract

[`src/tnt/adapters/v27.py`](../src/tnt/adapters/v27.py) is the exact supported callable allow-list. A method is not
accepted as a read because its name ends in `.query`, `.details`, or `get_instance`; every read, write, and destructive
method has an explicit manifest entry. Guard-only entries marked `supported = false` are classification evidence,
not callable methods.

At connection time tnt obtains the method-name mapping with `core.get_methods(service=None, target="WS")`, then
compares it with the supported manifest and checks every subsequent call against that live set. This is a presence
check: `core.get_methods` metadata does not establish that the current user has the method's required role, that a
method's result matches the documented schema, or that a call will succeed. RBAC refusal and malformed data remain
errors; tnt does not turn either into empty or zero-valued state. The copyable check is
[`tnt doctor --online`](CONSUMERS.md#check-a-hosts-v27-methods).

The pool method names follow the v27 index exactly. There is no callable `pool.delete` and no callable `pool.scrub`
method: `pool.scrub` is a namespace. `pool.export(id, options={destroy: bool})` is the pool export method, and its
`destroy` option is destructive. Scrub scheduling and execution use `pool.scrub.query`, `pool.scrub.create`,
`pool.scrub.update`, `pool.scrub.delete(id_)`, `pool.scrub.run(name, threshold=35)`, and
`pool.scrub.scrub(name, action="START" | "STOP" | "PAUSE")`. The last two take a pool name; `pool.scrub.delete`
takes a scrub schedule ID. `pool.scrub.run` and `.scrub` are deprecated in v27 in favor of `zpool.scrub.run`, which
this release does not expose. These shapes and classifications were checked against the API method pages and pinned
v27 middleware sources linked below.

## Iteration 2 read-view contract (implemented against the verified v27 reference)

The It2 overview screens use only the listed reads. A method must appear in both this evidence and the v27 adapter
manifest before a view calls it. A presence match in `core.get_methods` does not grant the required RBAC role; server
permission errors remain visible errors rather than empty or healthy results.

The shared Textual read-view shell provides status, search, refresh, help, copy, and a sanitized error panel; a failed
refresh retains the last successful sample and timestamp. The CLI read commands support `--json`. Job progress/log/error
data is scrubbed before display, callbacks are bounded, and each applied job call records the remote job ID, state, and
session generation in its result. If an apply stops partway through, every planned call is reported as completed,
failed, unknown, submitted, or not started; the partial result is returned with a nonzero CLI status and the TUI asks
the operator to inspect current host state before planning recovery.

The pinned synchronous client returns a job handle with an ID, completion event, callback updates, and result. tnt waits
for completion in its worker thread after the guarded RPC call lock is released. Session changes stop local waiting and
drain the worker before closing that connection; this does not abort the remote job. Although v27 defines
[`core.job_abort(id)`](https://api.truenas.com/v27.0/api_methods_core.job_abort.html), the read-only Jobs view does not
call it or present remote-abort controls.

viewer. tnt therefore exposes only audit entries.

The `system.reboot` reference page omits the argument details in its rendered body; its exact request schema and job
behavior above were checked in the immutable v27 `SystemRebootArgs`/`SystemRebootOptions` model and lifecycle plugin.
The `update.status` candidate schema does not include its train. tnt therefore calls `update.available_versions` and
requires exactly one row whose version, manifest, release notes, and release-notes URL match the candidate returned by
`update.status`; zero or multiple matches refuse the update. `core.get_jobs` returns all sessions' jobs only to
`FULL_ADMIN` and filters to the caller's own jobs otherwise, so tnt verifies `auth.me.privilege.roles` contains
`FULL_ADMIN` before showing a complete system preflight. The same preflight lists running VMs, containers, and the
active SMB-session count; running jobs block the plan unless `--force-with-jobs` is explicit.

`system.reboot`, `system.shutdown`, and `update.run` are destructive-class operations with typed host or target-version
confirmation. Configuration export is limited by the adapter guard to `core.download` invoking `config.save` with
`secretseed=true`, a local `.tar` filename, and no buffering; the one-time URL is never printed. The downloaded tar
includes TrueNAS's secret seed, so tnt creates a new local file exclusively with mode `0600` and refuses overwrite.

`vm.get_console(id)` returns a non-empty console connection string or command (the VM ID/name form in middleware),
not a host/port object. VNC/SPICE endpoints come from `vm.get_display_devices(id)`: display attributes include
`bind`, `port` (VNC/SPICE, `null` for auto-assignment), and `web_port` (`null` for auto-assignment). The result also
includes `password_configured`. `vm.get_display_web_uri(id, host="", options={protocol: "HTTP"})` returns
`{error, uri}` for the web console. tnt displays the bind/port endpoints and the API URI while omitting password
material. See the [v27 display device schema](https://github.com/truenas/middleware/blob/d83c3bf89aa4226c8fd1ef25dd273bdf447eb777/src/middlewared/middlewared/api/v27_0_0/vm_device.py),
[display service](https://github.com/truenas/middleware/blob/d83c3bf89aa4226c8fd1ef25dd273bdf447eb777/src/middlewared/middlewared/plugins/vm/vm_display_info.py),
and [URI builder](https://github.com/truenas/middleware/blob/d83c3bf89aa4226c8fd1ef25dd273bdf447eb777/src/middlewared/middlewared/utils/libvirt/display.py).

## Guard-only names

These names receive an explicit destructive classification in the manifest/policy but are not enabled as v27 RPCs:

| Method | Evidence and status |
|---|---|
| `container.restart` | No restart method appears in the [v27 method index](https://api.truenas.com/v27.0/api_methods.html) or the v27 [container schema](https://github.com/truenas/middleware/blob/d83c3bf89aa4226c8fd1ef25dd273bdf447eb777/src/middlewared/middlewared/api/v27_0_0/container.py). The workflow is stop then start; the stop is destructive and needs typed confirmation. |
| `pool.dataset.destroy_snapshots` | The v27 schema still defines `PoolDatasetDestroySnapshotsArgs`, but there is no public `@api_method` implementation and the name is absent from the [v27 method index](https://api.truenas.com/v27.0/api_methods.html). It is classified destructive and remains unsupported. |
| `app.uninstall`, `filesystem.rmdir`, `filesystem.unlink`, `filesystem.remove` | These names are classified destructive and are not present in the [v27 method index](https://api.truenas.com/v27.0/api_methods.html); they remain unsupported. |

The v27 container schema has no image field on `ContainerEntry` and no memory limit in `ContainerCreate`/`ContainerUpdate`; its create input contains an image selector and its event metrics schema reports current memory usage. The current image and a configurable memory limit therefore cannot be read or changed through the verified container CRUD contract. `container.create` accepts `cpuset`, but no container CPU-count field. The workflow must expose only the verified fields and identify those unavailable values clearly.

`pool.scrub.delete(id_: int)` deletes a scrub schedule by schedule ID; it does not take a pool ID. `pool.scrub.run(name: str, threshold: int=35)` and `pool.scrub.scrub(name: str, action="START" | "STOP" | "PAUSE")` take a pool name. See the [v27 scrub schemas](https://github.com/truenas/middleware/blob/d83c3bf89aa4226c8fd1ef25dd273bdf447eb777/src/middlewared/middlewared/api/v27_0_0/pool_scrub.py) and [service](https://github.com/truenas/middleware/blob/d83c3bf89aa4226c8fd1ef25dd273bdf447eb777/src/middlewared/middlewared/plugins/pool_/scrub.py). This is why `pool.scrub.delete` task IDs are not resolved as pool references.
