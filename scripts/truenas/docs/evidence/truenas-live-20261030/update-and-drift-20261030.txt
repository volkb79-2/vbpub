Q1 UPDATE MECHANICS
-------------------
The v27 RC.1 installation changed middleware Python files under
/usr/lib/python3/dist-packages/middlewared/ and the adapter helper modules
under that same Python package tree. Those files are in
boot-pool/ROOT/<BE>/usr, a per-boot-environment ZFS dataset. v1001 reports
/usr mounted read-only, with the active dataset property readonly=on; it is
not mounted from a live SquashFS filesystem. The update payload contains
rootfs.squashfs, which the updater verifies and extracts into the new BE.

The RC.1 marker <home> is in the
boot-pool/ROOT/<BE>/root dataset. Before the update it identified version
27.0.0-RC.1 and bundle 23e7667f4893f26f4861b17edc20e73f00ae2f8b797f9ff95cde446af1f25de1.
The update created and activated boot-pool/ROOT/27.0.0-MASTER-20261027-173422
with a new /usr dataset containing the nightly's unpatched stock hashes. It
also copied the BE's /root dataset, including the RC.1 marker, into the new
BE. The marker therefore survived but was stale: it described the previous
/usr contents, not the new BE. The active /data/freenas-v1.db belongs to that
BE's /data child dataset and was migrated by the update.

The old RC.1 BE remained listed with can_activate=true and retained its own
patched /usr and marker. It was booted successfully during the rollback
acceptance, then the target nightly was reactivated. This is an actual rollback
boot, not only a boot-environment API claim. Per-BE database files are separate
and have distinct hashes before/after migration; pool datasets outside
boot-pool/ROOT (Path A boot-pool/user-data and Path B boot-disk-data) remain
outside each BE and retained planted bytes, snapshots, clones, properties and
zvol contents. Boot-time mounting of those pools is middleware behavior and
can change with the selected BE.

Q2 DRIFT AND FAIL-CLOSED COMPATIBILITY
--------------------------------------
The supported builds are exact strings in scripts/truenas/boot-pool-patch/
supported-builds.json: v27 RC.1, v27 nightly 27.0.0-MASTER+20261027-173422,
v28 nightly 28.0.0-MASTER+20261014-230204, and v28 nightly
28.0.0-MASTER+20261027-175229. There is no registered v27 RC.2, v27 GA or
later nightly adapter.

Before apply, each adapter checks exact version, adapter/registry metadata,
full target path set and SHA-256 preimage hashes, then performs patch
--dry-run --fuzz=0. Missing, extra, symlinked or changed target files and any
anchor mismatch fail with a per-path diff. Apply is transactional; post-apply
checks validate output hashes, Python compilation, API probes, reverse zero-
fuzz patch dry-runs and restore /usr readonly=on. The recovery/reapply path
also requires the exact prior marker digest and the complete new-build stock
fingerprint set. This prevents version-prefix-only acceptance and fuzzy hunk
relocation.

Read-only commands are implemented by patch_drift.py: verify for one exact
registered extracted source tree, diagnose for an unknown candidate tree, and
upstream for official version listings plus current upstream middleware and
truenas_pylibvirt source anchors. The latter does not install anything on
v1001. When the official download listing is JavaScript-only, it uses PWMCP to
read rendered object names. The official v27 Nightlies listing reported
TrueNAS-27.0.0-MASTER+20261029-173417.iso, newer than the Oct 27 adapter and
unsupported. The v27 RC listing was not re-inspected: PWMCP's selector timed
out. The updater API advertised 28.0.0-MASTER+20261029-175210, and the live
lane rejected the older Oct 27 request before installing that exact Oct 29
build. The v28 rendered listing failed with HTTP 503. Neither Oct 29 build has
an adapter. Current upstream source differs from the pinned adapter targets
and reports REVIEW_REQUIRED; that is a source drift signal, not proof of the
exact ISO's installed file bytes. A new build requires extracted ISO or
package fingerprints and review before it can be registered.

Evidence: patch-drift-27-nightlies-20261030.log,
patch-drift-27-rc-20261030.log, patch-drift-28-nightlies-20261030.log,
patch-drift-upstream-20261030.log, v28-rejected-stale-oct27-target-20261030.log;
the exact per-BE target hashes above; the registry and per-adapter
`targets.sha256` files are in the checkout.

Q4 UPDATE-SURVIVAL ACCEPTANCE
----------------------------
Registered lanes live-update-survival-plant, live-update-survival-update and
live-update-survival-verify use midclt/WebSocket, direct ZFS properties and
SHA-256 file/zvol reads. They plant a unique group and user, hashed password
expectation, SSH key, API key digest, nested datasets with quota/refquota and
compression, snapshot/clone, zvol, disabled SMB/NFS records, cron/snapshot/
replication tasks, stopped container record when available, stopped VM and
device records, local certificate, and pre/post network/system configuration
and app/cloud-sync inventories. No guest VM is booted. Password and API
secrets are represented by digests only.

Vanilla v27 RC.1 -> v27 nightly: PASS. It planted Path A plus an ordinary
non-reserved pool on /dev/vda4; Path B was unavailable in that host setup.
The post-update verifier passed with seven data checksums and four explicit
expected differences. Logs: vanilla-plant-20261030.log,
vanilla-update-20261030.log, vanilla-verify-20261030.log.

the only free tail partition and left no separate non-reserved pool. The final verifier passed with seven data checksums, nine expected
differences, and no unexpected changes. Evidence: `patched-survival-
verify-20261030.log`; per-BE hashes and the observed Path A zvol reservation
