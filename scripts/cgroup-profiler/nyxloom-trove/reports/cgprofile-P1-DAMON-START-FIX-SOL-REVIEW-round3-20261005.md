## Blocking findings

**N1 — high — resizing the global kdamond array deletes stopped foreign monitors' configuration.** `lib/damon.py:314-366` reserves capacity by growing `nr_kdamonds` even when the baseline is nonzero; `lib/damon.py:410-445` restores that baseline with another count write after checking that all slots, including foreign ones, are `off`. A bare one-shot session has the same issue at `lib/damon.py:604-615,755-763`. The upstream Linux v7.1 [DAMON sysfs count-write implementation](https://github.com/torvalds/linux/blob/v7.1/mm/damon/sysfs.c#L1909-L1945) first refuses if *any* monitor is running, but on a successful write `damon_sysfs_kdamonds_add_dirs()` calls `damon_sysfs_kdamonds_rm_dirs()` unconditionally, then allocates fresh kdamond/context directories. Thus an existing foreign monitor at index 0 with `state=off` and configured context, targets, intervals or schemes is destroyed by the pool's first reservation; restoring the numeric baseline does not restore that configuration. A foreign owner can no longer start the monitor it had staged. This contradicts RW-442's explicit “never stop or delete foreign slots,” `lib/damon.py:242-248`, and `docs/DESIGN-GUIDE.md:228-236`. An intervening external count rewrite while all owned monitors are off can also replace pool-owned objects without changing the count, so count/state alone do not establish object identity or exclusive ownership on later reuse/close (`lib/damon.py:284-288,388-403,475-489`). The test `tests/test_damon.py:947-956` asserts only count and `state=off`; its fake's `create_kdamond` and `_write_int` (`tests/test_damon.py:57-70,153-165`) never remove/recreate existing contexts or configuration. It therefore accepts a destructive transition that Linux actually performs. Do not resize this shared array across foreign stopped slots without an ownership protocol that preserves their actual configuration; add a fake/state-transition oracle that makes foreign context loss observable. Refusing optional DAMON is safer than silently erasing another owner's setup.

**N2 — high — one-shot runtime DAMON collection failure still terminates ordinary profiling.** The new `cgprofile.py:441-457` handler degrades an optional DAMON *startup* failure and reaches READY, but `cgprofile.py:464-474` calls `damon_session.collect()` on sample zero and every twentieth sample without a failure boundary. A sysfs `OSError` or DAMON read/classification error escapes through `lib/sampler.py:295-300`, leaving `cmd_collect` before its normal manifest/DONE path (`cgprofile.py:495-503`). `ExitStack` closes DAMON, but it does not resume cgroup/CPU/memory sampling. `tests/test_cgprofile.py:1127-1157` covers construction/entry refusal only, and the successful-collection test does not inject a late failure. The daemon path does catch recommit and collect exceptions and continues recording ordinary samples (`lib/serve.py:1397-1404,1426-1430,1459-1473`), so this is specifically a one-shot caller gap. The wrapper can still launch the measured command (`cgprofile.py:770-813`), but that does not make a prematurely dead collector or missing finished series compliant with the DAMON-optional profiling rule (`README.md:71-79`, `docs/CONSUMERS.md:42-49`, `docs/DESIGN-GUIDE.md:247-252`). Catch a runtime DAMON failure around collection, disable/close only DAMON, and demonstrate subsequent ordinary samples plus normal DONE/manifest completion with a failing-then-later-tick test.
