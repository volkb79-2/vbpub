## ABI and proposed fix

The central ordering change is correct. The [kernel DAMON usage example](https://docs.kernel.org/6.19/admin-guide/mm/damon/usage.html) writes the context/target sysfs inputs before `state=on`. Current upstream [`damon_sysfs_commit_input()`](https://github.com/torvalds/linux/blob/master/mm/damon/sysfs.c#L2003-L2024) checks that the kdamond is running and returns `-EINVAL` otherwise; [`damon_sysfs_turn_damon_on()`](https://github.com/torvalds/linux/blob/master/mm/damon/sysfs.c#L2113-L2142) builds a context from the already-written inputs and starts it. In `lib/damon.py:457-483`, context, operation, intervals, initial targets, and `stat` scheme are written before `kdamond_on`, with no offline commit. `lib/damon.py:522-555` still uses `kdamond_commit` for an entered vaddr session's live target update. This source review does **not** establish that this host kernel accepts the complete configuration or produces DAMON samples.

## Blocking findings

**B1 — high — a reused pooled index can start with targets from an earlier session.** At `lib/damon.py:441-468`, pool acquisition can return a freed index while another session remains live. The reuse path calls `create_context` and `create_target` but never clears the old target array. The reused library's [`create_context` and `create_target`](../../../damon-analysis/lib/damon_analysis.py) are grow-only (`:147-153`, `:187-195`); when the index and target directories already exist, they do not rewrite `nr_contexts` or `nr_targets`. On the newly valid `state=on` path, [the kernel builds all configured targets](https://github.com/torvalds/linux/blob/master/mm/damon/sysfs.c#L1930-L1945), not just the pids in `self.targets`. Concrete case: session A on index 0 starts with PIDs `[10,20,30]`; session B keeps index 1 live; A stops; session C reuses index 0 with `[40]`. The sysfs target count remains three, so `on` tries `[40,20,30]`. If 20/30 still exist, C monitors unrelated processes; if either has exited, [`find_get_pid` returns `-EINVAL`](https://github.com/torvalds/linux/blob/master/mm/damon/sysfs.c#L1912-L1924) and C reports DAMON unavailable. `tests/test_damon.py:733-745` exercises reuse only with one target in both sessions, and its fake records target writes without retaining a target array, so it cannot see this defect. This behavior predates the six-file patch but becomes reachable when the corrected first `on` succeeds. **Minimal repair:** while the owned slot is off and before writing new PIDs, explicitly rebuild its sysfs target array to the new session's exact size, then write every PID and start. A write to [`nr_targets`](https://github.com/torvalds/linux/blob/master/mm/damon/sysfs.c#L324-L396) rebuilds its directories. Add a stateful fake case with A=`[10,20,30]`, B live, then C=`[40]` on A's index, asserting the kernel-facing target set is exactly `[40]`, B stays on, and final release respects the original baseline.

**B2 — high — online shrink keeps monitoring targets that left the session.** `lib/damon.py:522-555` rewrites only the leading `len(pids)` target slots; `SysfsInterface.create_target` does not reduce `nr_targets`. It then commits the entire sysfs array. For a live session whose set changes from `[10,20,30]` to `[11]`, the input remains `[11,20,30]`. If 20/30 remain alive outside the attributed subtree, the kernel keeps monitoring them; if they exit, context construction can return `EINVAL`, and `lib/serve.py:1353-1357,1381-1385,1403-1408` aborts the whole profiling session on that sampling tick. The test at `tests/test_damon.py:1149-1156` asserts the stale higher directories remain, but never checks the effective target set after commit; `test_recommit_targets_rewires_vaddr_targets_and_recommits` checks calls and `session.targets`, not the kernel-facing array. **Minimal repair:** make the sysfs target count match the requested nonempty PID list before the online commit (or use the documented obsolete-target protocol and reconstruct the directory array), then commit. Model the committed target set in the fake, test a live shrink with still-running removed PIDs, and test a disappearing PID/`EINVAL` path and its caller-visible outcome. Reconcile whether a late DAMON-only failure should degrade DAMON or abort the profiling session; that policy is not proved by this candidate.

## Other observations

- **S1 — low, documentation accuracy.** `CHANGES.md:17` says initial setup “starts with `state=on`”, although the fix's essential order is to write the attributes and targets first, then turn it on. `docs/DESIGN-GUIDE.md:225` says recommit is used “only for target changes,” but the token caller at `lib/serve.py:1381-1385` recommits at each discovery tick even when the set is unchanged. Clarify the changelog order and either guard the token caller on a changed PID set or describe the actual periodic behavior. CP-17's open status, pending live oracle, and backlog index link are consistent with the evidence.
- **Test scope.** The new fake correctly rejects offline commit with `EINVAL` (`tests/test_damon.py:103-111`), and the existing live-update test can now pass only while the fake state is `on` (`:1113-1124`). The initial-session test also observes `on` state and teardown (`:307-313`) and asserts no commit before `on` (`:351-366`). Those checks discriminate the original offline-commit bug. They do not model target-array contents, `on` input validation, or a caller-visible `start` result for an `OSError(EINVAL)` from `on`; B1/B2 are therefore false-green cases, not evidence that the ABI correction itself is wrong.
- **Error and ownership limits.** `DamonSession.__enter__` wraps ordinary sysfs exceptions as `DamonSessionError` (`lib/damon.py:484-500`); `lib/serve.py:1066-1084` reports initial failure as `unavailable:<reason>` and attempts teardown. The pool's live-index and baseline bookkeeping, plus the existing two-session tests, give static evidence that a failed initial start does not intentionally release another session's index. Teardown catches off/shrink failures, so a forced write failure can leave an off or unreleased placeholder; the candidate does not provide live kernel proof of cleanup or ownership after such a failure. No new regression in these paths was established from the deleted offline commit alone.
