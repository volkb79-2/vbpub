## Findings

**F1 — high, blocking — the pool's concurrent-session/reuse test constructs a state the kernel refuses.** The P1 C3 contract explicitly requires two concurrent sessions on indices 0 and 1 (`nyxloom-trove/reports/cgprofile-P1-DAEMON-HANDOFF.md:81-95`). `KdamondPool.acquire()` grows `nr_kdamonds` for the second slot (`lib/damon.py:279-295`; `../damon-analysis/lib/damon_analysis.py:72-78`) after the first session has already executed `state=on` (`lib/damon.py:489`). Upstream Linux v7.1 [`nr_kdamonds_store` and `damon_sysfs_kdamonds_add_dirs`](https://github.com/torvalds/linux/blob/v7.1/mm/damon/sysfs.c#L1923-L1944) refuse **any** count rewrite with `EBUSY` while any kdamond is running, including growth. The second start therefore becomes `unavailable:OSError ... EBUSY` through `lib/damon.py:490-506` and `lib/serve.py:1066-1070`, instead of a second live DAMON session. The modified `tests/test_damon.py:748-764` fake accepts that growth, so its A/B/C live-slot sequence proves exact target-array reset under a synthetic state but does not prove the promised live multiplexing or live pool reuse. This is an inherited pool design problem, exposed by reviewing the candidate's new reuse oracle; it remains a P1 contract failure. The host reports a 7.1.13 kernel, but this review did not inspect its Debian patches or perform a sysfs write. Resolve the kernel constraint or explicitly revise the concurrency contract and its user-facing docs before treating the pool scenario as accepted. `DESIGN.md:830-831` already warns that concurrent DAMON runs fight, while the P1 handoff and pool tests assert the opposite.

**F2 — high, blocking — failed DAMON stop is silently treated as successful release.** The new runtime degradation path detaches DAMON and calls `__exit__`, then reports it disabled (`lib/serve.py:1539-1566`). `DamonSession._teardown()` swallows every `kdamond_off` exception and still calls `pool.release()` (`lib/damon.py:588-603`). `release()` immediately puts that index in `_free`, or attempts a final shrink and clears ownership even if the shrink fails (`lib/damon.py:305-336`). A concrete kernel failure is `state=off` returning `EBUSY` when [`state_store` cannot acquire the sysfs lock](https://github.com/torvalds/linux/blob/v7.1/mm/damon/sysfs.c#L1793-L1812). In the currently reachable one-owned-slot case, the kernel refuses the attempted `nr_kdamonds` shrink while that monitor is running, but the pool forgets ownership and the monitor can outlive its session. If F1 is repaired to permit simultaneous owned slots, a failed-off slot would instead enter `_free` for reuse while still running; a later `state=on` on it is refused as busy. Ordinary profiling does continue, yet the claim that only DAMON was stopped/released is false. `tests/test_damon.py:534-540,604-612` explicitly expect release after a failed off; the new `tests/test_serve.py:2162,2192-2195,2261-2262` raises from a stub `__exit__` *after* incrementing its close counter, so it does not model a still-on kdamond. This behavior predates the diff but the candidate's new late-failure path and `CHANGES.md:17-21`/`docs/DESIGN-GUIDE.md:243-248` promise make it material to this repair. Cleanup needs to verify the slot is off (and retain/quarantine ownership when that cannot be proved) while preserving the ordinary profiling verdict; tests should model an off failure with a still-running monitor and subsequent acquisition/finalization.
