**Findings:**
- **P4-1 MAJOR (T1, brief :184).** CPython's `Future.set_result` wakes `wait()` inside the condition lock and only then runs `_invoke_callbacks()`. The main thread can therefore submit before the done-callback decrements the counter, so a correct implementation can record `jobs+1` under preemption.
  - Fix: decrement inside a wrapper around `fn` (in a `finally`), so the decrement happens before the future completes.
  - Also record the submitted positions and assert they equal `range(total)`.
- **P4-2 MAJOR (T3, :192-194).** Gating on "the runner returns" still leaves the git dirt check and snapshot teardown to run afterwards (mutation.py:2759-2808). Future 1 can finish after future 0, or both can land in one done batch, and then "emit on handling" still yields `[0,1,2]`.
  - Fix: release candidate 0 from an Event set by a wrapped `_write_mutation_state_record` when position 1 is handled (main thread).
  - Alternatively, extract the flush step as a pure function and test it directly.
- **P4-3 MAJOR.** Expiry and fatal semantics with `jobs ≥ 2` have no oracle. Add:
  - **T6:** `jobs=3`; position 1 raises LANE_TIMEOUT while 0 and 2 are held by Events. Expect results and state files for 0 and 2, events `[0,2]`, `submitted==3`, and the rest masked.
  - **T7:** a fatal at position 1 with 0 and 2 in flight. Expect state records for 0 and 2, nothing submitted past 2, and the fatal re-raised.
- **P4-4 MAJOR (:142).** "First fatal" depends on timing when `jobs > 1`, and the claim that only the reason can vary is false.
  - Worker fatals also include P22 `BUDGET_EXCEEDED/SNAPSHOT_LIMIT_EXCEEDED`, `MUTATION_DISCOVERY_FAILED` and kill-signal decode errors (mutation.py:2798-2808), so the lane's *outcome* can vary too.
  - Fix: drain all in-flight futures, then raise the lowest-position fatal among all observed. T4 should cover fatals arriving in different batches.
- **P4-5 MINOR (:129).** "At most `jobs-1` staged events" is false. Behind one long survivor, the other workers can complete any number of candidates, so the real bound is `total`.
  - Staged events are lost on a non-AssayError exit or SIGTERM while their state records exist. Fix: flush in a `finally`, ascending, skipping gaps.
- **P4-6 MINOR (:48).** The `:2316` early return guards the whole inventory. `_execute_mutation_jobs` receives `total=len(pending_jobs)` (`:2483`), which is 0 after a full resume, and today it still builds the executor (`:2893`). Say which behaviour is intended.
- **P4-7 MINOR.** T2 and T3 need a 3-candidate fixture. `_TARGETS` yields 5, and `_make_decide_by_mutated_content` raises on `e = False` (test_mutation_isolation.py:110-129).

**Findings:**
- **P6-1 BLOCKING.** Candidates still in flight when the lane or campaign deadline expires are classified and persisted.
  - `_run_attempt` caps the child at `deadline.remaining()` (mutation.py:2708-2713).
  - `TimeoutExpired` comes back as a *returned* `BUDGET_EXCEEDED/LANE_TIMEOUT` result (runner.py:~1224-1250), and the dirt-check expiry is absorbed (mutation.py:2761-2779).
  - The executor then writes a `budget_exceeded` record, and `--resume` replays it (mutation.py:1126 residual).
  - After the first invocation's 5 h budget, a resumed campaign can therefore never PASS, contrary to A-464 and D9. P6 forbids touching both the executor and `_run_attempt`, so the implementer cannot fix this.
  - Decide: a timeout that came from the lane remainder, not from `budget_per_candidate`, raises LANE_TIMEOUT (masked, no record). Assign an owner.
- **P6-2 MAJOR (Flow 5).** The post-runner check only covers a normal return. `LivenessHungExpired`, `TimeoutExpired` and `OSError` become returned results (runner.py:1224-1263), so a stall or timeout that coincides with termination becomes `hung` or `budget_exceeded` with a record. Fix: check `termination_requested()` on every exit path.
- **P6-3 MAJOR.** Non-liveness candidates can be misclassified as `killed`.
  - `timeout` sends SIGTERM to the whole process group, so a `default_process_runner` child can exit −15 and reach the worker's check before the main-thread handler sets `_TERMINATION`. It is then classified `killed` and recorded.
  - Decide: treat −SIGTERM/−SIGINT as unclassifiable (raise LANE_TIMEOUT), or run every candidate in a new session.
- **P6-4 MAJOR.** Signal-handler safety.
  - The registry is specified under a plain `threading.Lock`. If the signal lands while the main thread (the baseline `LivenessRunner`) holds it, the handler deadlocks.
  - A `print` from a handler can raise "reentrant call".
  - Both break "never raises". Use an `RLock` (or a non-blocking acquire with a fallback) and `os.write(2, …)`.
- **P6-5 MAJOR.** Missing proof for the coverage floor. O7 runs in a subprocess, and coverage is not configured for subprocesses (pyproject has only `[tool.coverage.report]`). The handler, registry and termination branches need in-process tests, with:
  - a reset fixture for the global Event;
  - a non-main-thread guard, since `signal.signal` raises ValueError off the main thread.
- **P6-6 MAJOR (conflicts with P9 and plan §9.3).** `init` refuses state records without a deadline file, but D7 and §9.3 step 4 import records before the first gated invocation, and `init` only runs inside the gate. Decide the order: an init-only gate mode, or accept records whose identity matches.

- **P6-8 MINOR.** Termination also trips the label-grace deadline (cli.py:1279). A SIGTERM before the HEAD read therefore exits 2 with no verdict. The decision table is silent on this.
- **P6-9 MINOR.** Gate-script details:

  - `timeout` exits 124, not 4, when it fires.
  - The outer 7h30m timeout cannot reach assay, because the inner `timeout` puts it in its own process group. Document that as a no-verdict failsafe.
