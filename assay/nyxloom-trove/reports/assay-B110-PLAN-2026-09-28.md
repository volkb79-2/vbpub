## 1. Goal and definition of done

**B105 is qualified when** one verifier-accepted `self-qualification` report exists for the final B105 tree. That report must have:
- R0 PASS;
- whole-target 100% line+branch R1;
- R2 PASS over the complete, unsharded candidate inventory, where every candidate is killed or has a ledger-audited `equivalent` disposition (A-465);
- the R3 canary with controls.

The report must pass `assay verify` and the extended `tools/b105_report_check.py`. It is produced inside `tester-unified` under the unchanged 3 CPU / 2 GiB / 8 GiB envelope. The run must also satisfy A-464:
- the measured plan projects ≤ 6 h;
- a persisted 8 h campaign deadline applies;
- hitting the deadline gives an incomplete infrastructure result, never a PASS;
- host load or elapsed time never classifies a candidate.

**B110 is done when:**
- packages P0–P8, the v14 integration branch and P7b (and P9/P10 as the screen result needs them) are merged, reviewed and gated;
- the §7 pilot has run and returned **Pilot GO** under §8.1;
- the screens (§9.1) and the ledger audit (§9.2) have reached **Qualifying GO** under §8.2;
- the §9.3 qualifying runbook is ready.

P11 is dispatched only after a Pilot NO-GO on the claim-preserving path and an operator decision.

## 2. Why the plan is shaped this way

Everything is sourced in the analysis report.
1. Every candidate ran the whole 5,831-test, coverage-instrumented suite in a fresh interpreter:
   - killed ≈ survived ≈ one baseline (~520–560 s);
   - the planner's 60 s fallback under-estimated the real cost about 9×;
   - spinning hangs cost 3 baselines each.
2. **A passing native R2 campaign contains only kills** (plus, after A-465, ledger-audited equivalents). Survivor cost belongs to a *non-qualifying* find-and-fix loop, not to the qualifying run.
3. A qualifying run's cost per candidate is roughly snapshot + interpreter start/collection + the declared-order prefix up to the first failing test. The cold witness (P3) and a tiered declared order (P1) cut the prefix. The snapshot changes (P5) cut the fixed cost. The work queue (P4) uses the 3 CPUs the gate already has.
4. Survivors and hangs must be driven to zero before the qualifying run:
   - screen → fix → ledger audit → qualify (§9);
   - loop guards (P2) turn spinning hangs into fast kills;
   - the dataclass contract test (P1) kills up to 148 flag flips cheaply.
5. The work must be distributable and async (§6). Evidence records are portable, fingerprinted and merge-checked. A consolidating `--resume` produces one ordinary verdict.

**D6 resolutions** (these replace the open list A1–A9):
- **A1 (placement):** a `witness-cold` execution has exactly `{mode, witness}` (Luna's review). Per-candidate proof lives in a new optional `evidence` object on native v14 `MutantOutcome`s. Command-level proof lives in `judgment.r2.r2_command` (§5).
- **A2 (a cold attempt that completes without failing):** if its collection and hook proof match the R2 baseline, it **is** the candidate's full run (`mode: "full"`, `evidence.command: "r2"`, bucket `survived`). No second run. If the proof does not match, the candidate gets one fresh attempt with the **declared** command (coverage on, cold off), which is authoritative.
- **A3:** `judgment.r2.cold_witness_kills` is a required explicit bool on every native v14 `judgment.r2`. It is absent on ingested judgments; the dataclass default is `None`, with a native-requiredness check.
- **A4:** `evidence` is required on `survived` outcomes and on `witness-cold` kills. It is optional on `full` kills, `crashed`, `hung` and `budget_exceeded` (a process that was killed or never started may leave no receipt). It is forbidden when `cold_witness_kills` is false, and on ledger `equivalent`s.
- **A5:** transform proof failures:

  | Static shape refusal: argv shape, override, fail-fast/order flags, xdist | Whole-lane `ERROR`/`BAD_LANE_CONFIG` before any execution. Same pattern as the `--reuse-from` refusals (runner.py `_refuse_reuse`). |

Earlier R0/R1 measurements are discarded, and `verify.py`'s independent-R2 terminals are **not** widened.   No new `ReasonCode`.
- **C2 (signals, cold mode):** a candidate attempt whose process ended by signal (`returncode < 0`) is never `killed`. During termination or deadline expiry it is unclassified (C3); otherwise it is `crashed`.
- **A6:** with `--cold-witness`, the coverage baseline (R0/R1 run) also gets the witness plugin in manifest-only mode. It is injected exactly like the liveness plugin: `argv_appended` / `env_effective` infrastructure injection, with `cli_argv_appended` frozen.
- **A7:** the auto per-candidate budget and liveness calibration keep deriving from the coverage baseline, which is slower and so more generous. The no-cov baseline's wall time is recorded as `r2_baseline_s` in the `plan` progress event for the planner.
- **A8:** order of attempts per candidate: B106 prefix replay (if `--reuse-from` applies) → cold attempt → declared-command full attempt (only on uncertainty). `--cold-witness` with `--shard` is allowed. `--reuse-from` still refuses `--shard`.
- **A9:** under v14, `reuse.py` treats schema versions **12 and 13, exactly,** as a bounded cold start that trusts only the version and consumes nothing. v11 and below stay refused, as today. A prior `witness-cold` kill is eligible for B106 prefix replay, and replay runs on the no-cov R2 command, since the declared command's pytest-cov wrapper is never replay-eligible.

**D6 addenda** (fixed in the P3 briefs so no implementer invents them):
- Native `judgment.r2` always emits `cold_witness_kills`, `r2_command` and `equivalence_ledger`, using explicit `null` where unset. `r2_command` is also `null` when the R2 claim carries no payload (refusal or error).
- `liveness.cpu_window_s` / `idle_floor_s` are `null` when liveness is inactive.
- An `evidence` object always has all six keys. When present, its collection and hook fields are non-null.
- Never-started budget leftovers keep `_outcome_of(job)` (`{"mode":"full"}`, no evidence).
- A cold attempt that ends `hung`, `budget_exceeded` or `crashed` is final, with no declared retry.
- A declared-command attempt that passes but cannot prove its collection is recorded `crashed`: R2 fails, and it never counts as a survivor.
- In cold mode the plugin stops at the first failure of any phase. A non-call failure is uncertain, which triggers the declared-command attempt.
- The ledger block requires `entry_count >= 1` and cannot be combined with `equivalence_artifact`.
- **X8 (C10) is split by producer:**
  - with a ledger declared, every `equivalent` is mode `ledger`, carries no evidence, and the counts are equal;
  - with the SQL artifact declared, no `ledger` modes are allowed;
  - with both declared, the lane is refused.
- An empty ledger is refused, and a ledger combined with `--shard` is refused.
- **Ledger placement precedes resume lookup.** Stored records for ledger candidates are ignored and reported. The ledger sha enters the judge identity whenever the lane declares a ledger.
- **Judge identity (P3B-4)** also folds in the R2 baseline's `hook_fingerprint_sha256`, so stale evidence re-executes instead of failing verify. Fingerprints normalize id-named plugins to `module.qualname` and site-packages paths to purelib-relative.
- A survivor's proof also requires `started_prefix_ok`, not `unsupported`, and session status 0 (P3B-7).
- `JudgmentR2`'s positional `[:-3]` slice becomes named `_NATIVE_REQUIRED_FIELDS` / `_NATIVE_OPTIONAL_FIELDS`.
- The gate retains the ordered no-cov manifest through `--r2-manifest PATH`: one node ID per line, each ending in `\n`.

- An active liveness `reason` is a non-empty string, as today: `auto-pytest-argv` or `declared-true` (`verdict.py:2950-2954`).
- `r2_command` is `null` when `cold_witness_kills` is `false`.
- Both baselines carry `runtime_fingerprint_sha256`. The two differ by design, because pytest-cov is loaded in the coverage baseline and blocked in R2, so there is no equality rule. The ledger audit (C10) binds both.
- The coverage baseline has 6 keys, and `wall_s` is **omitted**, not null. The R2 baseline has 7 keys.

**Verdict top level gains (C9)** an optional `campaign` block, emitted when the run used `--campaign-deadline`:
```json
"campaign": {"name": "b105-0123456789ab", "deadline_sha256": "<hex of the deadline file bytes>",
             "created_at_utc": "2026-10-01T08:00:00Z", "expires_at_utc": "2026-10-01T16:00:00Z"}
```

- `tools/b105_report_check.py --deadline FILE` is required and must match `deadline_sha256`. A screen verdict (no deadline) therefore can never pass as a qualifying one.
- `equivalence_ledger` is `null`, or `{path, sha256, entry_count, audit_sha256}` (P10).
- Counts are illustrative, never oracles.

**Verifier rules:**
- Applying the transform to `argv_declared` must give exactly `argv_transformed`.
- `coverage_baseline.collection_sha256 == r2_baseline.collection_sha256` and the counts are equal.
- Both `duplicates` values are `0`.

**`collection_sha256`** is the SHA-256 over the concatenation of `len(utf8(node_id)) ":" utf8(node_id) ","` (netstrings; the length is the UTF-8 *byte* length) for every `session.items` node ID, in order, after deselection.

**The `hook_fingerprint_sha256` preimage** is sorted lines `hook|plugin_token|module|relpath|flags` over this fixed hook list:
- `pytest_runtestloop`
- `pytest_runtest_protocol`

- `pytest_runtest_logreport`
- `pytest_runtest_call`
- `pytest_runtest_setup`
- `pytest_runtest_teardown`
- `pytest_collectreport`

`relpath` is normalized as follows:
- under the pytest `rootpath` → relative to it;
- under `_pytest` → `_pytest/...`;
- the witness/liveness plugins → their module token.

**`runtime_fingerprint_sha256`** is the SHA-256 of canonical JSON `{python: sys.version, implementation, machine, pytest: pytest.__version__, plugins: sorted "dist==version" from config.pluginmanager.list_plugin_distinfo()}`.

## 6. Distributed / async evidence (foresight in P3b, implemented in P9)

These are the things every package must preserve, even before P9 exists:
1. **Everything a worker needs is named by identity, never by local path.** Every record is bound by `judge_sha256`, which after P3 includes the tree, the effective R2 argv, the cold policy, the transform, the collection digest and the runtime fingerprint. Nothing may read state from a sibling worker's filesystem.
2. **Records are per-candidate files** (`<state-dir>/<candidate-hash>.json`, already atomic). No package may introduce a single mutable campaign database.
3. **Progress is informational.** Only state records plus the consolidating verdict are evidence.

P9 adds (revised by C12 and C8):
- `assay state import --lane L --from DIR --into STATE_DIR --require-campaign-deadline FILE [--receipt PATH]`.
  - It runs **inside tester-unified** through gate mode `b119-import`, never on the host, because the identity binds the exact-OID wheel.
  - It validates each record against the store's `CAMPAIGN-IDENTITY` file (no `.json` extension, so existing `*.json` globs in tests are unaffected) and against the deadline binding.
  - An **identical duplicate** is skipped.
  - A **conflict** (same candidate, different bucket) refuses the whole import, writes nothing, and names both records. Kills that differ only in execution mode are reported, not treated as conflicts.
  - A **mismatch** (wrong identity, foreign candidate, unbound deadline, non-final bucket such as hung, budget_exceeded or crashed, or a pilot store identified by its `PILOT-STATE` sentinel and `selection_sha256`) is refused per record, with the reason.
  - An exclusive `STORE/.lock` is honored by both `run` and `import`. `assay run` refuses a locked state dir with a whole-lane `BAD_LANE_CONFIG`. Bytes are re-hashed at write time. The receipt is journaled.
  - Gate arms and lanes: `b119-worker` runs a fixed `--shard k/N` into a local store, and `b119-import` creates the deadline, runs shard 0 into STORE and imports the inbox. The qualifying arm gains an `assay state audit-check` step that re-executes the audit sample.
- **Trust model** (stated honestly): identity-matched records written by a worker are trusted; `SHA256SUMS` only proves transfer. Mitigation: consolidation re-executes a deterministic audit sample of imported records (2% per source, minimum 5, seeded by the campaign name). Any disagreement refuses that source.
- **Provisional** means records in an inbox directory that has not yet been imported. **Accepted** means records inside the campaign state dir, written by `state import` or by a local worker of the same campaign.
- **Consolidation** is `assay run <lane> --resume --state-dir STATE_DIR --cold-witness ...` with no `--shard`. It re-runs the baselines (their manifests must match the recorded identity), resumes every accepted record and executes anything missing. The result is one ordinary verdict.
- **The worker runbook** (in the P9 brief) covers host enrolment by measurement, per-host cgroup RAM, `--shard k/N` with a fixed N, record transfer, and the conflict policy.
